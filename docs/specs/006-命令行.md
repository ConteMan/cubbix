## 结论摘要

| 项 | 结论 |
| --- | --- |
| 入口形态 | 独立二进制 `cubbix`，随包放在 `Cubbix.app/Contents/Resources/bin/cubbix`，由设置页在 `~/.local/bin` 建符号链接；不需要任何管理员授权 |
| 通信 | **Unix domain socket**，`~/Library/Application Support/cubbix/cli.sock`（路径过长时兜底到字面 `/tmp/cubbix-cli-<uid>.sock`），目录 0700、socket 0600；**两边都校验对端 uid**（应用拒绝别的用户的连接，工具也拒绝把正文发给别的进程），协议是「一行 JSON + 可选定长正文」 |
| 能力边界 | 动作集合与 URL 白名单**同一套**（`awake`／`awake.stop`／`awake.toggle`／`json.new`／`palette`／`settings`）+ 一条只读 `status`；参数语法与命令面板**同一个解析器**（`parseAwakeArg`），不自造第二套 |
| 走哪条代码路径 | 除 `awake.toggle` 外的改状态动作都经 `runURL`（因此 `a.lidURL = true`，`enableLid` 的 `authorize` 恒为假，**绝不弹授权**）；`awake.toggle` 走快捷键那条 `toggleAwakeResult`，**不是** URL 的递归分支（§4.2） |
| 不写记忆 | CLI 自己不写 `AwakeMinutes`／`AwakeUntil`／`AwakeMode`，不写收藏与最近使用，不写 `settingsError`。两个**既有**副作用要写明：`AwakeSession`（崩溃恢复）会写；合盖**成功**时 `completeLid` 会把 `AwakeLid` 置真并落盘（`lid_app.go` 约 44 行，URL 同样），v1 不改这条既有行为（§2.3） |
| 合盖保持 | 只走「已安装且已授权」的助手；未授权时回 `LidAuthNeeded`，**绝不**弹管理员授权（与 004 §6.2 第 6 条对 URL 的规定一致）；空截止由助手的 12 小时硬上限兜住 |
| 静音 | `a.quiet` 关掉 `announce` 与 `lidURLFeedback`；**异步合盖回调必须捕获 quiet 再进 `RunOnMain`**，否则 `applyCLI` 的 `defer` 已经复位（§4.4 第 8 条） |
| 未运行 | 需要改状态的动作默认后台拉起：**先用自己所属的 `.app` 路径** `open -g -a`，失败再 `-b com.conteman.cubbix`；只读的 `status`／`version` 不拉起 |
| 输出 | 人读一行（`status` 三行，文案由应用按当前界面语言给出，复用 `awakeStatus`／`awakeFeedbackMessage`）；`--json` 是稳定接口，字段只增不改，**带 `--json` 时任何退出码都只输出一行 JSON** |
| 提示 | 默认**不**弹 002 的屏幕提示（stdout／退出码就是反馈）；`--notify` 才走 `a.announce` 那一条，并受 `FeedbackMode` 约束 |
| 纯 Go | CLI 只 import 标准库；本机实验：`CGO_ENABLED=0 GOTOOLCHAIN=go1.27.1 GOOS=darwin GOARCH=arm64 go build` 通过，`go vet` 干净，运行时不需要 MyGo（§5.5） |
| 主要未实测项（均标「需实测」） | 真实双进程握手与接管、跨 uid 的端到端拒绝、`open -g -a`／`-b` 拉起菜单栏应用的实际时序与「两份已登记副本」的后果、设置页按钮的实机表现、异步合盖回调在真机上是否真的静音、`--follow` 身份串在真机 `ps` 输出上的形状、App Translocation 的判定、真实 Developer ID 重签后 CLI 的 identifier 是否保留（§8.3） |

## 1. 使用场景与命令

### 1.1 场景

维护者的原话是「CLI 支持，方便其他软件等联动」。实际使用者不是人，而是脚本、Agent、Raycast 脚本命令或「快捷指令」：

| # | 场景 | 现在的做法 | 有了 CLI 之后 |
| --- | --- | --- | --- |
| 1 | 跑长任务前开一小时常亮 | `open "cubbix://awake?minutes=60"`，拿不到结果 | `cubbix awake on --minutes 60 \|\| exit` |
| 2 | 任务结束后确认常亮已停 | 只能看菜单栏 | `cubbix awake status --json \| jq .state.awake.active` |
| 3 | Agent 把一段 JSON 结果开成窗口 | 写临时文件再交给别人打开 | `cat result.json \| cubbix json new` |
| 4 | 脚本里判断「这次能不能合盖」 | 不知道 | `cubbix awake on --minutes 120 --lid`，未授权时非零退出，脚本自己决定 |
| 5 | 在 Raycast 脚本命令里叫出面板／设置 | 拼 URL | `cubbix palette`／`cubbix settings --page shortcuts` |

三条设计要求直接来自这些场景：**要能拿到状态**（1、2）、**要能拿到错误**（4）、**要能被别的程序调用而不打扰人**（全部，尤其 3 的管道用法）。

### 1.2 命令表

| 命令 | 作用 | 应用必须在运行吗 |
| --- | --- | --- |
| `cubbix awake on [选项]` | 开启常亮（时长／到某时刻／跟随进程／模式／合盖） | 否：默认后台拉起，`--no-launch` 时直接失败 |
| `cubbix awake off` | 停止常亮，含合盖恢复 | 同上 |
| `cubbix awake toggle` | 开／关切换，与 ⌃⌥⌘K 走同一个 `toggleAwakeResult`（含记忆里的合盖偏好） | 同上 |
| `cubbix awake status` | 只读：常亮一行状态 | **是**：不拉起应用 |
| `cubbix status` | 只读：常亮 + JSON 窗口数 + 版本 | **是**：不拉起应用 |
| `cubbix json new [选项]` | 新建 JSON 窗口（空白或写入正文） | 否：默认后台拉起 |
| `cubbix palette` | 打开命令面板（等价于 ⌥.） | 否：默认后台拉起 |
| `cubbix settings [--page NAME]` | 打开设置页 | 否：默认后台拉起 |
| `cubbix version` | 打印版本与来源包路径 | 否：不连应用 |
| `cubbix help [命令]` | 帮助 | 否：不连应用 |

`awake toggle` 与 ⌃⌥⌘K 的关系要说清：**两者都进 `awake_app.go` 的 `toggleAwakeResult`（约 113 行）**，因此「记忆了合盖偏好」时会话照样带着合盖开始（未授权则由 `enableLid` 返回 `LidAuthNeeded`）。URL 的 `awake.toggle`（`palette.go` 的 `runURL`，约 832 行）现在会在「记忆了合盖、请求又没有 `HasMinutes`」时返回 `LidAuthNeeded`，与快捷键不一致；本次**不改 URL 语义**（003 已定稿，改它要单独走一遍），CLI 也不复用那条递归分支（§4.2）。

### 1.3 `awake on` 的参数

| 选项 | 取值 | 缺省 | 说明 |
| --- | --- | --- | --- |
| `--minutes N` | 整数 `0`–`525659`（`awakeMinutesMaximum`）；`0` = 不限时 | 无 | 固定时长，与 URL 的 `minutes` 同口径 |
| `--until HH:MM` | 24 小时制 `H:MM`／`HH:MM`，交给 `untilTime`（`keepawake.go`，约 209 行）校验；早于或等于现在时顺延到明天 | 无 | 与 `常亮 until 18:30` 同一条规则 |
| `--follow PID` | 正整数 | 无 | 跟随进程，等价于面板「跟随进程…」选中的那个 PID |
| `--mode screen\|tasks` | 枚举 | 记忆里的 `config.AwakeMode` | 与 `常亮 … tasks`、URL 的 `mode` 同义 |
| `--lid` / `--no-lid` | 布尔 | 不给＝记忆里的 `awake_lid`（`a.lidPreference()`） | 见 §3.6；不写记忆 |
| `--notify` | 布尔 | 否 | 走 002 的提示（§7） |
| `--json` | 布尔 | 否 | JSON 输出（§1.5） |
| `--no-launch` | 布尔 | 否 | 应用没运行时不拉起，直接退出 3 |
| `--timeout DURATION` | `1s`–`60s` | `5s` | 连不上时等应用就绪、以及读响应的上限 |
| `--socket PATH` | 路径 | 默认路径（§3.2） | 只在调试与集成测试里用，`help` 里放在「调试」段 |

组合规则（按顺序判定，违反即用法错误，退出 2）：

1. `--minutes`、`--until`、`--follow` **至多一个**；都不给＝用记忆的时长／截止（`a.selectedSession()`）。
2. `--minutes 0` 等价于「不限时」，与 `常亮 ∞`、URL 的 `minutes=0` 同义。
3. `--until` 与 `--minutes` 同时出现、`--follow` 与二者任一同时出现 → 退出 2，提示 `--minutes/--until/--follow are mutually exclusive`。
4. `--notify` 只对会改状态的命令有效（`awake on/off/toggle`、`json new`、`palette`、`settings`）；在 `status`／`version`／`help` 上用它 → 退出 2。
5. `--lid` 与 `--no-lid` 同时出现 → 退出 2。
6. 参数在 CLI 侧先用共享解析器校验一遍（§2.1），失败就**不连应用**、按 §1.4 退出；应用侧收到后**再校验一遍**，不信任对端。
7. `--lid`／`--no-lid` 显式给出时，请求里必须带 `HasLid`（§3.3 的 `lid` 字段是 `*bool`）：不给就落到 `config.AwakeLid`，显式给 `false` 才能关掉记忆里的合盖。
8. `awake off`／`awake toggle` 不接受 `awake on` 的时长与模式选项（`--minutes`／`--until`／`--follow`／`--mode`／`--lid`／`--no-lid`）→ 退出 2：两者用的是记忆会话（`selectedSession()`），接受这些选项只会让脚本以为它们生效了。`--notify`／`--json`／`--no-launch`／`--timeout`／`--socket` 照常可用。

### 1.4 退出码

| 码 | 含义 | 典型来源 |
| --- | --- | --- |
| `0` | 成功（请求已被接受并执行完） | 全部命令 |
| `1` | 意外错误：协议不符、响应损坏、内部错误 | `bad-request`、`protocol-mismatch`、`untrusted-peer`、`internal`、JSON 编码失败 |
| `2` | 用法错误：未知子命令／选项、参数语法非法、互斥选项、正文超限、本地读文件失败 | `usage` |
| `3` | 应用不可用：没在跑、socket 被占或已失效、没能拉起、拉起后没就绪、正在退出 | `not-running`、`refused`、`stale-socket`、`quitting` |
| `4` | 应用拒绝执行：参数被应用侧判非法、格子已停用、合盖未授权、进程已结束、忙 | `code` 为动作错误键或 `disabled`／`busy`（§3.3） |
| `5` | 连上了但没有在 `--timeout` 内拿到响应 | `timeout`（应用主线程卡住，例如某个原生模态面板还没关） |

约定四点：

- 退出码与 `--json` 无关，始终反映结果；脚本只看退出码 + `--json` 的 `code` 即可。
- 人读的错误写 **stderr**，成功的结果写 **stdout**；两者不混。
- **带 `--json` 时，无论退出码是几，stdout 都恰好只有一行 JSON**（用法错误也一样，`code:"usage"`）；这时 stderr 不再重复写同一句话。不带 `--json` 时错误才写 stderr。
- 应用侧的文案变化不改退出码；退出码变化算不兼容改动。

### 1.5 输出

**人读**（默认）。一行结果，文案由应用生成，所以与菜单栏 tooltip、002 的提示是同一句话：

| 命令 | stdout |
| --- | --- |
| `awake on` / `awake toggle` | `awakeFeedbackMessage` 那一句，例如「保持屏幕常亮 · 1 小时」「仅保持任务 · 合盖也保持 · 剩余 59:12」 |
| `awake off` | `ToastAwakeOff`（「常亮已关闭」） |
| `awake status` | `awakeStatus(locale, now)`（`awake_app.go`，约 216 行），例如「保持屏幕常亮 · 合盖也保持 · 剩余 1:24」 |
| `status` | 三行：上一行 + `CLIStatusJSON`（「JSON 窗口 2」）+ `Cubbix 0.4.0` |
| `json new`／`palette`／`settings` | 不输出（成功即退出 0）。`json new` 不打印窗口名，名字归窗口标题 |
| `version` | 两行：`Cubbix 0.4.0` 与它所属的包路径（默认 `/Applications/Cubbix.app`）；取法见 §5.5 |
| `help` | 用法文本 |

多行结果的取词方式：应用在响应里给 `lines`（1–3 条已本地化的字符串），CLI 逐行打印。`message` 只承载**单行**结果（`run` 类命令与错误），`status` 用 `lines`；两者都由应用生成，CLI 不认识任何一句中文或英文。

**`--json`**（稳定接口）。一次调用输出**恰好一个** JSON 对象加一个换行，不输出其它内容：

```json
{
  "v": 1,
  "ok": true,
  "code": "",
  "message": "保持屏幕常亮 · 1 小时",
  "state": {
    "version": "0.4.0",
    "tiles": { "awake": true, "json": true },
    "awake": {
      "active": true,
      "mode": "screen",
      "minutes": 60,
      "until": "",
      "end": "2026-11-04T12:30:00Z",
      "remainingSeconds": 3599,
      "follow": null,
      "lid": {
        "capable": true,
        "available": true,
        "state": "on",
        "reason": "",
        "batteryMin": 20
      },
      "error": ""
    },
    "json": { "windows": 2 }
  }
}
```

失败时同一个对象，`ok:false`、`code` 非空、`state` 省略或为 `null`：

```json
{ "v": 1, "ok": false, "code": "LidAuthNeeded", "message": "合盖保持需要在系统设置里允许 Cubbix" }
```

`status` 的响应把多行人读文本放进 `lines`，`run` 类命令用 `message`（两者可以同时出现，脚本只读 `state`）：

```json
{ "v": 1, "ok": true, "code": "",
  "lines": ["保持屏幕常亮 · 合盖也保持 · 剩余 1:24", "JSON 窗口 2", "Cubbix 0.4.0"],
  "state": { … } }
```

CLI 本地的失败（用法错误、连不上、超时）由 CLI 自己写同形状的对象，`state` 为 `null`：

```json
{ "v": 1, "ok": false, "code": "usage", "message": "--minutes, --until and --follow are mutually exclusive." }
```

字段规则（写进实现约定，并由 §8.1 的 golden 测试守住）：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `v` | int | 协议版本，`1`。**改动语义才升版本**；加字段不升 |
| `ok` | bool | 是否成功 |
| `code` | string | 成功为 `""`；失败见 §3.3 |
| `message` | string | 单行人读结果；失败时是错误文案。脚本不要解析它 |
| `lines` | []string | 仅 `status`：1–3 行已本地化文本（§1.5 的人读形态）。`run` 命令不带 |
| `state` | object／null | 成功时是执行完的即时快照（`status` 与改状态的命令都带）；CLI 本地失败为 `null` |
| `state.version` | string | `runningVersion()`（`main.go`） |
| `state.tiles.awake`／`.json` | bool | `config.AwakeEnabled`／`config.JSONEnabled` |
| `state.awake.active` | bool | `a.awake.snapshot().Active` |
| `state.awake.mode` | `"screen"`／`"tasks"` | 会话模式；未运行时为 `""` |
| `state.awake.minutes` | int | 会话的固定分钟数；`0` 表示不限时或不适用 |
| `state.awake.until` | string | 会话记录的 `AwakeUntil`；没有则 `""` |
| `state.awake.end` | RFC3339 UTC／null | 截止时刻；不限时、跟随进程为 `null` |
| `state.awake.remainingSeconds` | int／null | 与 `end` 同时为 `null` 或同时有值；向上取整同 `awakeSuffix` |
| `state.awake.follow` | `{"pid","name"}`／null | `Session.PID > 0` 时填 |
| `state.awake.lid.capable`／`.available` | bool | `a.lidCapable()`／`a.lid.Available()` |
| `state.awake.lid.state` | 枚举 | `off`、`enabling`、`on`、`stopping`、`restore-failed`、`helper-gone`、`blocked`、`error`（`lidState` 的映射，`lid_controller.go`，约 41 行） |
| `state.awake.lid.reason` | string | 资源键，空表示无异常 |
| `state.awake.lid.batteryMin` | int | `config.AwakeLidBatteryMin` |
| `state.awake.error` | string | `awakeState.Error`（资源键） |
| `state.json.windows` | int | `len(a.jsonDocuments)` |

**不放进 JSON 的东西**：JSON 窗口名与文件路径（文件名可能敏感）、配置路径、用户名、任何进程列表。`status` 只需要「有几个窗口」，不需要「叫什么」。

## 2. 与命令面板、URL 的关系

### 2.1 复用表（禁止另写一套）

| CLI 行为 | 复用的函数 | 位置 |
| --- | --- | --- |
| 时长／时刻／不限时的语法 | `parseAwakeArg` → `parseAwakeDuration` → `awakeUntilArg`／`parseAwakeMinutes`；上限 `awakeMinutesMaximum` | `commands.go`，约 836／854／899 行 |

### 2.2 与 URL 白名单的关系

URL 是**窄**通道（任何应用与网页都能触发），CLI 是**同一批动作**的本地通道。三条关系：

1. **动作集合相同**：`paletteURLRequest.Kind` 的六个取值（`awake`、`awake.stop`、`awake.toggle`、`json.new`、`palette`、`settings`）就是 CLI 能触发的全部动作，一个一个对应 `runURL` 的 `switch`。CLI 多了 `status`，它是只读的。
2. **有三处 URL 表达不了，只有 CLI 有**：`--until`（到某时刻）、`--follow PID`（跟随进程）、只读 `status`。这三条用的是**面板已有的语义**（`untilTime`、`processIdentity`、`awake.snapshot()`），不新增动作、不新增权限，也不放宽 URL 的任何校验：`parsePaletteURL` 永远不产生这两个字段（§4.4 第 3、4 条 + 一条测试）。因此「动作白名单封顶」这句话只对**动作种类**成立，不能拿来当「协议能力已被 URL 封顶」的理由——§3.5 第 8 条按真实理由重写过。
3. **URL 的既有约束照旧**：`lid` 在 URL 上要求 `minutes` 1–480 且助手已授权；CLI 的 `--lid` 沿用「已授权」这一条；**显式**给出 `--lid` 时的时长要求是「有明确截止（`--minutes` 1–480、`--until` 不晚于 480 分钟后）或 `--follow`」，而记忆驱动的合盖按快捷键语义处理（§3.6）。

### 2.3 不写的东西

CLI 路径必须**不**做下面这些（与 003 §8.3 第 8、10 条同一条纪律）：

1. 不写记忆：CLI 自己**不写** `config.AwakeMinutes`／`AwakeUntil`／`AwakeMode`。两个**既有**副作用不算 CLI 写记忆，但要写明：(a) `startAwake` 触发的 `awakeChanged` 会写 `AwakeSession`（崩溃恢复记录）；(b) 合盖**成功**时 `completeLid` 会把 `config.AwakeLid` 置真并落盘（`lid_app.go` 约 44 行 → `awakeChanged` → `save`），URL 路径同样如此。v1 不改 (b)：要它只对面板生效就得动 004 的语义，那要单独走一遍；文档与测试都按「`--lid` 成功会记住合盖偏好」写，不假装 CLI 完全不碰配置。
2. 不调用 `setDuration`／`setMode`／`startAwakeWith`（三者都会写记忆，`awake_app.go` 约 122／138 行、`commands.go` 约 394 行）。
3. 不设 `a.lidAuthorize`：那是「允许弹管理员授权」的开关，只有设置页与卡片面板的手动动作能置位（`awake_view.go` 约 79 行、`menubar_panel.go` 约 229／240／253 行、`commands.go` 约 395 行）。
4. 不调用 `recordRecent`／`toggleFavorite`（`palette.go`，约 391／375 行）：CLI 不是人在面板里选命令，写「最近使用」会把它挤满。
5. 不写 `settingsError`／`paletteState.errorKey`：错误只回到发起者（stdout／stderr）。
6. 不读剪贴板：`json new` 走 `openJSONText`，不走 `newJSONWindow`（后者读剪贴板，`json_app.go`，约 127 行）。
7. 不接受文件路径：`json new --file` 由 **CLI 自己**读文件，只把正文交过来；应用侧仍然只收文本。
8. 不额外打开界面：不改激活策略、不弹对话框、不主动打开设置页（`settings` 命令自己就是打开设置页，属于该动作的既有语义，与 URL 相同）；`json new`／`settings` 会激活应用，那也是它们自己的既有语义。

## 3. 与运行中应用的通信

### 3.1 方案比较

| 方案 | 能拿到状态与错误 | 安全面 | 代价 | 结论 |
| --- | --- | --- | --- | --- |
| (a) 只走 `open -g cubbix://…` | **不能**：`open` 只负责送达，退出码反映的是 `open` 而不是 Cubbix；错参数与失败全都看不见 | 与现有 URL 完全相同（最小） | 几乎为零 | 只保留为文档里的手工用法，**不做 CLI 的实现** |
| (b) 应用开一个仅当前用户可访问的 Unix socket | **能**：请求／响应、状态、错误键 | 比 URL 多一个本地入口，但动作种类不放宽（§2.2）；目录 0700 + socket 0600 + 对端 uid 校验 | 约 300 行服务端 + 约 200 行 CLI，协议要写死并加不变量测试 | **采用** |
| (c1) socket 换成 CFMessagePort／XPC | 能 | 与 (b) 相同量级 | 要手写 CoreFoundation 的 port 回调与 reply 链；004 §3.3 已经因为「没有任何可参考的绑定、无法在本机验证」否掉过 XPC | 不选 |
| (c2) 应用轮询一个「命令目录」里的文件 | 勉强（要靠第二个文件回结果） | 文件权限可写错，且要处理半写文件 | 省一次 listen，但多一套状态文件与清理 | 不选 |
| (c3) 状态写进一个 `status.json`，CLI 只读它 | 能读到状态，但拿不到单次请求的错误，且数据随时过期 | 只读，最小 | 「开一次常亮并知道成没成」做不到 | 不选 |
| (c4) 回环 TCP | 能 | **更差**：同机任何用户都能连，端口还可能被别的进程占 | 与 (b) 相当 | 不选 |

选 (b) 的另一个理由：仓库里已经有一份同款实现可以照抄结构——`internal/lid/transport.go` 的 `Server.Serve`（约 23 行起，换行分隔 JSON、单次读写超时、`net.ListenUnix`、先校验对端再读内容）与 `internal/lid/security_darwin.go` 的 `VerifyPeer`（`getsockopt` + SecCode）。CLI 服务端不发明新传输。

### 3.2 路径、权限、生命周期

| 项 | 规定 |
| --- | --- |
| 路径 | `~/Library/Application Support/cubbix/cli.sock`。应用侧与 `config.toml` 同目录（`filepath.Dir(a.path)`）；CLI 侧用 `os.UserHomeDir()` + `Library/Application Support/cubbix`（与 `main.go` 的 `configPath` 同一拼法，约 674 行），不读 `$TMPDIR` |
| 目录权限 | `os.MkdirAll(dir, 0700)`；已存在但组／其他人可写时照常服务，但记一条日志（真正的门是 §3.5 的 uid 校验与客户端的属主校验） |
| socket 权限 | `ListenUnix` 成功**之后**才 `os.Chmod(path, 0600)`。顺序不能反：`Listen` 之前那个路径上可能还是别人的 inode（同 004 §3.3 的理由） |
| 路径长度 | `sun_path` 是 104 字节（SDK `sys/un.h`，本轮已核对）。拼出来的路径 ≥ 100 字节时，改用**字面** `/tmp/cubbix-cli-<uid>.sock`（例：`/tmp/cubbix-cli-501.sock`）。**不用 `os.TempDir()`**：`$TMPDIR` 在终端与 `open` 拉起的进程之间可以不同，两边会算出两个路径，谁也连不上。兜底路径只依赖 `os.Getuid()` 与字面 `/tmp`，因此两端一致。`/tmp` 是世界可写的，所以兜底路径额外做两件事：socket 的属主必须是当前 uid（否则不删、不服务，记一条日志）；服务端只删自己那个 inode（见下一行）。计算函数放在 `internal/cli`，CLI 与服务端共用 |
| 创建 | `ready()` 里起服务端（`a.startCLIServer()`），与 `registerPaletteShortcut`／`registerURLScheme` 同一段 |
| 接管与退出 | 顺序照 `mygo@v0.6.2/single_instance.go` 的 `RequestSingleInstanceLock`（约 53-124 行）与 `releaseSingleInstanceLock`（约 152-162 行），见下面两段 |
| 并发连接 | 每条连接一个 goroutine；**槽位在 `Accept` 之后、读第一个字节之前占用**（见下），同时在处理的连接数上限 8，第 9 条直接回 `{"ok":false,"code":"busy"}` 并关闭（避免 8 个 64 MiB 正文同时驻留，也不让「先慢慢发一行、再挂住」占满进程） |

**启动时的接管**（而不是「`Listen` 失败再 `Dial`」）：

```
for attempt := 0; attempt < 5; attempt++ {
    if conn, err := net.DialTimeout("unix", path, time.Second); err == nil {
        conn.Close()            // 另一个实例在服务：不删、不服务，记一条日志后放弃
        return
    }
    os.Remove(path)             // 没人应答：残留文件，删掉重绑
    ln, err := net.ListenUnix("unix", addr)
    if err == nil { 接管成功，进入就绪；break }
    if !errors.Is(err, syscall.EADDRINUSE) { 失败退出 }
    sleep(backoff)              // 竞态输给了别人，下一轮会连上它
}
```

`Listen` 成功后立刻 `ln.SetUnlinkOnClose(false)`，并 `os.Stat(path)` 把 inode 记下来。上面循环开始前还要先 `os.Stat` 一次：路径存在但**属主不是当前 uid** → 不删、不服务，记一条日志（需要这条的是 `/tmp` 兜底路径；家目录那条属主必然是自己）。

**退出**（`beforeQuit`）：

1. `listener.Close()`，让 `Accept` 返回；**不依赖** Go 的默认 unlink（已关掉）。
2. 等在飞请求收尾，最多 1 秒；超时就放弃等待（连接随进程退出关闭）。
3. `fi, err := os.Stat(path)`；只有 `os.SameFile(fi, savedStat)` 为真才 `os.Remove(path)`——这段时间里另一个实例可能已经绑了新 socket，删它等于把新实例踹掉。

`SetUnlinkOnClose(false)` + `os.SameFile` 这两步是必须的：`UnixListener.Close` 默认会 unlink 那个路径，而「等在飞请求之后才删」的窗口正好覆盖别人的重新绑定。上面这套顺序是对照 `mygo@v0.6.2/single_instance.go` 读出来的，**真实双进程的接管、压接与退出清理需实测**（§8.3）：单测只能造一个残留文件，造不出两个真实例同时跑的时序。

### 3.3 协议

传输：`SOCK_STREAM`。请求与响应都是**一行 JSON**（`\n` 结尾），需要带正文时，请求行之后紧跟**恰好 `bytes` 字节**的原文，不再有分隔符：

```
→ {"v":1,"id":"9f2c…","op":"run","action":"json.new","bytes":12}\n{"a":1,"b":2}
← {"v":1,"id":"9f2c…","ok":true,"code":"","message":"","state":{…}}\n
```

为什么不用「一行装下所有正文」：`jsonFileLimit` 是 64 MiB（`json_documents.go`，约 15 行），一行 64 MiB 的 JSON 要把正文做转义，既放大 1.2 倍又要一次分配 130 MiB，还要放弃「单行上限」这个最简单的防御。定长正文帧把「元数据」与「正文」分开，两个上限各自独立：行 ≤ 4096 字节，正文 ≤ 64 MiB。

| 项 | 规定 |
| --- | --- |
| 版本 | `v` 必须是 `1`，否则 `protocol-mismatch` 并断开 |
| `id` | 客户端生成，`^[A-Za-z0-9_-]{1,64}$`；响应原样回带，用于对齐（也是「串话」的防线） |
| `op` | 只接受 `status`、`run` |
| `action` | `run` 时必填，取值＝`paletteURLRequest.Kind`：`awake`、`awake.stop`、`awake.toggle`、`json.new`、`palette`、`settings` |
| 行上限 | 4096 字节。读超即断开（不回响应：对端已经越界，回什么都可能被当成有效数据） |
| 正文上限 | `jsonFileLimit`（64 MiB）。`bytes` 只允许出现在 `json.new` 上，其余动作带 `bytes>0` → `bad-request` |
| 正文编码 | UTF-8；`!utf8.ValidString` → `bad-request`（与 `parsePaletteURL` 对 `text` 的检查同一口径） |
| 超时 | 连接后读请求行 10s；读正文 30s；写响应 5s；主线程上的动作最多等 15s（`stopAwake` 里有助手往返，最长约 5s） |
| 响应上限 | 4096 字节（状态对象几百字节；`message` 一句话、`lines` 最多三行，加起来仍远低于这一上限） |
| 并发槽位 | 在 `Accept` 之后、读请求行之前占用；响应写完（或连接关闭）后释放。第 9 条连接拿到 `busy`，且**不读**它的任何字节。因为这时还没读到 `id`，`busy` 的响应是 `{"v":1,"id":"","ok":false,"code":"busy"}`——CLI 本来就知道自己发的是哪个请求，`id` 为空不影响它 |
| 未知字段 | 忽略（与 004 的协议一致），便于以后加字段 |

请求字段（`op:"run"`）：

| 字段 | 类型 | 适用 | 说明 |
| --- | --- | --- | --- |
| `action` | string | 全部 | 见上表 |
| `arg` | string | `awake` | 归一后的参数原文（`1h30m`、`until 18:30`、`∞`、空串＝用记忆设置）；≤ 128 字节；**不含**合盖修饰词 |
| `mode` | string | `awake` | `screen`／`tasks`；缺省＝`config.AwakeMode` |
| `lid` | `*bool` | `awake` | `null`（缺省）＝用 `a.lidPreference()`；`true`／`false` ＝显式的 `HasLid`（**必须**按这个语义实现，否则 `--lid`／`--no-lid` 会被记忆值盖掉） |
| `follow` | int | `awake` | `>0` 时表示跟随该 PID；此时 `arg` 必须解析成 `awakeArgDefault` |
| `text` | **只用正文帧** | `json.new` | 见 `bytes` |
| `bytes` | int | `json.new` | 正文长度，`0` 表示空白文档 |
| `blank` | bool | `json.new` | 与 `bytes>0` 并存时以正文为准（同 URL 的 `text` 优于 `blank`） |
| `notify` | bool | `run` | 对应 `--notify`：`false`（缺省）时 `handleCLI` 在主线程上把 `a.quiet` 置真，`true` 时保持假（§4.3、§7）。`op:"status"` 上没有这个字段 |
| `page` | string | `settings` | `general`／`tiles`／`shortcuts`／`about`；其它值或缺失 → 通用页（与 `cubbix://settings` 一致） |

`page` 到 `a.page` 的整数映射（`parsePaletteURL` 已核对，`palette.go` 约 754 行）：`general` 或缺失＝`0`、`about`＝`1`、`tiles`＝`2`、`shortcuts`＝`3`。CLI 侧只认这四个字符串，其它值退出 2（§8.1）；应用侧收到整数后照现有 `runURL` 的 `settings` 分支执行。

`code` 的取值（稳定集合）：

| 分类 | 值 | 说明 |
| --- | --- | --- |
| 成功 | `""` | |
| 协议 | `bad-request`、`protocol-mismatch`、`untrusted-peer`、`busy`、`quitting` | 服务端产生 |
| 客户端本地 | `usage`、`internal`、`not-running`、`refused`、`stale-socket`、`timeout` | CLI 产生，应用永远不发这些 |
| 动作 | `AwakeStartError`、`DurationError`、`TimeError`、`ProcessEnded`、`LidAuthNeeded`、`LidNeedsMinutes`、`LidUnsupported`、`LidDevBuild`、`LidBatteryTooLow`、`LidEnableFailed`、`LidRestoreFailed`、`LidForeign` | 全部是现有资源键（`LidNeedsMinutes` 是 004 命名空间下新增的一个）。`code` **不**直接拿 `err.Error()`：走 §4.2 的 `cliErrorKey` 白名单（`paletteErrorKey` + `ProcessEnded`），表外的错误一律收成 `AwakeStartError` |
| 格子停用 | `disabled` | **由 `applyCLI` 自己产生**（§4.2）：`startAwake` 内部那句 `"keep awake disabled"`（`awake_app.go`，约 45 行）不是协议码，绝不能原样外泄；CLI 路径上它不可能出现，因为 `applyCLI` 先判 `config.AwakeEnabled`／`JSONEnabled` |

`quitting`、`disabled`、`usage` 是三个**协议／本地**码（不是界面文案键）：`quitting` 表示应用正在退出（`a.quitting`），`disabled` 表示格子已停用，`usage` 表示 CLI 自己的参数错误。它们不挂资源键；CLI 给英文提示（§9.3），`message` 在 `disabled`／`quitting` 上留空。

### 3.4 应用没在跑的时候

| 步骤 | 行为 |
| --- | --- |
| 1 | 连 socket（`DialTimeout` 3s）。连上就发请求 |
| 2 | 连不上且 `--no-launch` → 退出 3，「Cubbix is not running」 |
| 3 | 否则拉起应用：**先**用 CLI 自己所属的包（`os.Executable()` → `filepath.EvalSymlinks` → 若是 `…/Cubbix.app/Contents/Resources/bin/cubbix`，取三级父目录）跑 `open -g -a <app>`；失败再退到 `open -g -b com.conteman.cubbix` |
| 4 | 每 50ms 重试连接，直到 `--timeout`（默认 5s）。超时 → 退出 3 |
| 5 | 连上后照常发请求；`--timeout` 同时也限读响应 |

为什么把顺序反过来（先路径、后 bundle id）：

- 先 `-b` 时，LaunchServices 可能选中**另一份已登记的副本**（例如旧版还在别处），而两份共用同一个 `cli.sock` 路径——CLI 会连上「不是自己所属的那个应用」，版本与行为都对不上。用自己所属的 `.app` 路径拉起，一定拉起与 PATH 里那个 `cubbix` 同一份。
- `open -g` 比 `open` 少一次前台切换：`-g` 是 `--background`（`open` 的用法输出本轮已核对）。Cubbix 是 `LSUIElement`，启动本来也不出窗口。
- `-b` 保留为兜底：包被搬走、或 CLI 被单独拷出 `.app` 之后仍能工作。

其他细节：

- **已核对**：本机实验里 `os.Executable()` 返回的是**调用时**的路径（符号链接没有被解析），`filepath.EvalSymlinks` 才得到真实路径（§5.5）。所以「用 `os.Executable` 直接推出 `.app` 路径」在 `~/.local/bin/cubbix` 这种安装方式下**是错的**，必须先解析符号链接。
- **需实测**：`open -g -a <app>` 与 `-b` 的实际时序、以及「两份已登记副本」在 LaunchServices 下到底拉起哪一份，本轮只读了 `open` 的用法输出，没有真机验证。实测时重点看两件事：拉起的是不是 PATH 里那个包（`cubbix version` 对得上）、另一份在跑时 CLI 请求落到谁（共用 `cli.sock`，后启动的那份不服务，§3.2）。`-a` 与 `-b` 都不接受「等待就绪」，所以步骤 4 的轮询不能省。
- `status`／`version`／`help` 不启动应用：状态查询去拉起一个应用是意外副作用，脚本里更不可接受。
- 服务端在 `ready()` 里 listen，所以「连上」等价于「服务端已就绪」；反过来，应用正在退出时 listener 已关，CLI 会把「退出中」误判为「没在跑」而走拉起分支（§6）。这是已知取舍：退出与重开之间本来就不该有请求成功。

### 3.5 安全边界

前提：单用户 Mac，攻击者最多是「以同一或另一用户身份运行的本地进程」；root 与内核被攻陷不在防护范围（与 004 §6.1 同一模型）。

| # | 面 | 处理 |
| --- | --- | --- |
| 1 | 动作种类 | 只有 §1.2 那 9 条会联动的命令（`help` 不连应用）；动作种类＝URL 白名单（§2.2）。没有「执行命令」「打开任意文件」「读任意路径」「evaluate JS」任何一条通道 |
| 2 | 正文 | `json.new` 的正文只当文档内容写进新窗口；不进 shell、不当路径、不 `new Function`（与 003 §8.3 第 7 条同一条硬约束） |
| 3 | 对端身份 | 服务端在 `Accept` 之后、读第一个字节之前取 `getsockopt(fd, SOL_LOCAL, LOCAL_PEERCRED)`（`sys/un.h` 里 `SOL_LOCAL=0`、`LOCAL_PEERCRED=0x001`），反序列化成 `struct xucred` 比对 `cr_uid` 与 `os.Getuid()`；不一致直接关连接，不读内容、不记 payload。本机实验：`xucred` 长度 76 字节、`cr_version=0`、`cr_ngroups=16`、`cr_uid` 等于本进程 uid（§5.5）。同 uid 与不同 uid 两条连接的真机对比**需实测**（§8.3），单测只能注入 verifier |

| 5 | 请求大小与并发 | 行 ≤ 4096、正文 ≤ 64 MiB、并发 ≤ 8（槽位在读正文之前占用）；超限即断开，不做部分执行 |
| 6 | 参数不可信 | 服务端对每个字段重新校验（枚举、范围、UTF-8、`arg` 走 `parseAwakeArg`、`follow` 走 `processByPID`），不因为「是 CLI 发来的」就跳过（§8.1 的测试清单） |
| 7 | 提权 | 这条通道**永远不**能触发管理员授权：`--lid` 只在助手已安装且 `svcEnabled` 时走到 `enableLid`，而 `runURL` 已把 `a.lidURL` 置真，`enableLid` 的 `authorize` 是 `a.lidAuthorize && !a.lidURL`（`awake_app.go`，约 72 行）即为假；`lidController.enable` 在「需要安装且 `authorize` 为假」时直接 `fail("LidAuthNeeded")`，**不调 `Register()`**（`lid_controller.go`，约 314-318 行）。两行都是源码核对，**端到端「不弹授权框」需实测**（§8.3） |
| 8 | 代码签名（v1 不校验） | v1 **只校验 uid**，不校验对端签名。理由要写准：动作种类确实没多，但 CLI 多了 `--until`／`--follow`／`status` 三处 URL 表达不了的能力，所以**不能**说「能力已被 URL 封顶」。真正的理由是两条：① 同 uid 的进程本来就拥有这个用户的一切（能改配置文件、能发通知、能直接跑 `caffeinate`、能读同一个文件），CLI 通道不额外扩大它的能力；② 目录 0700 + socket 0600 已经只允许同 uid 连接，v1 的目标只是「挡住其他用户」。剩下一个具体风险是「同 uid 进程先占住 socket，冒充应用收走 CLI 发去的正文」——它收到的只是调用者自己本来就能读的东西，所以接受；要彻底堵住，照 `internal/lid/security_darwin.go` 的 `VerifyPeer` 加一个 requirement（`identifier "cubbix"`）即可，入口现成，列为后续加固 |
| 9 | 日志 | 只记「一次请求失败 + code」，不记正文、不记 `arg` 原文、不记对端信息（与 004 §6.2 第 10 条同一条纪律） |

### 3.6 合盖保持：CLI 不授权

先摆清三条既有事实（本轮核对）：

- `startAwake` 的最后一步是 `a.enableLid(s.End, a.lidAuthorize && !a.lidURL)`（`awake_app.go`，约 72 行）——**只有同时「允许授权」且「不是 URL/CLI 路径」时才可能弹授权**。
- `lidController.enable` 里 `needsInstall` 为真（`svcNotRegistered`／`svcBroken`／连接失败）时，`authorize` 为假直接 `fail("LidAuthNeeded")`；为真才 `Register()`（`lid_controller.go`，约 305-318 行）。
- 空截止由助手侧封顶：`effectiveDeadline` 取 `journal.Started + HardLimit`，`HardLimit` 是 12 小时（`internal/lid/engine.go`，约 97-103 行；`internal/lid/protocol.go`，约 20 行）。

| 情况 | 行为 |
| --- | --- |
| `--lid`，助手未安装／已停用（`a.lid.service.Status() != svcEnabled`） | 回 `LidAuthNeeded`，退出 4，**不弹授权**，也不启动安装脚本 |
| `--lid`，格子不支持（桌面 Mac／开发构建／助手二进制缺失／系统 < 13／包不在 `/Applications/Cubbix.app`） | 回 `LidUnsupported`／`LidDevBuild`（`lidReason()` 的键），退出 4 |

| 记忆驱动的合盖（没给 `--lid`／`--no-lid`，但 `awake_lid` 为真） | 与 ⌃⌥⌘K 一致：**不额外要求明确时长**，`cubbix awake on` 无参数也能带着记忆里的合盖开始；不限时的会话由助手的 12 小时硬上限兜住。这条与 URL **不同**（`cubbix://awake` 在记忆了合盖且没有 `minutes` 时返回 `LidAuthNeeded`，`palette.go` 约 809 行），本次不改 URL，CLI 按快捷键语义走，两边都用测试钉住 |
| 异步 | `a.lidAsync` 在可用的机器上恒为真（`lid_restore_darwin.go` 的 `prepareLid`，约 90 行），`enableLid` 在 goroutine 里跑。因此 `--lid` 的成功响应可能是 `lid.state = "enabling"`：`ok:true` 只表示**已被接受**。要确认到位，脚本应再查一次 `awake status`（`state.awake.lid.state == "on"`） |
| 通知 | `enableLid` 的异步回调会在稍后一次 `RunOnMain` 里发 004 §6.2 第 5 条那种通知（`lidURLFeedback`）或错误提示（`announceAwake`）。CLI 默认静音，而且**必须把静音带过这道异步边界**（§4.4 第 8 条），否则 `applyCLI` 返回时 `defer` 已经把 `a.quiet` 清掉，通知照样发出去。单测能钉住闭包的行为，真机上「`--lid` 成功后屏幕上真的什么都没弹」**需实测**（§8.3） |
| 安全提醒 | `notifyLid`（`lid_app.go`，约 189 行）里的 `LidRestoreFailed`／`LidBatteryLow`／`LidMaxDuration` 等属于安全提醒，**不受 `a.quiet` 影响**（与 002 §5.4 对电池提醒的规定一致） |

`applyCLI(req)` 在主线程上执行，语义是「把 CLI 的意图翻译成 `paletteURLRequest`，然后走 `runURL`」：

`message` 的来源必须固定，免得又一套文案：`awake`／`awake.toggle` 用 `awakeFeedbackMessage(locale, state.Session).Text`（失败时用 `a.text(locale, code)`）、`awake off` 用 `ToastAwakeOff`、`json new`／`palette`／`settings` 留空串。

`code` 的来源也只有一个：新增 `func cliErrorKey(err error) string`（放 `cli_server.go`），先把 `ProcessEnded` 原样返回，其余交给 `paletteErrorKey`（`palette.go`，约 357 行）。原因：`paletteErrorKey` 会把认不出的错误（含 `ProcessEnded`）收成 `AwakeStartError`，而 `--follow` 的「进程已结束」必须让脚本分得出来（§3.3）；`paletteErrorKey` 本身不改，免得顺带改了命令面板的文案。

可用条件在 `applyCLI` 入口统一判断，与 `handleURL` 的那一行同口径：`awake*` 要求 `config.AwakeEnabled`、`json.new` 要求 `config.JSONEnabled`，否则直接回 `disabled`，不互相糊到错误键里。**`disabled` 只能由这里产生**：`startAwake` 内部还有一句 `"keep awake disabled"`（`awake_app.go`，约 45 行），它是给旧调用者的内部字符串，CLI 路径上不会被触发；万一出现，按 `AwakeStartError` 收，不外泄成协议码。

`status` 的取数来源：`a.awake.snapshot()`、`a.lid.snapshot()`、`a.lidCapable()`、`a.lid.Available()`、`a.config`、`len(a.jsonDocuments)`、`runningVersion()`。全部是只读，不触发 `Inspect()`／`pmset` 之类的探测——`status` 必须是「不产生副作用」的，一次脚本轮询不能在日志或系统调用里留下痕迹。

### 4.3 上主线程与静音

- `Accept` 循环与服务端读写都在 goroutine 里；**所有**触碰应用状态的动作都经 `a.urlDispatch`（`main.go` 里指向 `mygo.RunOnMain` 的 seam，测试里替换成直接执行）。
- `mygo.RunOnMain` 会**等**函数返回（`mygo@v0.6.2/loop.go`，约 86 行），因此 socket 的 goroutine 能自然拿到结果；`loop.drain` 在原生模态面板里也会被继续处理（同文件注释：运行自己循环的函数会把排在后面的也跑掉），所以文件选择器开着时请求仍会被执行，只是要排队。
- 事件循环已经关掉时 `RunOnMain` **静默丢弃**函数（`onMain` 里 `loop.post` 返回 false 就 `return`）。所以服务端必须自己留痕，不能假设「调用过就等于执行过」；这条是「应用正在退出」时能给 CLI 明确答案的唯一办法（§6）。同一段闭包也是静音标志唯一合法的置位点（下面第 1 条）。

**静音的作用域**（评审必须改第 1 条）——两条硬约束：

1. **只在主线程上置位与复位**。`a.quiet` 被 `announce`（主线程）读，如果在 socket 的 goroutine 里写它，既是数据竞争，也会把一个恰好同时发生的快捷键动作一起静音。所以置位放进 `urlDispatch` 的闭包，与 `ran` 同一层：

```go
var out cliResult
ran := false
a.urlDispatch(func() {
    ran = true
    a.quiet = !req.Notify          // 主线程，与下面的 defer 同一个栈
    defer func() { a.quiet = false }()
    out = a.applyCLI(req)
})
if !ran {
    out = cliResult{Code: "quitting"}
}
```

2. **静音要活到异步回调**。`a.quiet` 为真时，`announce`（`feedback.go`，约 332 行）与 `lidURLFeedback`（`lid_app.go`，约 217 行）开头直接 `return`。但**合盖是异步的**：`enableLid`（`lid_app.go`，约 56 行）在 `lidAsync` 为真时把 `completeLid` 与那两个通知放进 goroutine 后的 `RunOnMain` 里执行，那时 `applyCLI` 早已返回、`defer` 已经复位。所以 `enableLid` 必须像既有的 `fromURL := a.lidURL` 一样，在**调用时**把 `a.quiet` 也捕获下来，回调里用捕获值判断：

```go
fromURL, quiet := a.lidURL, a.quiet
go func() {
    err := a.lid.enable(end, min, authorize)
    mygo.RunOnMain(func() {
        a.lidBusy = false
        if a.quitting { return }
        a.completeLid(err)
        if fromURL && !quiet {          // CLI 默认走到这里就跳过
            if err == nil { a.lidURLFeedback() } else { a.announceAwake(err) }
        }
    })
}()
```

用捕获值而不是在回调里重读 `a.quiet`，就不依赖「回调时那个请求是否还在飞」这种时序假设；同步分支（`!a.lidAsync`）直接用当前的 `a.quiet` 即可。这两段代码的**真机时序需实测**（§8.3）：单测只能证明闭包里不再发通知，证明不了真机上的 RunOnMain 排期。

## 5. 二进制与安装

### 5.1 构建与签名

`scripts/build-cli.sh`（照 `build-helper.sh` 写，区别只有两处：产物名与 identifier）：

```sh
# 形状示意，不是最终脚本
export CGO_ENABLED=0 GOTOOLCHAIN=go1.27.1
for arch in arm64 amd64; do
  target="resources/darwin-$arch/bin"
  mkdir -p "$target"
  GOOS=darwin GOARCH="$arch" go build -trimpath -o "$target/cubbix" ./cmd/cubbix
  # Go embeds an a.out ad-hoc identifier; MyGo preserves an existing identifier.
  /usr/bin/codesign --force --sign - --identifier cubbix "$target/cubbix"
done
```

要点：

- **必须固定 identifier**。Go 链接器给裸 Mach-O 的默认 identifier 是 `a.out`（本机实验：`codesign -dv` 输出 `Identifier=a.out`）。MyGo 的 `nestedCodesignArgs`（`mygo@v0.6.2/cmd/mygo/resources.go`，约 793 行）在生产签名时不传 `--identifier`，只加 `--options runtime --timestamp --preserve-metadata=entitlements`；`cubbix-helper` 的做法是先在自己那份构建产物上固定 identifier（`build-helper.sh` 的注释：Go embeds an a.out ad-hoc identifier; MyGo preserves an existing identifier）。**证据边界要说清**：本轮只在 ad-hoc QA 包里核对过 `Contents/Resources/bin/cubbix-helper` 的 `Identifier=cubbix-helper`；但 ad-hoc 签名时 `signNestedCode` 会跳过**已有有效签名**的嵌套 Mach-O（`case !n.bundle && n.signed: continue`），所以这一次观察**不能**证明「用真实 Developer ID 重签时 identifier 被保留」——那一半只有 004 的实测记录。因此 `scripts/check-cli.sh` 必须在真实签名的发布包上跑（§4.4 第 14、15 项），这是本规格唯一依赖「别人的实测结论」的地方，也是**需实测**的一项（§8.3）。
- **产物落在 `resources/darwin-<arch>/bin/`**。`mygo build` 会把 `resources/` 与平台目录的内容合并进 `Contents/Resources`（`mygo@v0.6.2/cmd/mygo/build.go` 的说明，约 30 行）；QA 包里 `Contents/Resources/bin/cubbix-helper` 的存在就是证据。所以 CLI 的最终位置是 `Contents/Resources/bin/cubbix`，助手在同一个目录里，二者不冲突。
- **`.gitignore` 不用改**：`/resources/darwin-*/bin/` 已经覆盖产物。
- **体积**：一个只 import 标准库的 CLI（`net`、手写参数解析、`encoding/json`）在本机编出来约 3.5 MB（实验程序 3.5 MB，它比真 CLI 多一个 `os/exec`，少几个解析函数，量级一致）。两个 arch 目录各一份，`darwin/universal` 打包前再 lipo；对安装包体积的影响在 4 MB 量级。
- **不需要 entitlement**：QA 包里应用没有 App Sandbox（`codesign -d --entitlements` 输出为空），所以设置页往 `~/.local/bin` 写链接不会被沙箱拦。
- **`mygo dev`**：`PathResources` 在开发运行下是仓库里的 `resources/`（`mygo@v0.6.2/paths.go` 的 `resourcesDir` 注释），所以开发时 `bin/cubbix` 只在跑过 `build-cli.sh` 之后才存在。设置页那一行用「二进制存在与否」决定显不显示，与 004 的 `lidCapable()` 同一手法。

### 5.2 装到 PATH

| 方案 | 权限 | 是否在 PATH | 更新后 | 结论 |
| --- | --- | --- | --- | --- |
| `~/.local/bin/cubbix` 符号链接 | 普通用户，**零授权** | 取决于 shell 配置（zsh 默认没有这个目录在 PATH 里） | 链接指向包内路径，更新原地换包，链接仍有效（§5.4） | **默认** |
| `/usr/local/bin/cubbix` 符号链接 | 该目录通常是 root 拥有，写入需要管理员授权 | 默认在 PATH（`/etc/paths`） | 同上 | **不做默认**；文档给出手动命令，谁需要谁自己 `sudo ln -s` |
| 把二进制复制进 PATH 目录 | 复制后签名仍有效（签名在文件里） | 是 | **失效源**：更新后路径里是旧版本，`version` 与真实应用不一致 | 不采用 |
| 装一个 `#!/bin/sh` 包装脚本 | 无签名 | 是 | 指向包内二进制，跟着更新 | 不采用：多一层无签名代码，还要处理退出码透传 |

设置页按钮的动作（**不需要管理员授权**）：

1. `os.MkdirAll("~/.local/bin", 0755)`。
2. `target` ＝ `filepath.Join(resourcesDir, "bin", "cubbix")`，`resourcesDir` 取 **`mygo.App.Path(mygo.PathResources)`**（与 `lidPackagedHelper` 同一个取法，`lid_service_darwin.go`，约 118-125 行）。**不要拼死 `/Applications/Cubbix.app`**：包可能装在别处（用户自选目录、`~/Applications`、开发运行的仓库目录），拼死会建出一个指向空路径的链接。先确认 target 是可执行的普通文件，否则不显示这一行。
3. 链接路径 `~/.local/bin/cubbix`：
   - 不存在 → `os.Symlink(target, link)`。
   - 已是符号链接且指向本包的 CLI → 视为已安装（可顺手「修复」已经失效的目标）。
   - 是符号链接但指向别处，或普通文件 → **不覆盖**，显示 alert + `CLILinkConflict`（tooltip 里带路径）。覆盖别人的文件比「装不上」危险得多。
4. 失败 → alert + `CLIInstallFailed`。

手动等价命令（同时写进 README 与 tooltip）。路径要写**用户自己的包路径**，默认才是 `/Applications`：

```sh
mkdir -p ~/.local/bin
ln -sf "<Cubbix.app 所在目录>/Cubbix.app/Contents/Resources/bin/cubbix" ~/.local/bin/cubbix
# 默认安装位置就是 /Applications，所以多数人写：
#   ln -sf "/Applications/Cubbix.app/Contents/Resources/bin/cubbix" ~/.local/bin/cubbix
# 若 ~/.local/bin 不在 PATH 里，在 shell 配置中加入：
#   export PATH="$HOME/.local/bin:$PATH"
exec zsh        # 或开新终端
which cubbix
```

不带 `-f` 的手动写法更安全（与设置页一致）：先看 `ls -l ~/.local/bin/cubbix` 是否已存在。`-f` 会覆盖同名文件，那是用户手动执行时的知情选择，设置页里的按钮**不**这么做。

卸载：设置页那一行的移除按钮（只在链接指向本包时可用），或手写

```sh
rm -f ~/.local/bin/cubbix
```

没有任何其他落盘：socket 在应用退出时删掉，残留文件由下次启动重绑或清理（§3.2）。配置目录里不记「CLI 是否安装过」——真相只有文件系统那一个符号链接，避免出现「配置说装了、其实被删了」的第二份事实。

**包不在 `/Applications` 会怎样**：CLI 链接照常可用（链接目标取自 `PathResources`），但合盖保持本来就不可用——`prepareLid` 要求 `lidBundlePath()` 恰好等于 `/Applications/Cubbix.app`（`lid_restore_darwin.go`，约 27、31 行），否则 `supported=false`、`unavailable="LidUnsupported"`。这是 004 的既有规则，与 CLI 无关；文档要写明「`--lid` 需要应用装在 `/Applications`」，免得用户以为装了 CLI 就能合盖。

### 5.4 更新、失效与卸载

| 场景 | 结果 |
| --- | --- |
| 应用自动更新 | MyGo 的 `swapBundle`（`mygo@v0.6.2/updater.go`，约 277 行）把旧包 `Rename` 走、新包 `Rename` 到**同一路径**，所以既有的符号链接仍指向同一路径、指向新包。CLI 二进制随包一起被替换成新版 |
| 用户把 `Cubbix.app` 改名或搬家 | 链接失效 → 设置页显示 `CLILinkBroken`，点一下重建；命令行层面是 `exec: no such file`（shell 报错），不会有更糟的后果 |
| 用户删掉应用 | 链接变成死链，`which cubbix` 仍能找到。文档写明「卸载应用后执行 `rm -f ~/.local/bin/cubbix`」；应用已不存在，不可能替用户清理 |
| 同一台机器装两份 Cubbix（例如旧版还在 `~/Applications` 且已被 LaunchServices 登记） | 链接只有一个，指向最后点击安装的那份；两份**共用同一个 `cli.sock` 路径**，所以「哪一份在跑」决定 CLI 连到谁。`cubbix version` 打印自己所属的包路径，能看出 PATH 里那个是哪一份；拉起时优先用自己所属的 `.app` 路径（§3.4），避免把另一份叫起来 |

### 5.5 纯 Go、不依赖 MyGo：可行性证据

结论：**可行**，并且已经在仓库外的临时目录验证过。

| 检查 | 做法 | 结果 |
| --- | --- | --- |
| 编译 | 临时目录里一个只 import 标准库（`net`、`os`、`syscall`、`unsafe`…）的 `main` 包，`CGO_ENABLED=0 GOTOOLCHAIN=go1.27.1 GOOS=darwin GOARCH=arm64 go build -trimpath` | 通过，产物 3,536,722 字节，`codesign -dv` 显示 `flags=0x20002(adhoc,linker-signed)`、`Identifier=a.out` |
| 静态检查 | 同一个包 `go vet ./...` | 通过 |
| `os.Executable` 与符号链接 | 用 `ln -s` 指向真实二进制后经链接运行 | 返回**链接路径**（未解析）；`filepath.EvalSymlinks` 才得到真实路径 |
| `LOCAL_PEERCRED` | 自建 `net.ListenUnix` 服务端 + 自身连接，`syscall.Syscall6(SYS_GETSOCKOPT, fd, 0, 0x001, …)` 填 76 字节的 `xucred` | 成功：`size=76`、`version=0`、`ngroups=16`、`uid` 等于本进程 uid |
| MyGo 依赖 | `cmd/cubbix` 的 import 列表只有标准库与 `internal/cli`／`internal/awake` | 不需要 MyGo、不需要 purego、不需要 cgo |

为什么不做成「`cubbix` 就是应用二进制加一个子命令」：`Cubbix.app/Contents/MacOS/Cubbix` 启动就要连窗口服务器、设置激活策略，从终端跑它只会变成「又开一个 Cubbix」；而且用户会以为 PATH 里那个东西是应用本体。独立小二进制还能让 `help`／`version` 在没有应用时也毫秒级返回。

`version` 的取法（不连应用）：解析 `os.Executable` → `EvalSymlinks` → 若是 `…/Cubbix.app/Contents/Resources/bin/cubbix`，读上三级目录的 `Contents/Info.plist`，取 `CFBundleShortVersionString`。读 plist 用标准库 `encoding/xml`（plist 的 XML 形态）或退化成一次正则匹配；读不到就打印 `unknown`，不因此失败。这样「PATH 里的 cubbix 的版本」永远等于它所属包的真实版本，不会出现两处版本号各自漂移。

| 情况 | 行为 |
| --- | --- |
| 多个 CLI 同时请求 | 每连接一个 goroutine；**槽位在 `Accept` 之后、读请求行与正文之前占用**（第 9 条连接立即拿 `busy` 并被关闭，不读它的字节），上限 8；`applyCLI` 全部经 `RunOnMain` 串行到主线程，`paletteState`／`jsonDocuments`／`lidController` 仍然只有主线程碰，不需要新锁 |
| 响应顺序 | 不保证与请求顺序一致；每个响应带自己的 `id`。CLI 一次调用只发一个请求，所以对脚本没有影响 |
| 应用正在退出 | `beforeQuit` 关 listener；在飞请求的 `RunOnMain` 被丢弃（§4.3），回 `quitting`；CLI 退出 3。已经发出的 `stopAwake` 不会被回滚 |
| 命令面板正开着 | CLI 不动面板状态（不 `hidePalette`、不改 `p.errorKey`）。`json.new`／`settings` 会激活应用，面板按既有 `OnBlur` 收起；`palette` 与 ⌥. 同义（会拿键盘）；`awake on` 面板保持原样，用户看到的结果是猫标与卡片状态随之变化 |
| 设置页有未保存的录制 | 无关：CLI 不碰 `shortcutRecording`、不注册／注销快捷键 |
| 助手正忙（`a.lidBusy`） | `startAwake` 返回 `LidEnableFailed` → 退出 4；不会排队 |
| 已有会话再开一次 | 幂等：与 URL 相同，等于重置时长／截止。不报错、不加队列 |
| `json new` 的正文 | 上限 `jsonFileLimit`（64 MiB）。CLI 侧先卡一遍（超限退出 2，**不发请求**）；服务端再按 `bytes` 卡一遍（超限 `bad-request` 并断开），两遍都不看正文内容 |
| stdin | 只在 `json new` 且没有 `--text`／`--file` 时读：`os.Stdin.Stat()` 的 `ModeCharDevice` 为 0（管道或重定向）才读，读到 EOF 为止；是终端则不读（避免命令挂在那里等人打字）。`--file -` 等价于「读 stdin」，即使它是终端 |
| `--file PATH` | CLI 侧读：必须是普通文件（`readJSONFile` 的同一口径），`size ≤ jsonFileLimit`。CLI 侧读不到、不是普通文件、超限 → 退出 2（`code:"usage"`），不发请求；应用侧根本不读文件（CLI 只交文本），所以 `JSONReadError`／`JSONFileLimit` **不会**出现在协议里。正文原样发送，**不校验 JSON 合法性**——编辑器允许编辑非法 JSON（与 URL 的 `text` 一致） |
| 空输入 | `json new` 无参数、无管道 → 空白文档（等价于 URL 的 `cubbix://json/new`）。要强制空白加 `--blank` |
| 应用没装（socket 不存在、`-a` 与 `-b` 都失败） | 退出 3，提示「Cubbix is not running」；不猜路径 |
| 两个实例同时连 8 条以上 | 第 9 条起 `busy`；CLI 不重试（脚本自己决定）。理由：重试会把「应用卡住」变成「脚本看起来卡住」 |
| 文本里有 `\n` | 无关：正文走定长帧，不做行分隔，`{"a":1}\n{"b":2}` 原样进去 |

## 7. 快捷键反馈与提示

| 项 | 结论 |
| --- | --- |
| 默认 | **不弹** 002 的屏幕提示，也不发系统通知。CLI 自己的 stdout／退出码就是反馈，与 002 §1.1「只在操作本身没有其他可见结果时提示」同一条推理：脚本运行时屏幕上多一个 1.5 秒浮层是噪音 |
| 静音的开关 | `a.quiet`，由 `handleCLI` 在**主线程的 `urlDispatch` 闭包内**按 `req.Notify` 置位、同一闭包的 `defer` 复位（在 goroutine 里写它是数据竞争，§4.3）；`announce` 与 `lidURLFeedback` 开头各一道闸；**异步合盖回调靠 `enableLid` 调用时捕获的 quiet**（§4.3） |
| `--notify` | 只有它让 `a.quiet` 保持为假，于是 `announceAwake` 照原样走 `a.announce` → 受 `FeedbackMode` 约束（`off` 时仍然什么都不显示，这不是错误）。文案与快捷键路径完全一致（`awakeFeedbackMessage` 读**本次会话**） |
| 合盖的强制通知 | URL 路径的 `lidURLFeedback`（`lid_app.go`，约 217 行）在 004 §6.2 第 5 条里是「例外清单第二条」。CLI 默认**不**触发它（`a.quiet` 拦住，包括异步那次）；`--notify` 时恢复 |
| 安全提醒 | `notifyLid`（合盖恢复失败、电量过低、12 小时上限等）不受 `a.quiet` 影响，与 002 §5.4 对电池提醒的规定一致 |
| 不提示的动作 | `palette`（面板自己就是反馈，与 003 §9 一致）、`settings`（窗口出现）、`json new`（窗口出现，与 002 对 ⌃⌥⌘J 的规定一致：新窗口本身就是反馈）。`--notify` 在这三条命令上被接受但**没有可见效果**（不报错）：它们本来就不是「没有其他可见结果」的操作 |
| 与 002 的边界 | 002 的「触发范围」表新增一行：CLI 默认不提示，`--notify` 例外。其余不动 |

### 9.1 README 草稿（接在「命令面板与 URL scheme」之后）

> ## 命令行
>
> 应用包里带一个 `cubbix` 命令行工具，供脚本、Agent 与启动器联动。「设置 → 通用 → 命令行工具」点一次会在 `~/.local/bin/cubbix` 建一个符号链接，不需要管理员授权；`~/.local/bin` 需要在你 shell 的 `PATH` 里（zsh 默认不含，配置里加一行 `export PATH="$HOME/.local/bin:$PATH"`）。不想用按钮就手动（把路径换成你自己那份 `Cubbix.app`；默认装在 `/Applications`）：
>
> ```sh
> mkdir -p ~/.local/bin
> ln -sf "/Applications/Cubbix.app/Contents/Resources/bin/cubbix" ~/.local/bin/cubbix
> ```
>
> ```sh
> cubbix awake on --minutes 60          # 一小时常亮
> cubbix awake on --until 18:30         # 到 18:30
> cubbix awake on --follow 1234         # 跟随进程
> cubbix awake on --minutes 120 --lid   # 合盖也保持（助手已授权时）
> cubbix awake status --json | jq .state.awake.active
> cubbix awake off
> echo '{"a":1}' | cubbix json new      # 新建 JSON 窗口并写入正文
> cubbix palette                         # 打开命令面板
> ```
>
> 参数语法与命令面板完全一致（`45m`、`1h30m`、`until 18:30`、`∞`），CLI 只是把同一句话交给同一个解析器。动作范围与 `cubbix://` 相同：开／关／切换常亮、新建 JSON 窗口、开面板、开设置，外加只读的 `status`。CLI **不改**记忆的时长、截止与模式，也和 URL 一样绝不读剪贴板——`json new` 的内容只来自参数、文件或标准输入。
>
> 需要改状态的命令在应用没运行时后台拉起（用你这个 `cubbix` 所属的那份 `Cubbix.app`），最多等 5 秒；`status` 与 `version` 不会拉起应用。默认不弹提示（输出即反馈），`--notify` 才走与快捷键相同的提示。人读输出是应用当前界面语言的一句话；`--json` 是给脚本的稳定接口，字段只增不改，退出码 `0` 成功、`1` 内部错误、`2` 用法错误、`3` 应用不可用、`4` 被拒绝、`5` 超时。
>
> `--lid` **不会**弹授权：助手没装或没授权时直接返回错误，脚本自己决定要不要提示用户去卡片面板点一下。合盖会话仍受 004 的 12 小时上限与低电量下限保护，且应用必须装在 `/Applications/Cubbix.app` 才支持合盖（004 的既有规则）。
>
> 通信走 `~/Library/Application Support/cubbix/cli.sock`（目录 0700、socket 0600、对端校验 uid），协议与边界见 [006 规格](docs/specs/006-命令行.md)。卸载应用后记得 `rm -f ~/.local/bin/cubbix`。

第 1 版的 17 项待决定，按评审意见全部定稿；**仍需维护者拍板的：无**。表里保留一句「为什么」，方便以后翻案时知道当时的理由。

| # | 问题 | 定稿 | 理由 |
| --- | --- | --- | --- |
| 1 | CLI 自有文案是否中英双语 | **只英文** | 应用给的 `message` 已是界面语言；`--json` + 退出码才是稳定接口（§9.3） |
| 2 | 链接位置 | **固定 `~/.local/bin`**，不做「选择目录」 | `/usr/local/bin` 要管理员授权；`~/.local/bin` 零授权，路径写进 README |
| 3 | `~/.local/bin` 不在 PATH 时是否在设置页提示 | **不提示** | 低信息密度；命令写在 README 与 tooltip |
| 4 | `status` 是否自动拉起应用 | **不拉起** | 只读命令拉起应用是意外副作用；要拉起就让脚本先跑一条动作 |
| 5 | `json new` 在 stdin 是管道时自动读 | **读**；`--blank` 强制空白，`--text` 优先 | 管道是 Agent 的主要用法（§1.1 场景 3） |
| 6 | `--lid` 的时长限制 | **显式 `--lid`：`--minutes` 1–480、`--until` ≤ 480 分钟、`--follow` 不限、不限时拒绝（`LidNeedsMinutes`）；记忆驱动的合盖不额外限制** | 显式请求要能当场判断「这个组合行不行」；记忆驱动的那条要与 ⌃⌥⌘K 一致。`--follow` 与不限时的会话长度分别由目标进程与助手的 12 小时硬上限兜住（`internal/lid/engine.go` 的 `effectiveDeadline`，约 97-103 行；`HardLimit` 在 `internal/lid/protocol.go` 约 20 行） |
| 7 | `awake on` 是否写记忆 | **不写时长／截止／模式**；合盖成功后 `AwakeLid` 会被既有 `completeLid` 置真（URL 同样） | 与 URL 同一条纪律（§2.3）；`AwakeLid` 是 `enableLid` 的既有副作用，改它会动 004 的语义，不在本次范围 |
| 8 | `--follow` 是否支持无 TTY 的进程（daemon） | **支持** | 新增窄接口 `processByPID`（单次 `ps`，参数数组），不复用只列 GUI／TTY 的 `listProcesses`；`Identity` 必须与 `processIdentity` 一致（§4.4 第 6 条） |
| 9 | `json new` 是否要 `--background`（不激活应用） | **v1 不加** | 与 URL 行为一致，需要时再加 |
| 10 | CLI 是否记入「最近使用」 | **不记** | 面板的记录只反映人在面板里的选择 |
| 11 | socket 路径超过 104 字节时 | **兜底到字面 `/tmp/cubbix-cli-<uid>.sock`** | 只依赖 uid，两端一致；用 `os.TempDir()` 会因为 `TMPDIR` 不同而算出两个路径（§3.2） |
| 12 | 并发上限 | **8 条连接**，槽位在 `Accept` 之后、读正文之前占用，超出回 `busy` | 8 个 64 MiB 正文是内存上限的合理值；先占位才挡得住「慢慢发一行、再挂住」的连接（§3.3、§6） |
| 13 | `--socket` 是否出现在 `help` | **出现**，放在「调试」小段 | 集成测试靠它 |
| 14 | 是否校验对端代码签名 | **v1 只校验 uid**，不校验签名 | 同 uid 进程本来就拥有这个用户的一切，CLI 不额外扩大其能力；0700/0600 已挡住其他用户；「先占住 socket 收走正文」的风险接受。后续加固用 `internal/lid/security_darwin.go` 的 `VerifyPeer` 加 `identifier "cubbix"`。**不能**把理由写成「能力已被 URL 封顶」（§3.5 第 8 条） |
| 15 | 是否加 `awake toggle` | **加**，走 `toggleAwakeResult`（不是 `runURL` 的递归） | 与 ⌃⌥⌘K 真正一致，含记忆里的合盖；URL 那条分支的差异保持现状并加测试钉住（§1.2、§4.2） |
| 16 | `settings --page` 非法值 | **CLI 报错退出 2** | 脚本要好查错；URL 保持「落通用页」不变 |
| 17 | 是否要 R10 画板 | **不单独出** | 只多一行、用既有行样式与既有图标；行数变化按 002／004 的先例处理 |
