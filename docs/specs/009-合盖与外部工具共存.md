# 详细设计 009：合盖保持与外部电源工具共存

- 状态：设计稿，待评审。本文档只描述设计与证据，不包含实现。
- 关联：[004 合盖保持](004-合盖保持.md)（状态机、journal、助手修订号、恢复责任全部沿用）、[006 命令行](006-命令行.md)（`status`／`awake` 输出）。
- 引用仓库代码写 `文件` 的 `函数名/类型名`（行号只作辅助）；引用 Apple 接口写框架与头文件/文档名，不给本机路径。
- 本轮只读：未运行 Cubbix，未执行 `pmset` 写入、`launchctl`、管理员授权、`pmset -g log`。执行过的读取只有 `pmset -g batt`、`pmset -g adapter`、`ioreg`（含 `AppleSmartBattery`）、`system_profiler SPPowerDataType`、只读 IOKit 调用（`IOPSCopyExternalPowerAdapterDetails`、`IOPSGetProvidingPowerSourceType`）与只读 SMC 键读取，以及读 SDK 头文件与公开资料。
- 维护者现场在 2026-11-09 由 AlDente Pro 校准期间产生。本文档中凡是本轮无法只读确认的取值，一律标「未证实」并给出实测方法（§4.5、§7.3），不写推测当结论。

## 结论摘要

| 项 | 结论 |
| --- | --- |
| A 的核心 | 把「值是不是 1」改成「值是谁写的」。新增**观察（watching）**态：外部持有 1 时 Cubbix 不写值、只登记「想要合盖」，并在外部释放（0）时由**助手**写回 1 转为 `on-ours`；反向（我方 `on-ours` 被外部改回 0）同样由助手重写，带次数上限（§3.4） |
| 责任边界 | 谁写的 1，谁负责恢复。Cubbix **从不**为自己没写过的 1 写 0；`watching` 释放在助手退出/崩溃/重启时只丢登记，绝不写系统设置（§2.4） |
| 不弹授权 | 接手、重写全部发生在助手内部与已授权连接上；URL／CLI／轮询路径仍永不调用 `Register()`（沿 004 §6.2 第 6 条） |
| B 的核心 | 低电量保护只在**确认没接适配器**时触发；接适配器（`Power Source State = AC` 或 `IOPSCopyExternalPowerAdapterDetails` 非空）不触发；读不到、信号矛盾一律按未插电（保守） |
| B 的关键难点 | 外部工具强制放电时，powerd／IOPS 很可能报「没有适配器」，与真的拔电不可区分。本轮已取得只读读数（§4.2），但**无法确认**当时适配器是否物理连接，标「未证实」，由维护者按 §4.5 采集一次定论 |
| 执行位置 | 电量保护与外部写入都在**助手**侧（合盖后应用看不到界面、也不保证在跑）；应用只做开启前预检与展示。助手修订号 `4`→`5`，升级后用户下一次主动点合盖开关时再授权一次（§6） |
| 新增状态码 | 助手 `state=watching`；`code` 新增 `contested`、`external-release-failed`；瞬态事件放 `detail`（`adopted`、`external-release`、`rewrite-failed`）。协议常量 `Protocol=1` 不变 |
| 防抢数值 | 观察间隔 5s；重写最小间隔 10s；10 分钟内最多 3 次；单个租约最多 12 次。超限降级为 `contested` 并提示，需用户重开一次（§3.4 给理由） |
| 升级 | 旧 journal 无 `writer` 字段一律视为我方所有（向后兼容）；助手修订号不匹配的既有闸门（`lidController.connect`）已能挡住新旧组合，不新增兼容分支 |

## 0. 现场与只读读数

现场时间线（维护者提供，助手修订 4，Cubbix 0.6.1）：

```
01:15 request op=disable → state=off value=0          （维护者关闭合盖）
09:50 ping → foreign-setting state=on-foreign value=1  （校准开始，外部写 1）
11:53 ping → ok state=off value=0                      （阶段切换，外部写 0）
13:50 ping → foreign-setting state=on-foreign value=1  （充电保持阶段）
16:47 / 21:13 request op=enable ok=false code=foreign-setting
```

`on-foreign` 由 `internal/lid/engine.go` 的 `refresh` 产生：读到 1 且没有 journal 就是「别人的 1」；`enable` 在 `Handle` 里对 `value != 0` 直接回 `foreign-setting`。应用侧 `lid_controller.go` 的 `apply` 把它映射成 `LidBlocked` + `LidForeign`，`lid_view.go` 的 `panelLid` 又把 `LidForeign` 写进 `Disabled(...)`——这就是「开关变灰」的完整链路。

本轮只读读数（同一台维护者机器，2026-11-09 22:30 前后；与上面的现场是同一台机器，但不是校准时刻）：

| 信号 | 读取方式 | 读数 |
| --- | --- | --- |
| 供电来源 | `pmset -g batt` | `Now drawing from 'Battery Power'`；`95%; discharging; 9:11 remaining` |
| 适配器 | `pmset -g adapter` | `No adapter attached.` |
| IOPS 供电状态 | `IOPSGetProvidingPowerSourceType` | `Battery Power` |
| IOPS 电池描述 | `IOPSCopyPowerSourcesInfo` → 内置电池 | `Power Source State = Battery Power`、`Is Charging = 0`、`Current Capacity = 95`、`Max Capacity = 100` |
| **适配器详情** | `IOPSCopyExternalPowerAdapterDetails` | **NULL** |
| 电池注册表 | `ioreg -rn AppleSmartBattery` | `ExternalConnected = No`、`AppleRawExternalConnected = No`、`IsCharging = No`、`NotChargingReason = 4096` |
| 同一条注册表里的适配器缓存 | 同上 | `AdapterDetails`（`Watts = 65`）与 `AppleRawAdapterDetails` **仍然存在** |
| USB-C 侧 | `ioreg` 的端口子树 | 某端口 `CC` 传输 `Active = Yes`，带 SOP 伙伴（Vendor ID `11641`／Product ID `8195`）；同端口 `Power In` 为 `Active = No`；`USB-PD` 节点缓存了 65 W 的 `WinningPowerSourceOption` |
| SMC（只读、非 root） | 只读 `AppleSMC` 键 | 本机型存在 `B0AC`（si16）、`CHIE`、`CHSC`、`AC-N`；`CH0B`、`CH0C`、`CH0I`、`CHTE`、`CHWA`、`ACEN`、`B0St`、`D0IR` **不存在** |
| 系统报告 | `system_profiler SPPowerDataType` | `AC Charger Information: Connected: No` |

三条必须记住的结论：

1. **`AdapterDetails` 不能当作「适配器接着」的证据。**上面这一组读数里 powerd 一侧都说「没有适配器」，而电池注册表里的适配器缓存依旧在。任何用「缓存字段存在」判断插电的实现都会被它骗。
2. **同一时刻的读数彼此矛盾**：powerd／IOPS 说没有适配器，USB-C 侧却还有活跃的 CC 会话与缓存的 65 W 合约。两种解释都成立——(a) 真的没插电，端口数据是残留；(b) 插着但输入被禁用（外部工具强制放电）。本轮**未证实**是哪种，所以本文档既不用「缓存存在」也不把「适配器详情为 NULL」当成绝对结论。
3. `pmset -g adapter`、`system_profiler` 的 `Connected` 与 IOPS 的供电状态来自同一套 powerd 结论，互相印证但不构成独立证据。

## 1. 场景与时间线

### 1.1 两种意图

外部工具持有 1 时，Cubbix 只有两种姿态，由用户点不点合盖开关决定：

| 用户动作 | Cubbix 的行为 | 系统设置 | 责任 |
| --- | --- | --- | --- |
| 不点开关 | 只报告「已有别的工具关闭了合盖睡眠」，不写、不抢 | 别人的 1 原样 | 别人的 |
| 点开关 | 进入 `watching`：登记「想要合盖保持」，**不写值**，监听到 0 就接手 | 别人的 1 原样，直到它自己变 0 | 别人的 1 由别人恢复；接手后的 1 由 Cubbix 恢复 |

### 1.2 按 AlDente 校准过程逐段（A 行为）

设维护者在 09:50 之后点了合盖开关，会话是「仅保持任务 · 2 小时」。

| 阶段 | 外部动作 | 助手侧 | 应用侧 | 合着盖 | 开着盖 |
| --- | --- | --- | --- | --- | --- |
| 01:15 | 用户关掉合盖 | `off` | 开关关 | 会睡 | 开关关 |
| 09:50 | AlDente 写 1 | 观察到 1 且无 journal → `on-foreign`（不写） | `lidBlocked` + `LidForeign`；**开关可点** | 略（此刻还没人登记意图） | 状态行提示「其他工具已关闭合盖睡眠」 |
| 09:55 | 用户点开关 | `enable{adoptForeign:true}` → 写 journal（`writer=foreign`）→ `watching`，**零次 `pmset` 写入** | `lidOn` + `watching`；开关打开；第二行「暂由其他工具维持，它释放后 Cubbix 接手」 | 机器不睡，因为 AlDente 的 1 生效；Cubbix 不上报「合盖也保持已中断」 | 会话继续计时 |
| 11:53 | AlDente 写 0（阶段切换） | 观察（≤5s）→ 写 journal（`writer=ours`）→ `Set(1)` → 读回 1 → `on-ours`，`detail=adopted` | 开关仍打开，第二行消失 | **不睡**（关键改进：以前这里会当成合盖结束） | 状态行不变 |
| 13:50 | AlDente 写 1（保持阶段） | 值本来就是 1 → **不写**，`on-ours` 不变，责任仍在我方 | 无变化 | 不睡 | 无变化 |
| 16:47 | CLI/URL `cubbix awake on --minutes N --lid` | 已 `on-ours` → 走续期（更新 `deadline`，不写值） | `ok:true`，`lid.state=on` | 不睡 | 无变化 |
| 21:13 | AlDente 写 0（校准结束） | 观察 → 重写 1（预算消耗 1/3）→ `on-ours`，`detail=external-release` | 开关仍打开，无提示 | **不睡**（以前会睡） | 状态行不变 |
| 用户停止 | — | `disable` → 写 0 → 读回 0 → 删 journal | 开关关；普通常亮可能继续 | 恢复会睡 | 同左 |

反例（不做 A 的现状）：11:53 与 21:13 两次外部写 0 都会被 `engine.go` 的 `refresh` 判成 `poll-readback-mismatch` → `restore("pmset-failed")`，合盖保持结束，开关关掉；16:47 的 `enable` 直接回 `foreign-setting`，开关是灰的，用户无从下手。

### 1.3 反方向与抢的边界

| 情形 | 期望 | 由谁执行 |
| --- | --- | --- |
| 我方 `on-ours`，外部写 0，意图仍有效且未到截止/电量保护/12 小时 | 5 秒内写回 1，继续 `on-ours` | 助手（观察 + 重写） |
| 同上，但 10 分钟内已重写 3 次（或本次租约已 12 次） | 停止重写，删 journal，进 `off` + `code=contested`，提示一次；普通常亮继续 | 助手判断，应用提示 |
| 我方 `on-ours`，外部写 0，重写本身失败 | 记 `detail=rewrite-failed`，保持 `on-ours`，按下一轮观察重试（仍受预算）；读不到 → 按既有连续读失败计数（3 次恢复）；预算耗尽 → `contested` | 助手 |
| 我方 `watching`，外部写 0 | 先写 journal（`writer=ours`）再写 1，然后读回，`on-ours` | 助手 |
| 我方 `watching`，外部写 1（本来就 1） | 什么都不做 | — |
| 外部写 1 时我方 `off` | 只报告 `on-foreign`，绝不改写 | 助手 |

### 1.4 会睡、会不睡、谁负责恢复

| 场景 | 合盖后 | 恢复责任 |
| --- | --- | --- |
| `watching` 中用户停止/退出/到期/助手重启 | 由**外部工具**决定（它的 1 还在） | 外部工具 |
| `watching` 中外部释放（0）→ 我方接手 | 不睡 | Cubbix |
| `on-ours` 中任何结束路径 | 恢复会睡 | Cubbix（写 0 → 读回 0 → 删 journal） |
| `contested` | 该值此时是 0，无遗留 | 无（已确认 0 才删 journal） |

## 2. 状态机

### 2.1 助手侧（`internal/lid/engine.go`）

现有状态：`off`、`on-ours`、`on-foreign`、`restoring`、`restore-failed`（`engine.go` 的 `refresh`／`restore`／`Handle`）。本设计新增 **`watching`**，并把「要不要写 0」从「有没有 journal」改成「journal 里的 `writer` 是谁」。

| 状态 | 含义 | 进入条件 | 执行者 | journal | 界面/CLI |
| --- | --- | --- | --- | --- | --- |
| `off` | 没有租约 | 初始；所有结束路径收敛后 | 助手 | 无 | 开关关；`lid.state=off` |
| `on-ours` | 租约有效，值 1 是我方写的 | `enable` 从 0 写 1 并读回；或 `watching` 接手成功；或重写成功 | 助手 | `writer=ours` | 开关开；`on` |
| `watching` | 租约有效，值 1 是外部写的，我方只登记意图 | `enable{adoptForeign:true}` 且现值 1、无 journal | 助手 | `writer=foreign` | 开关开 + 第二行「暂由其他工具维持…」；`watching` |
| `on-foreign` | 值 1 且无 journal（别人的） | 观察读到 1 且无 journal | 助手（由外部写入触发） | 无 | 开关可点；`LidForeign` |
| `restoring` | 正在写 0 | 结束路径且 `writer=ours` | 助手 | `writer=ours` | `stopping` |
| `restore-failed` | 写 0 或读回失败，按 004 §3.4 退避重试 | `restore` 失败 | 助手 | 保留 | `restore-failed` + 既有恢复入口 |

转换表（含 journal 变化）：

| # | 从 | 到 | 触发 | 执行者 | journal 动作 | 系统设置 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `off` | `on-ours` | `enable`，现值 0，前置检查通过 | 助手 | 写入（`writer=ours`，`started=now`） → `Set(1)` → 读回 1 | 0→1 |
| 2 | `off` | `on-foreign` | 观察到 1、无 journal | 助手（外部写入是起因） | 无 | 不动 |
| 3 | `on-foreign` | `watching` | `enable{adoptForeign:true}` | 助手 | 写入（`writer=foreign`） | **不写** |
| 4 | `watching` | `on-ours` | 观察到 0 | 助手 | 原地改 `writer=ours`、`started=now` → `Set(1)` → 读回 1 | 0→1 |
| 4b | `watching` | `on-ours`（写入未成功） | 同上但 `Set`／读回失败 | 助手 | 保持 `writer=ours`，计入预算 | 可能仍为 0 |
| 5 | `on-ours` | `on-ours` | 观察到 0，预算允许 | 助手 | 计数 +1 落盘 → `Set(1)` → 读回 1 | 0→1 |
| 6 | `on-ours` | `off`（`code=external-release-failed`） | 观察到 0，重写失败且再读确认 0 | 助手 | 删除 | 不动（已是 0） |
| 7 | `on-ours`/`watching` | `off`（`code=contested`） | 预算耗尽（见 §3.4） | 助手 | 删除 | 不动 |
| 8 | `on-ours` | `restoring` → `off` | 用户 `disable`、EOF、租约过期、`deadline`、12 小时上限、电量保护 | 助手 | 写 0 → 读回 0 → 删除 | 1→0 |
| 9 | `watching` | `off`（`code=ok` 或 `max-duration`／`battery-low`／`battery-unknown`） | 同上四条 | 助手 | **只删除，不写值** | 不动 |
| 10 | `on-ours` | `restore-failed` | `restore` 失败 | 助手 | 保留 | 可能仍为 1 |
| 11 | `restore-failed` | `off` | 退避重试成功 | 助手 | 删除 | 1→0 |
| 12 | 任意（启动） | `off`／`on-foreign` | 助手启动读到 journal | 助手 | `writer=ours`：先恢复 0 再删；`writer=foreign`：**直接删除、不写** | 前者 1→0，后者不动 |

### 2.2 应用侧（`lid_controller.go`）

`lidState` 与 `lidSnapshot` 是界面的唯一来源（`lid_view.go`、`awake_app.go`、`cli_server.go` 全部读它）。本设计不新增 `lidState` 值，而是给 `lidSnapshot` 加三个字段：`watching bool`、`adapter string`、`rewrites int`。理由：`lidOn` 已经是「开关打开、租约有效」，把它拆成两个状态会把 `toggleLid`、`finishLidPoll`、`stopLocked` 里所有 `state == lidOn` 的判断都要改一遍，收益为零。

| 助手状态 | 应用 `lidSnapshot` | 开关 | 说明文字 |
| --- | --- | --- | --- |
| `on-ours` | `state=lidOn, watching=false` | 开 | 无 |
| `watching` | `state=lidOn, watching=true` | 开 | 第二行 `LidWatching` |
| `on-foreign` | `state=lidBlocked, reason=LidForeign` | **可点（关态）** | 无（点了才进入 watching） |
| `off` + `contested` | `state=lidBlocked, reason=LidContested` | 关 | alert 图标 + tooltip |
| `off` + `external-release-failed` | `state=lidBlocked, reason=LidExternalReleaseFailed` | 关 | alert 图标 + tooltip |

### 2.3 谁执行

| 动作 | 执行者 | 说明 |
| --- | --- | --- |
| 写／读 `disablesleep` | **只有助手** | 应用侧唯一的例外仍是 004 §3.8 的「强制恢复睡眠」手动按钮，且它只在**我方遗留**时出现 |
| 判定「外部写入了」「外部释放了」 | **助手**（观察 + `Tick`） | 合盖后应用可能不在前台、也不保证进程存活，判定必须在助手 |
| 判定意图（用户是否想要合盖） | 应用 | `config.AwakeLid` + 会话 `Lid` 位；助手只接受 `enable`／`disable` |
| 授权 | 只有用户主动点开关／命令面板 | URL、CLI、轮询永不授权（004 §6.2 第 6 条、006 §7 第 7 条） |
| 提示 | 应用 | 助手只回 `state`／`code`／`detail` |

### 2.4 责任矩阵（谁写的 1，谁负责恢复）

| 值 | journal | 值是谁写的 | 我方是否负责恢复 | 我方停止／退出／崩溃 | 助手重启 | 应用崩溃 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 无 | 外部 | 否 | 不写 | 不改（`on-foreign`） | 不写 |
| 1 | `writer=foreign` | 外部 | 否 | 只丢登记，不写 | 丢登记，不写 | 租约过期后丢登记，不写 |
| 1 | `writer=ours` | 我方 | **是** | 写 0 → 读回 0 → 删 journal | 启动即恢复 0 | 租约过期（≤15s）后恢复 |
| 0 | `writer=ours` | ——（外部已改回） | 已无遗留 | 预算内重写 1；超限删 journal | 写 0（幂等）并删 | 启动时恢复为 0 并删 |

四条不变量（实现与评审都可以拿它当检查表）：

1. 任何时刻如果值是 1 且 `writer=ours`，则 journal 一定先于写入落盘（§3.3）。
2. 我方**从不**为自己没写过的 1 写 0。
3. 只有在确认值为 0 之后才允许删掉 `writer=ours` 的 journal（不确认就删，会丢掉恢复义务）。
4. `watching` 在我方崩溃／助手重启后一律失效（不做无人看管的观察），重新挂靠只能由在线应用发起。

## 3. A：外部占用时记住意图

### 3.1 数据结构

`internal/lid/engine.go` 的 `Journal` 增加四个字段（JSON 名保持 camelCase，与现有字段一致）：

```go
type Journal struct {
	Started    time.Time  `json:"started"`
	Deadline   *time.Time `json:"deadline"`
	MinPercent int        `json:"minPercent"`
	Previous   int        `json:"previous"`

	// Writer 记录这一次的 1 是谁写的。空字符串表示旧版助手写的 journal，
	// 旧版只会自己写 1，因此一律按 "ours" 处理（向后兼容见 §6）。
	Writer      string    `json:"writer,omitempty"`      // "ours" | "foreign"
	Rewrites    int       `json:"rewrites,omitempty"`    // 本租约累计重写次数
	WindowAt    time.Time `json:"windowAt,omitempty"`    // 当前预算窗口起点

### 3.3 关键顺序（硬约束）

观察 → 接手的顺序（`watching` → `on-ours`）：

```
1. 读到值 0（此时我方没有任何写入）
2. 预算允许
3. journal 原地改写为 writer=ours、started=now，并落盘（fsync）
4. pmset -a disablesleep 1
5. 读回，必须是 1；不是 1 或读失败 → 保留 journal（我方已声明所有权），下一轮由
   observe/restore 收敛；绝不在「声明了 ownership 却没写成功」时删 journal
6. state=on-ours, detail=adopted
```

重写的顺序（`on-ours` + 读到自己不是 1）：

```
1. 读到值 0
2. 预算允许 → 计数先落盘（崩溃后仍能看出打了几次）
3. pmset -a disablesleep 1 → 读回 1
4. 读回不是 1 或写失败 → detail=rewrite-failed，保持 on-ours，等下一轮
```

「先落盘再写」的理由与 004 §3.2 相同：崩溃点都必须能收敛到「值 0 且无 journal」或「值 1 且有 journal」，不允许出现「值 1 而无人负责」。

### 3.4 防抢参数

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| `ObserveInterval` | 5s | 「外部释放后立即接手」的可感知下限。观察主要由应用每 5s 一次的 `ping` 驱动（`awake_app.go:startAwakeServices` 的 1s ticker 里 `minute%5 == 0` 调 `pollLid` → `Inspect` → `ping`），因此 `tick` 里的 5s 观察只是**兑底**：应用卡在 `lidBusy`、或某次 `ping` 被有意跳过时仍有人在看。代价是租约期间最多每 5s 一次 `pmset -g` 只读（与既有每次请求都读一次同量级），不改变租约 15s 的语义 |
| `RewriteGap` | 10s | 一次外部释放只花一次重写；两个 5s 采样不会连写两次，也给对方留出完成它自己那次写入的时间 |
| `RewriteWindow` / `RewriteWindowLimit` | 10 分钟 / 3 次 | 现场里外部写入的间隔是分钟到小时级（09:50、11:53、13:50、21:13）。10 分钟内被改回 3 次已不属于正常阶段切换，而是两个工具在抢 |
| `RewriteSessionLimit` | 12 次 | 12 小时硬上限内最多每小时一次，覆盖「慢速来回」这种不会触发窗口上限、但同样属于抢的形态 |
| 超限后的行为 | 停止重写 → `contested` → 删 journal（此时值已确认为 0，无遗留）→ 应用提示一次 → 普通常亮继续 | 自动重试循环正是要避免的故障形态；让人按一次比让程序无限试更便宜、也更可解释 |
| 预算重置 | 用户关掉再打开合盖开关（新 journal），或新会话开始 | 不做时间上的自动恢复：`contested` 之后静默自愈会把一次真实的冲突藏起来 |

### 3.5 明确不做

- 不因为「看到 1」就写 0：`watching`、`on-foreign` 都不写值。
- 不在 `watching` 时伪造「我方遗留」标记（`lid_controller.go:writeMarker` 只在我方确认 1 之后调用）。
- 不把「外部 1 + 用户想要」直接变成「我方 1」：改写成我方 1 等于替对方解除它的设置，违反「不改别人的设置」。
- 不在 URL／CLI 路径上引入任何授权或安装。
- 不引入第二套「谁想要合盖」的记录：意图仍然只有 `config.AwakeLid` 与会话 `Lid` 位。

## 4. B：插电时不触发低电量保护

### 4.1 现状定位

`internal/lid/engine.go:Engine.tick` 每 30s 采一次 `Power.Source()`，只要 `p <= journal.MinPercent` 就 `restore("battery-low")`，完全不看适配器；`Engine.Handle` 的 `enable` 分支同样只看 `kind == "battery" && p <= min`。`internal/lid/power_darwin.go:SystemPower.Source` 只读内置电池的 `Power Source State`（`AC Power`／`Battery Power`）与 `Current Capacity`／`Max Capacity`（`IOPSKeys.h` 的 `kIOPSPowerSourceStateKey`、`kIOPSCurrentCapacityKey`、`kIOPSMaxCapacityKey`）。应用侧 `lid_controller.go:enable` 的预检复制了同一条件。

也就是说：判断依据是「谁在供电」，不是「适配器在不在」。外部工具强制放电时「谁在供电」就是电池，于是保护误触发——这正是需要修的地方。

### 4.2 候选信号

| # | 信号 | 依据 | 无适配器 | 插电（供电或保持） | 外部工具强制放电 | 评价 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | IOPS `Power Source State`／`IOPSGetProvidingPowerSourceType` | `IOPowerSources.h`（文档化）；仓库 `internal/lid/power_darwin.go:SystemPower.Source` 已在用 | `Battery Power`（实测） | `AC Power` | **`Battery Power`（未证实，几乎必然）** | 只回答「谁供电」，单独用无法区分放电与拔电 |

**推荐规则**（v1）：

```
plugged := (Power Source State == AC) || (IOPSCopyExternalPowerAdapterDetails() != NULL)
保护触发 := !plugged && percent <= minPercent
读不到 percent → 沿用 004 的 battery-unknown 计数（不变）
读不到 plugged（绑定失败、矛盾）→ plugged=false（保守，保护保留）
```

理由：第 2 项是唯一文档化的「适配器是否接着」接口，第 1 项补上「已经明确在 AC 供电」的情况；其余都不可用或不可移植。**兜底原则按维护者要求：判断不了就当没插电。**

先说清代价：如果周一实测证明「强制放电期间第 2 项也返回 NULL」，那么放电期间 `plugged=false`，保护仍会在 `minPercent` 触发——也就是**今天的现状**，A 的两个改进不受影响，B 在放电场景下不生效。具体后果有两处：会话中降到下限会结束合盖保持（`LidBatteryLow`）；在校准放电期间才去开启会被预检以 `LidBatteryTooLow` 拒绝（“电量太低，先充电”，但适配器其实还接着）。这是有意选择：不为了让这一个场景好看而依赖第 6、7 项这类私有/机型相关的信号。是否要为此加一层私有信号，交给维护者按实测结果决定（§8 第 1 项）。

### 4.4 放在哪一侧、要不要升修订号

/usr/sbin/ioreg -rn AppleSmartBattery | grep -E '"(ExternalConnected|AppleRawExternalConnected|IsCharging|NotChargingReason)"'

```

`adapter-probe` 是一个几十行的只读小程序（附录给出源码，`clang -framework IOKit -framework CoreFoundation` 编译），只调用两个文档化的 IOPS 函数并打印结果，不写任何设置。

采集点（共 5 次，每次 10 秒内完成）：

| 次 | 时机 | 期望回答 |
| --- | --- | --- |
| 1 | 拔掉适配器、只用电池 | 基线：`Battery Power` + 详情 NULL（本轮已取得同样读数） |
| 2 | 插上适配器、正常供电 | 详情非 NULL；记下字典里的 `Watts`／`Current`／`Voltage` |
| 3 | 到达充电上限、保持态（插着、不充电） | 详情是否仍非 NULL（这一档决定「保持态」是否被保护误伤） |
| 4 | **强制放电中（校准的 Discharge 阶段）** | **关键**：详情是否非 NULL。是 → B 按设计生效；否 → B 在放电场景不生效（§8 第 1 项） |
| 5 | 放电结束、重新供电 | 详情恢复非 NULL |

每次同时记 `pmset -g adapter` 与 `AppleSmartBattery` 的那四个键，用来判断第 3、4 项是否与详情一致。第 6、7 项（USB-C 端口、SMC）只作参考，不进入实现。

### 5.3 新增文案（`design/locales/zh-CN.json`、`en.json` 同步）

| 键 | 简体中文 | English |

规则：

- `LidForeign`（「系统里已有别的工具关闭了合盖睡眠，Cubbix 不会覆盖」）**保留并继续只用于「用户没表态」的情形**；用户表态之后换成 `LidWatching`。两条不能混用：一条是「我不动别人的」，一条是「我记着，等它放手」。
- `LidContested` 与 `LidExternalReleaseFailed` 加入 `lid_app.go:notifyLid` 的异常白名单（发一次系统通知）；`adopted` 与 `external-release` **不通知**，只在状态行体现——它们是正常收敛，通知会变成噪音。
- 不新增任何要求用户复制命令的文案（沿用 004 第 2 版的决定）。

## 6. 兼容与升级

| 项 | 处理 |
| --- | --- |
| 旧 journal（无 `writer` 字段） | 一律视为 `writer=ours`。旧版助手只在「自己要写 1」之后才写 journal（`engine.go:Handle` 的 `enable` 分支先 `Store.Save` 再 `Set(1)`），所以空值只能是旧的我方记录。**不能**把缺省值当成 `foreign`——那会让一次真实的我方遗留失去恢复者 |
| IPC protocol | `Protocol` 保持 `1`。只新增字段与新枚举值；`state="watching"` 只会出现在修订 5 的助手上，而修订号不等的组合会被 `lid_controller.go:connect` 的 `errLidHelperUpdate` 挡住（应用侧要求 `r.Helper == lid.Version`），不存在「旧应用解析新状态」的路径 |
| 助手修订号 | `internal/lid/protocol.go:Version` `"4"`→`"5"`。理由见 §4.4 |
| 升级时是否再授权一次 | **要一次**，且只在用户下一次主动点合盖开关／命令面板动作时发生（004 §3.6 的既有流程：恢复 → 授权安装 → 同版 hello）。轮询、CLI、URL、启动都不安装、不授权 |
| 升级顺序 | 应用与助手同一版本发布：新应用 + 旧助手 = `LidHelperUpdate`（可用性不受影响，只是合盖保持需要更新）；旧应用 + 新助手 = 同样被版本闸门挡住，行为不会「半新半旧」 |
| `config.AwakeLid` | 语义不变（下次会话是否带合盖）。`watching` 时用户表态成功就记 true；`contested`／`external-release-failed` 只结束本次会话，不清偏好 |
| 标记文件 `lid-restore-required` | 只在我方确认写 1 之后创建（`lid_controller.go:writeMarker`）；`watching` 不创建，进入 `watching` 时若存在则删除（意味着过去的我方遗留已被处理）。`canForce` 的判定不变，因此 `watching` 期间永远不会出现「强制恢复睡眠」 |
| 降级路径 | 助手不在线时的 `readStale`（`lid_controller.go:readStale`）行为不变：读到 1 且无标记 → 只提示、不提供按钮。这一条正好与 A 相容：没有助手就没有观察者，不能登记意图 |
| 006 的成功判定 | 006 §4.4 写的是「只有读回 1、保存标记并确认会话仍有效，才返回 `ok:true` 与 `lid.state:on`」。本设计把成功的定义扩为「读回 1」**或**「助手已写入 `watching` 并受理」；`watching` 时**不写标记**（未写值即无遗留），其余（会话仍有效、失败退出 4、不授权）不变。实现时同步改 006 的这句话与它的测试断言 |
| 需要回改的既有规格 | 004 §3.7（应用状态机与 `on-foreign` 的描述）、§5.2 第 11、12 行（电量保护改为插电不触发）、§5.3 启动表（`foreign` journal 不恢复）、§5.5（补充适配器判定）、§8.1（新增四个键、`LidForeign` 只用于未表态情形）、§8.4（新增待决项）；006 §4.4（成功判定）与 §4.5 的 `lid.state` 枚举。两份规格的其余条款不变，冲突时以 009 为准 |

## 8. 待维护者决定

| # | 问题 | 推荐 |
| --- | --- | --- |
| 1 | 若周一实测证明强制放电期间 `IOPSCopyExternalPowerAdapterDetails` 为 NULL（放电不可识别），怎么办 | **接受现状**：放电期间按「未插电」保留保护（用户会在 20% 看到一次 `LidBatteryLow`），不为此引入 USB-C 私有类或 SMC 键（本轮已实测键名随机型变化）。若维护者要求放电也不触发，则另开一版，只在助手侧加一条私有信号，并接受随系统更新失效的风险 |
| 2 | 防抢数值（5s / 10s / 3 次/10min / 12 次/租约） | 按 §3.4 采用。若真实节奏更密（例如某个工具每秒写一次），把 `RewriteWindowLimit` 降到 1 就能退化成「一次机会 + 人工」，不需要改结构 |
| 3 | 预算耗尽后是否需要自动恢复 | **不自动**：等用户重开一次合盖开关（新租约）。自动恢复会把真实冲突藏起来 |
| 4 | 助手重启后是否自动重挂观察 | **自动重挂一次**（每次重连一次），因为丢掉登记会让用户以为仍在保持；不重开会静默失效。不自动重开的是「我方已写成 1 的会话」（004 §5.3 的既有规则不变） |
| 5 | 接手/重写要不要发系统通知 | 不发。只在状态行与 tooltip 体现；异常的两条（`contested`、`external-release-failed`）发 |
| 6 | 接手后 12 小时上限从哪算 | 从**接手时刻**起算（`Started` 重置）。此前没有 1，若沿用外部写入时间，用户会得到一个被外部工具「吃掉」的时限 |
| 7 | `watching` 能否由 URL/CLI 触发 | 可以，但没有新的放宽：CLI 仍要求显式时长（006 §3.6），URL 仍要求 `minutes` 1..480。它们不写值、不授权，最坏后果只是一次「接管登记」 |
| 8 | 是否接受助手修订号 `4`→`5` 带来的再一次授权 | 接受。这是 004 已定的规则（改行为必升修订号），且只影响下一次主动点开关 |
| 9 | `watching` 时猫标是否要第三态图标 | 不要。004 §8.2 已把第三态留给品牌资产；本次用第二行文字，等资产到位再说 |

### 附 A：`adapter-probe`（只读，供 §4.5 使用）

编译：`clang -framework IOKit -framework CoreFoundation -o adapter-probe adapter-probe.c`。它只调用两个文档化的 IOPS 函数并打印结果，不写任何设置、不读任何用户数据。

```c
#include <stdio.h>
#include <CoreFoundation/CoreFoundation.h>
#include <IOKit/ps/IOPowerSources.h>
#include <IOKit/ps/IOPSKeys.h>

int main(void) {
    CFTypeRef snapshot = IOPSCopyPowerSourcesInfo();          // 调用方持有，需 release
    CFStringRef kind = IOPSGetProvidingPowerSourceType(snapshot);
    char buf[128] = "<nil>";
    if (kind) CFStringGetCString(kind, buf, sizeof buf, kCFStringEncodingUTF8);
    printf("ProvidingPowerSourceType = %s\n", buf);

    CFDictionaryRef adapter = IOPSCopyExternalPowerAdapterDetails();
    if (!adapter) {
        printf("ExternalPowerAdapterDetails = <NULL>\n");
    } else {
        CFStringRef text = CFCopyDescription(adapter);
        char *out = NULL;
        CFIndex size = CFStringGetMaximumSizeForEncoding(CFStringGetLength(text),
                                                         kCFStringEncodingUTF8) + 1;
        out = malloc(size);
        if (out && CFStringGetCString(text, out, size, kCFStringEncodingUTF8)) {
            printf("ExternalPowerAdapterDetails = %s\n", out);
        }
        free(out);
        CFRelease(text);
        CFRelease(adapter);
    }
    if (snapshot) CFRelease(snapshot);
    return 0;
}
```

判读：`ExternalPowerAdapterDetails` 非 NULL 就是「读到了适配器」；NULL 同时覆盖「没接」与「出错」两种情况，因此必须与同一时刻的 `ProvidingPowerSourceType`、`pmset -g adapter` 一起看（§4.2 第 1、2 项）。
