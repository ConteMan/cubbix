## 结论摘要

| 项 | 结论 |
| --- | --- |
| A 的核心 | 把「值是不是 1」改成「值是谁写的」。新增**观察（watching）**态：外部持有 1 时 Cubbix 不写值、只登记「想要合盖」，并在外部释放（0）时由**助手**写回 1 转为 `on-ours`；反向（我方 `on-ours` 被外部改回 0）同样由助手重写，带次数上限（§3.4） |
| 责任边界 | 谁写的 1，谁负责恢复。Cubbix **从不**为自己没写过的 1 写 0；凡 `writer=foreign`（含 `watching`）的结束路径只删登记，绝不调用 `Sleep.Set`（§2.1、§3.2） |
| 不弹授权 | 接手、重写全部发生在助手内部与已授权连接上；URL／CLI／轮询路径仍永不调用 `Register()`（沿 004 §6.2 第 6 条） |
| B 的核心 | 低电量保护只在**没有适配器**时触发：`Power Source State = AC` 或 `IOPSCopyExternalPowerAdapterDetails` 非 NULL 才算插电，其余（含 NULL、绑定失败）一律按未插电（保守） |
| B 的已证实限制 | 外部工具强制放电时，powerd 侧公开接口**一律**报「未插电」（2026-11-09 23:11 维护者现场确认，§0）。因此 B **不会**在「插着电强制放电」这一段生效；缓解手段是新增 5% 阈值档（§4.6），不是私有信号 |
| 执行位置 | 电量保护、观察与写入都在**助手**侧（合盖后应用看不到界面、也不保证在跑）；应用只做开启前预检与展示。助手修订号 `4`→`5`，升级后用户下一次主动点合盖开关时再授权一次（§6） |
| 新增状态码 | 助手 `state=watching`；`code` 新增 `contested`、`external-release-failed`；瞬态事件放 `detail`（`adopted`、`external-release`、`rewrite-failed`）。协议常量 `Protocol=1` 不变 |
| 防抢数值 | 只读观察 1s（搭在助手已有的 1 秒 `tick` 上）；重写最小间隔 10s；10 分钟内最多 3 次；单个租约最多 12 次；连续写失败 3 次放弃。超限降级为 `contested`／`external-release-failed` 并提示，需用户重开一次（§3.4 给理由） |
| 低电量下限 | 允许值 `5／10／20／30`，默认仍是 20（§4.6）。旧配置（10／20／30）不改写、不迁移；助手侧 `minPercent` 的协议范围由 10..50 放宽到 5..50 |
| 升级 | 旧 journal 无 `writer` 字段一律视为我方所有（向后兼容）；助手修订号不匹配的既有闸门（`lidController.connect`）已能挡住新旧组合，不新增兼容分支 |

## 0. 现场与只读读数

现场时间线（维护者提供，助手修订 4，Cubbix 0.6.1）：

```
01:15 request op=disable → state=off value=0          （维护者关闭合盖）
09:50 ping → foreign-setting state=on-foreign value=1  （校准开始，外部写 1）
11:53 ping → ok state=off value=0                      （阶段切换，外部写 0）
13:50 ping → foreign-setting state=on-foreign value=1  （充电保持阶段）
16:47 / 21:13 request op=enable ok=false code=foreign-setting
```

`on-foreign` 由 `internal/lid/engine.go` 的 `refresh` 产生：读到 1 且没有 journal 就是「别人的 1」；`enable` 在 `Handle` 里对 `value != 0` 直接回 `foreign-setting`。应用侧 `lid_controller.go` 的 `apply` 把它映射成 `LidBlocked` + `LidForeign`，`lid_view.go` 的 `panelLid` 又把 `LidForeign` 写进 `Disabled(...)`——这就是「开关变灰」的完整链路。

本轮只读读数（2026-11-09 22:30 前后，与上面的现场同一台机器，但不是校准时刻；当时没有插适配器，见下）：

| 信号 | 读取方式 | 读数 |
| --- | --- | --- |
| 供电来源 | `pmset -g batt` | `Now drawing from 'Battery Power'`；`95%; discharging; 9:11 remaining` |
| 适配器 | `pmset -g adapter` | `No adapter attached.` |
| IOPS 供电状态 | `IOPSGetProvidingPowerSourceType` | `Battery Power` |
| IOPS 电池描述 | `IOPSCopyPowerSourcesInfo` → 内置电池 | `Power Source State = Battery Power`、`Is Charging = 0`、`Current Capacity = 95`、`Max Capacity = 100` |
| **适配器详情** | `IOPSCopyExternalPowerAdapterDetails` | **NULL** |
| 电池注册表 | `ioreg -rn AppleSmartBattery` | `ExternalConnected = No`、`AppleRawExternalConnected = No`、`IsCharging = No`、`NotChargingReason = 4096` |
| 同一条注册表里的适配器缓存 | 同上 | `AdapterDetails`（`Watts = 65`）与 `AppleRawAdapterDetails` **仍然存在** |
| USB-C 侧 | `ioreg` 的端口子树 | 某端口 `CC` 传输 `Active = Yes`，带一个 USB-C 供电伙伴；同端口 `Power In` 为 `Active = No`；`USB-PD` 节点缓存了 65 W 的 `WinningPowerSourceOption` |
| 私有电源键 | 同上，`FedDetails`、`PowerDistribution` | `FedDetails` 里有一项 `FedExternalConnected = 1`；`PowerDistribution` 里还有 65 W 的输入功率 |
| SMC（只读、非 root） | 只读 `AppleSMC` 键 | 本机型存在 `B0AC`（si16）、`CHIE`、`CHSC`、`AC-N`；`CH0B`、`CH0C`、`CH0I`、`CHTE`、`CHWA`、`ACEN`、`B0St`、`D0IR` **不存在** |
| 系统报告 | `system_profiler SPPowerDataType` | `AC Charger Information: Connected: No` |

**维护者现场确认（2026-11-09 23:11）**：上面这一组读数采集时，机器**插着 Type-C 一线通电源**，AlDente 正在把电量从 100% 放回 80%（强制放电）。也就是说，插着电、由外部工具强制放电时，`pmset -g batt`、`pmset -g adapter`、`IOPSGetProvidingPowerSourceType`、`IOPSCopyPowerSourcesInfo`、`system_profiler` 与 `AppleSmartBattery.ExternalConnected`／`AppleRawExternalConnected` **全部报未插电**。

由此得到三条结论：

1. **「插电强制放电时公开接口一律显示未插电」已证实。** 上面那一组矛盾读数不是残留缓存造成的误判，而是真实状态：适配器物理插着，powerd 认为没有。任何只依赖公开接口的实现在这一段都无法区分「插着放电」与「真的拔了」。
2. **`AdapterDetails` 不能当作「适配器接着」的证据**（与第 1 条相互印证）：缓存字段在拔掉时依然存在，在插着放电时也存在，它恒在。
3. **私有键不能用来补这个洞**：同一次读数里 `FedDetails` 的 `FedExternalConnected` 是 1、`PowerDistribution` 里还有 65 W 输入，多端口之间彼此不一致，也无法区分「真的拔了」和「缓存还在」。它们**不进入 v1 判定**（§4.3）。

因此 B 的定位要说清楚：它修的是「插着电、正常供电或保持不充电时电量低于下限被误恢复」（这一档公开接口能正确回答），**不修**「插着电、被外部工具强制放电」这一档——那一档改用 5% 阈值档来让校准不被保护打断（§4.6）。

## 1. 场景与时间线

### 1.1 两种意图

外部工具持有 1 时，Cubbix 只有两种姿态，由用户点不点合盖开关决定：

| 用户动作 | Cubbix 的行为 | 系统设置 | 责任 |
| --- | --- | --- | --- |
| 不点开关 | 只报告「已有别的工具关闭了合盖睡眠」，不写、不抢 | 别人的 1 原样 | 别人的 |
| 点开关 | 进入 `watching`：登记「想要合盖保持」，**不写值**，监听到 0 就接手 | 别人的 1 原样，直到它自己变 0 | 别人的 1 由别人恢复；接手后的 1 由 Cubbix 恢复 |

### 1.2 按 AlDente 校准过程逐段（A 行为）

设维护者在 09:50 之后点了合盖开关，会话是「仅保持任务」、没有用户指定截止（只剩 12 小时硬上限）。

| 阶段 | 外部动作 | 助手侧 | 应用侧 | 合着盖 | 开着盖 |
| --- | --- | --- | --- | --- | --- |
| 01:15 | 用户关掉合盖 | `off` | 开关关 | 会睡 | 开关关 |
| 09:50 | AlDente 写 1 | 观察到 1 且无 journal → `on-foreign`（不写） | `lidBlocked` + `LidForeign`；**开关可点** | 略（此刻还没人登记意图） | 状态行提示「其他工具已关闭合盖睡眠」 |
| 09:55 | 用户点开关 | `enable{adoptForeign:true}` → 写 journal（`writer=foreign`、`started=09:55`）→ `watching`，**零次 `pmset` 写入** | `lidOn` + `watching`；开关打开；第二行「暂由其他工具维持，它释放后 Cubbix 接手」 | 机器不睡，因为 AlDente 的 1 生效；Cubbix 不上报「合盖也保持已中断」 | 会话继续计时 |
| 11:53 | AlDente 写 0（阶段切换） | 观察（≤1s）→ 预算允许 → journal 原地改 `writer=ours`、`started=11:53`（`deadline` 不变）→ `Set(1)` → 读回 1 → `on-ours`，`detail=adopted` | 开关仍打开，第二行消失 | 尽快写回；写回前的几秒窗口未证实，可能短暂睡眠 | 状态行不变 |
| 13:50 | AlDente 写 1（保持阶段） | 值本来就是 1 → **不写**，`on-ours` 不变，责任仍在我方 | 无变化 | 不睡 | 无变化 |
| 16:47 | CLI/URL `cubbix awake on --minutes N --lid` | 已 `on-ours` → 走续期（更新 `deadline`，不写值、不清重写预算） | `ok:true`，`lid.state=on` | 不睡 | 无变化 |
| 21:13 | AlDente 写 0（校准结束） | 观察 → 重写 1（预算消耗 1/3）→ `on-ours`，`detail=external-release` | 开关仍打开，无提示 | 尽快写回；写回前的几秒窗口未证实，可能短暂睡眠 | 状态行不变 |
| 用户停止 | — | `disable` → 写 0 → 读回 0 → 删 journal | 开关关；普通常亮可能继续 | 恢复会睡 | 同左 |

时间窗口：11:53 的接手把 `started` 重置到接手时刻（§8 第 6 条），硬上限因此落在 23:53，21:13 那次重写仍在窗口内。若用户当年在 09:55 指定了更早的 `deadline`，则到点按 §2 第 9 行结束：`watching` 只删登记、`on-ours` 写 0 并读回。

反例（不做 A 的现状），两条不同的路径，不能混成一条：

- **21:13 那一次（有租约）**：`engine.go` 的 `refresh` 读到 `state == on-ours` 且值不是 1，走 `poll-readback-mismatch` → `restore("pmset-failed")`，写 0、删 journal、合盖保持结束。这是本设计要改掉的那条（§3.2）。
- **11:53 那一次（没租约）**：01:15 已关闭，当时没有 journal；`refresh` 在 `journal == nil` 且值为 0 时只把状态设回 `off`，不会写任何东西——后果不是「被当成读回不符」，而是 **11:53 之后没有人再写回 1**，直到 13:50 外部又写 1。16:47 与 21:13 的 `enable` 也不是被读回逻辑拒绝，而是 `Handle` 的 `value != 0` 分支直接回 `foreign-setting`，开关是灰的，用户无从下手。

### 1.3 反方向与抢的边界

| 情形 | 期望 | 由谁执行 |
| --- | --- | --- |
| 我方 `on-ours`，外部写 0，意图仍有效且未到截止/电量保护/12 小时 | 尽量快写回 1（观察 1s，写入 ≥10s 一次），继续 `on-ours` | 助手（观察 + 重写） |
| 同上，但 10 分钟内已重写 3 次（或本次租约已 12 次），且此刻又明确读到 0 | 停止重写，删 journal，进 `off` + `code=contested`，提示一次；普通常亮继续 | 助手判断，应用提示 |
| 同上，但写入连续失败 3 次，且此刻明确读到 0 | 删 journal，进 `off` + `code=external-release-failed`，提示一次 | 助手判断，应用提示 |
| 我方 `on-ours`，外部写 0，重写本身失败 | 记 `detail=rewrite-failed`，保持 `on-ours` 与 journal，下一轮观察重试（仍受预算）；**读回 1 则当无事发生**；读失败沿用 `readFailureLimit` 计数，不删 journal | 助手 |
| 我方 `watching`，外部写 0 | 先写 journal（`writer=ours`）再写 1，然后读回，`on-ours` | 助手 |
| 我方 `watching`，外部写 1（本来就 1） | 什么都不做 | — |
| 外部写 1 时我方 `off` | 只报告 `on-foreign`，绝不改写 | 助手 |

### 1.4 会睡、会不睡、谁负责恢复

| 场景 | 合盖后 | 恢复责任 |
| --- | --- | --- |
| `watching` 中用户停止/退出/到期/助手重启 | 由**外部工具**决定（它的 1 还在） | 外部工具 |
| `watching` 中外部释放（0）→ 我方接手 | 尽快写回；写回前的几秒窗口未证实，可能短暂睡眠 | Cubbix |
| `on-ours` 中任何结束路径 | 恢复会睡 | Cubbix（写 0 → 读回 0 → 删 journal） |
| `contested`／`external-release-failed` | 该值此时经确认是 0，无遗留 | 无 |

**v1 不承诺「合着盖一定不睡」**：从外部把 `disablesleep` 写成 0，到助手读回并写回 1，中间有一个窗口。004 已说明 `caffeinate` 挡不住合盖；powerd 会不会在合盖已关闭的情况下立刻睡，本轮**未证实**。一旦睡了，`internal/lid/transport.go` 的 `Server.Serve` 里那条 1 秒 `Tick` 也会停，写回发生在醒来之后。v1 的承诺降级为：**租约还在时，尽可能快地写回**（观察 1s + 写入间隔 10s），并把「外部写 0 → 我方读回 1」的间隔与机器是否睡过记在 §7.3 第 7 项。

## 2. 状态机

### 2.1 助手侧（`internal/lid/engine.go`）

现有状态：`off`、`on-ours`、`on-foreign`、`restoring`、`restore-failed`（`engine.go` 的 `refresh`／`restore`／`Handle`）。本设计新增 **`watching`**，并把「要不要写 0」从「有没有 journal」改成「journal 里的 `writer` 是谁」。

| 状态 | 含义 | 进入条件 | 执行者 | journal | 界面/CLI |
| --- | --- | --- | --- | --- | --- |
| `off` | 没有租约 | 初始；所有结束路径收敛后 | 助手 | 无 | 开关关；`lid.state=off` |
| `on-ours` | 租约有效，值 1 是我方写的 | `enable` 从 0 写 1 并读回；或 `watching` 接手成功；或重写成功 | 助手 | `writer=ours` | 开关开；`on` |
| `watching` | 租约有效，值 1 是外部写的，我方只登记意图 | `enable{adoptForeign:true}` 且现值 1、无 journal | 助手 | `writer=foreign` | 开关开 + 第二行「暂由其他工具维持…」；`watching` |
| `on-foreign` | 值 1 且无 journal（别人的） | 观察读到 1 且无 journal | 助手（由外部写入触发） | 无 | 开关可点；`LidForeign` |
| `restoring` | 正在写 0 | 结束路径且 `writer=ours` | 助手 | `writer=ours` | `stopping` |
| `restore-failed` | 写 0 或读回失败，按 004 §3.4 退避重试 | `restore` 失败（只可能发生在 `writer=ours`） | 助手 | 保留 | `restore-failed` + 既有恢复入口 |

转换表（含 journal 变化）：

| # | 从 | 到 | 触发 | 执行者 | journal 动作 | 系统设置 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `off` | `on-ours` | `enable`，现值 0，前置检查通过 | 助手 | 写入全套（`writer=ours`、`started=now`、`deadline`、`minPercent`、`previous=0`） → `Set(1)` → 读回 1 | 0→1 |
| 2 | `off` | `on-foreign` | 观察到 1、无 journal | 助手（外部写入是起因） | 无 | 不动 |
| 3 | `on-foreign` | `watching` | `enable{adoptForeign:true}`，现值 1 | 助手 | 写入全套（`writer=foreign`、`started=now`、`deadline`、`minPercent`、`previous=0`、预算计数清零），见 §3.2 的 `Engine.watch` | **不写** |
| 4 | `watching` | `on-ours` | 观察到**明确 0**，预算允许 | 助手 | 原地改 `writer=ours`、`started=now`（`deadline`／`minPercent`／已有预算计数不动） → `Set(1)` → 读回 1 | 0→1 |
| 4b | `watching` → `on-ours`（写入未成功） | 同上但 `Set` 失败或读回不是 1 | 助手 | 保持 `writer=ours`（已声明所有权），`detail=takeover-write-failed`／`takeover-readback-failed`；**不删 journal** | 可能仍为 0 |
| 5 | `on-ours` | `on-ours` | 观察到**明确 0**，预算允许 | 助手 | 只更新 `rewrites`／`windowAt`／`windowCount`／`lastRewrite`（**`started`、`deadline` 一律不动**） → `Set(1)` → 读回 1 | 0→1 |
| 6 | `on-ours` | `off`（`code=contested`） | 观察到**明确 0**，且预算已耗尽（§3.4） | 助手 | 删除 | 不动（已是 0） |
| 7 | `on-ours` | `off`（`code=external-release-failed`） | 观察到**明确 0**，且写入已连续失败 `RewriteFailLimit` 次 | 助手 | 删除 | 不动（已是 0） |
| 7b | `watching` | `off`（`code=contested`） | 观察到**明确 0**，但预算不允许接手 | 助手 | **只删除，不写值** | 不动（已是 0） |
| 8 | `on-ours` | `restoring` → `off` | 用户 `disable`、EOF、租约过期、`deadline`、12 小时上限、电量保护 | 助手（经 `Engine.end`） | 写 0 → 读回 0 → 删除 | 1→0 |
| 9 | `watching` | `off`（`code=ok`／`max-duration`／`battery-low`／`battery-unknown`） | 同上全部结束路径 | 助手（经 `Engine.end` → `dropWatch`） | **只删除，不写值** | 不动 |
| 10 | `on-ours` | `restore-failed` | `restore` 失败 | 助手 | 保留 | 可能仍为 1 |
| 11 | `restore-failed` | `off` | 退避重试成功 | 助手 | 删除 | 1→0 |
| 12 | 任意（启动） | `off`／`on-foreign` | 助手启动读到 journal | 助手 | `writer=ours`：先恢复 0 再删；`writer=foreign`：**直接删除、不写**，随后观察一次 | 前者 1→0，后者不动 |

两条硬约束（评审「必须改」1、3 的落地形式）：

1. **凡 `writer=foreign` 的结束路径（第 9、7b 行）都不得调用 `Sleep.Set`。** `Engine.tick` 今天在截止时间、12 小时上限、租约、`battery-low`、`battery-unknown`、`restore-failed` 重试上都直接 `restore`，而 `restore` 无条件 `Sleep.Set(0)`；`Engine.refresh` 还有两条会 `restore` 的现有分支（`on-ours` 且连续读失败计满 `readFailureLimit`、`on-ours` 且值不是 1 的 `poll-readback-mismatch`）。实现时：前者只在 `writer=ours` 时累加与恢复；后者不再 `restore`，改走 `rewrite`（§3.2）。
2. **只有本次 `Sleep.Read` 明确得到 0，才允许删掉 `writer=ours` 的 journal。** 读到 1 → 保持 journal、不做结束；读失败 → 沿用 `on-ours` 的 `readFailureLimit`，不删除。这是第 6、7、7b 行的共同前提，也是 §2.4 不变量 3。

### 2.2 应用侧（`lid_controller.go`）

`lidState` 与 `lidSnapshot` 是界面的唯一来源（`lid_view.go`、`awake_app.go`、`cli_server.go` 全部读它）。本设计不新增 `lidState` 值，而是给 `lidSnapshot` 加四个字段：`watching bool`、`adapter string`、`rewrites int`、`rearmPending bool`。`rearmPending` 有上限：助手持续不在超过 `4 × Lease = 60` 秒就放弃重挂，按既有规则清标志，避免无限挂着。理由：`lidOn` 已经是「开关打开、租约有效」，把它拆成两个状态会把 `toggleLid`、`finishLidPoll`、`stopLocked` 里所有 `state == lidOn` 的判断都要改一遍，收益为零。

| 助手状态 | 应用 `lidSnapshot` | 开关 | 说明文字 |
| --- | --- | --- | --- |
| `on-ours` | `state=lidOn, watching=false` | 开 | 无 |
| `watching` | `state=lidOn, watching=true` | 开 | 第二行 `LidWatching` |
| `on-foreign` | `state=lidBlocked, reason=LidForeign` | **可点（关态）** | 无（点了才进入 watching） |
| `off` + `contested` | `state=lidBlocked, reason=LidContested` | 关 | alert 图标 + tooltip |
| `off` + `external-release-failed` | `state=lidBlocked, reason=LidExternalReleaseFailed` | 关 | alert 图标 + tooltip |

`watching` 的判据只有一处事实来源：助手回的 `state == "watching"`。应用侧不自己推断「值 1 是不是别人的」。

### 2.3 谁执行

| 动作 | 执行者 | 说明 |
| --- | --- | --- |
| 写／读 `disablesleep` | **只有助手** | 应用侧唯一的例外仍是 004 §3.8 的「强制恢复睡眠」手动按钮，且它只在**我方遗留**时出现 |
| 判定「外部写入了」「外部释放了」 | **助手**（自己的 1 秒 `tick`） | 合盖后应用可能不在前台、也不保证进程存活，判定必须在助手 |
| 判定意图（用户是否想要合盖） | 应用 | `config.AwakeLid` + 会话 `Lid` 位；助手只接受 `enable`／`disable` |
| 授权 | 只有用户主动点开关／命令面板 | URL、CLI、轮询永不授权（004 §6.2 第 6 条、006 §7 第 7 条） |
| 提示 | 应用 | 助手只回 `state`／`code`／`detail` |

### 2.4 责任矩阵（谁写的 1，谁负责恢复）

| 值 | journal | 值是谁写的 | 我方是否负责恢复 | 我方停止／退出／崩溃 | 助手重启 | 应用崩溃 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 无 | 外部 | 否 | 不写 | 不改（`on-foreign`） | 不写 |
| 1 | `writer=foreign` | 外部 | 否 | 只丢登记，不写 | 丢登记，不写 | 租约过期后丢登记，不写 |
| 1 | `writer=ours` | 我方 | **是** | 写 0 → 读回 0 → 删 journal | 启动即恢复 0 | 租约过期（≤15s）后恢复 |
| 0 | `writer=ours` | ——（外部已改回） | 值上无遗留，登记还在 | 预算内重写 1；预算耗尽且**读到 0** 才删 journal | 写 0（幂等）并删 | 启动时恢复为 0 并删 |

四条不变量（实现与评审都可以拿它当检查表）：

1. 任何时刻如果值是 1 且 `writer=ours`，则 journal 一定先于写入落盘（§3.3）。
2. 我方**从不**为自己没写过的 1 写 0。`writer=foreign` 的收尾只有一种动作：删登记。
3. 只有在确认值为 0 之后才允许删掉 `writer=ours` 的 journal（不确认就删，会丢掉恢复义务）。
4. `watching` 在我方崩溃／助手重启后一律失效（不做无人看管的观察），重新挂靠只能由在线应用发起。

由此引申一条明确接受的取舍：接手时若 `Set(1)` 失败、随后外部工具恰好把值写成 1，我方会按 `writer=ours` 对待它并在结束时写回 0——即**可能替别人关掉一次**。选择理由：另一种做法（写失败就放弃所有权）会留下无人负责的 1，正是不变量 3 要避免的形态；而这条路径需要「我方写失败」与「外部同时写 1」同时发生，现场是小时级间隔，概率极低。这条取舍写在这里，不藏。

## 3. A：外部占用时记住意图

### 3.1 数据结构

`internal/lid/engine.go` 的 `Journal` 增加五个字段（JSON 名保持 camelCase，与现有字段一致）：

```go
type Journal struct {
	Started    time.Time  `json:"started"`
	Deadline   *time.Time `json:"deadline"`
	MinPercent int        `json:"minPercent"`
	Previous   int        `json:"previous"`

	// Writer 记录这一次的 1 是谁写的。空字符串表示旧版助手写的 journal，
	// 旧版只会自己写 1，因此一律按 "ours" 处理（向后兼容见 §6）。
	Writer      string    `json:"writer,omitempty"`      // "ours" | "foreign"
	Rewrites    int       `json:"rewrites,omitempty"`    // 本租约累计重写次数
	WindowAt    time.Time `json:"windowAt,omitempty"`    // 当前预算窗口起点
	WindowCount int       `json:"windowCount,omitempty"` // 当前窗口已用次数
	LastRewrite time.Time `json:"lastRewrite,omitempty"` // 上一次重写时刻
}
```

`Journal.Previous` 仍只在 `Engine.Handle` 的 `enable` 里写成 0；`Engine.Start` 不读它（004 的「非 0 拒绝」在当前助手里没有对应分支）。`watch` 与接手也继续写 0。

`internal/lid/protocol.go`：

```go
Version = "5" // 助手实现修订号：新增 watching、适配器判定与 5% 下限，必须递增

const (
	ObserveInterval     = 1 * time.Second   // 只读观察间隔，搭在已有的 1 秒 tick 上
	RewriteGap          = 10 * time.Second  // 两次重写的最小间隔
	RewriteWindow       = 10 * time.Minute  // 预算窗口
	RewriteWindowLimit  = 3                 // 每窗口最多 3 次
	RewriteSessionLimit = 12                // 单个租约最多 12 次
	RewriteFailLimit    = 3                 // 连续写失败 3 次放弃（与 readFailureLimit 同值同理由）
)
```

`Request` 增加一个字段，只对 `enable` 生效：

```go
AdoptForeign bool `json:"adoptForeign,omitempty"`
```

`Response` 增加两个诊断字段（应用不用它们做判断，只用于 `cubbix status --json` 与实测）：

```go
Adapter  string `json:"adapter,omitempty"`  // "yes" | "no" | "unknown"
Rewrites int    `json:"rewrites,omitempty"` // 本租约已重写次数
```

新增 `state` 值 `watching`；新增 `code` 值 `contested`、`external-release-failed`；瞬态事件写在 `detail`：`adopted`、`external-release`、`rewrite-failed`、`takeover-write-failed`、`takeover-readback-failed`。`Protocol` 仍为 `1`（只加字段与新枚举值，旧应用被版本闸门挡住，见 §6）。

`Request.Validate`：`adoptForeign` 只允许出现在 `enable`（其它 `op` 一律 `bad-request`）；`minPercent` 的范围由 `10..50` 放宽为 `5..50`（§4.6），其余校验不变。

### 3.2 函数级改动（助手侧）

| 文件:函数 | 改动 |
| --- | --- |
| `internal/lid/engine.go:Engine.Start` | 读到 journal 后按 `Writer` 分流：`ours`（含空、含「JSON 解析失败但 journal 非 nil」）→ 现有 `restore("ok")`；`foreign` → `Store.Remove()` 后观察一次，**一个字节都不写**。分流必须独立成立：安装脚本 `lid_scripts.go:lidInstallScript` 会 `bootout` 旧助手，那条路径不经过 `Engine.Shutdown`，所以不能把安全收尾挂在关机钩子上 |
| `internal/lid/engine.go:Engine.Handle`（`enable` 分支） | 现值 `!= 0` 时：`!r.AdoptForeign` → 仍回 `foreign-setting`；`r.AdoptForeign` → 调新增的 `Engine.watch(owner, r, now)`。`journal != nil` 的续期分支放宽为 `on-ours` **或** `watching` 都可续期：只改 `Deadline`，不动 `Started`、不动预算计数、不写值 |
| `internal/lid/engine.go:Engine.Handle`（`disable` 分支） | 所有结束路径统一走新增的 `Engine.end(code)` |
| `internal/lid/engine.go:Engine.refresh` | 拆成「读一次」+「按值判定」；判定逻辑与定时观察共用新增的 `Engine.observeValue(value int, now time.Time)`。`on-ours` 且值不是 1 的 `poll-readback-mismatch` 分支删除，改由 `observeValue` → `Engine.rewrite` 处理；连续读失败计数（`readFailureLimit`）只在 `Writer=="ours"` 时累加 |
| 新增 `Engine.observe(now)` | 只读观察：`if now.Sub(e.lastObserve) < ObserveInterval { return }`；`e.lastObserve = now`；`Read` 失败 → `e.observeValue(-1, now)`；成功 → `e.observeValue(value, now)` |
| 新增 `Engine.observeValue(value, now)` | 唯一的值分派点：无 journal（1 → `on-foreign`／0 → `off`，与今天一致）；`watching` + 0 → `Engine.takeover`；`watching` + 1 或读失败 → 什么都不做；`ours` + 1 → 清 `detail`，保持 `on-ours`；`ours` + 0 → `Engine.rewrite` 或按 §3.4 结束；`ours` + 读失败 → 沿用 `readFailureLimit` 计数 |
| `internal/lid/engine.go:Engine.tick` | 截止时间、12 小时上限、租约、`restore-failed` 重试四条分支的 `restore(...)` 改成 `end(...)`；电量分支同样改为 `end("battery-low")`／`end("battery-unknown")`；在电量采样之前插入 `e.observe(now)`。`Tick()` 由 `internal/lid/transport.go:Server.Serve` 每秒调用一次，因此观察不依赖应用在线 |
| 新增 `Engine.watch(owner, r, now)` | 写 journal：`Started=now`、`Deadline=r.Deadline`、`MinPercent`（`r.MinPercent` 为 0 时写 20）、`Previous=0`、`Writer="foreign"`；再设 `owner`、`lastRequest=now`、`lastBattery=now`、`lastObserve=now`、`unknown=0`、`readFailures=0`、`rewrites/windowCount=0`、`state="watching"`、`code="ok"`、`detail=""`。保存失败 → `pmset-failed`（值未被改动，无遗留风险）。**必须写齐这些字段**：`effectiveDeadline` 用 `Started+HardLimit`，`Started` 为零值时上限落在公元 1 年，`tick` 第一次就会按 `max-duration` 结束；`lastRequest` 为零值时同一轮 `tick` 的 `Lease`（15 秒）也立刻成立 |
| 新增 `Engine.takeover(now)` | 预算检查（`allowRewrite`）→ 写 journal（`Writer="ours"`、`Started=now`，`Deadline`／`MinPercent` 不动，计入一次重写）→ 转调 `Engine.rewrite` 的同一条写入路径（`Set(1)` → 读回 1 → `on-ours`、`detail=adopted`）。失败 → 见下一行 |
| 新增 `Engine.rewrite(now)` | 只更新预算字段（`Rewrites++`、`WindowCount++`、`LastRewrite=now`，必要时重置 `WindowAt`）并落盘，**禁止改 `Started` 与 `Deadline`** → `Set(1)` → 读回 1 → `detail=external-release`（接手路径为 `adopted`）；写失败／读回不是 1 → `detail=rewrite-failed`、`state` 保持 `on-ours`、journal 保留、连续失败计数 +1，下一轮观察重试（仍受预算）。接手与重写共用这一条写入路径，唯一区别是接手前先把 `Writer` 改成 `ours`，因此失败时的收敛、计数与预算完全一致。两条路径**不能共用一个「更新 journal」函数**：那个函数一旦顺带写 `Started`／`Deadline`，外部每把值打回 0 一次就会把 12 小时上限清零 |
| 新增 `Engine.allowRewrite(now)` | 纯判定（§3.4），不改状态，逐条五条：① `now - LastRewrite ≥ RewriteGap`；② `now - WindowAt ≥ RewriteWindow` 时先把 `WindowAt=now`、`WindowCount=0`，否则要求 `WindowCount < RewriteWindowLimit`；③ `Rewrites < RewriteSessionLimit`；④ 连续写失败次数 `< RewriteFailLimit`；⑤ 调用方已确认本次读到 0 |
| 新增 `Engine.end(code)` | `writerOf() == "foreign"` → `dropWatch(code)`；否则 → 现有 `restore(code)` |
| 新增 `Engine.dropWatch(code)` | 删 journal、清 `owner`、`state="off"`、`code=code`、清 `detail` 与全部计数；**从不调用 `Sleep.Set`** |
| `internal/lid/engine.go:Engine.Disconnect`／`Shutdown` | 改为调用 `end("ok")`，行为随 `Writer` 分流。`Disconnect` 在读到 EOF 或读超时（`Lease`，15 秒）后由连接处理函数调用，它本身立刻收尾，不再等下一轮 `tick` |
| `internal/lid/protocol.go` | 常量、`Version`、`Request.AdoptForeign`、`Response.Adapter`／`Rewrites`、`Validate`（`adoptForeign` 只许 `enable`；`minPercent` 5..50） |

**观察会写值，`cubbix status` 不会。** 会写值的只读请求是**助手上的** `ping` 与 `hello`：它们经 `Engine.Handle` → `Engine.tick` → `Engine.observe`（今天则是 `refresh`）落到同一条判定上，因此一次 `ping` 可能触发一次接手或重写——这与既有行为一致（`refresh` 本来就能触发 `restore`）。`cubbix status` 走的是应用侧的 `cli_server.go:cliState`，只读 `lidSnapshot`，**不调用助手**（006 要求 `status` 不产生探测），实现时不要给 `cliState` 加 `ping`。`tick` 与 `refresh` 共用同一个 `lastObserve`，同一次 `ping` 只做一次观察、只计一次预算。

### 3.2b 函数级改动（应用侧）

| 文件:函数 | 改动 |
| --- | --- |
| `lid_controller.go:enable` | 「想要合盖」的四条路径（用户点开关、CLI、URL、重挂）**一律**带 `AdoptForeign: true`；只有已经在 `watching`／`on-ours` 上的续期可以不送（续期只改 `Deadline`）。理由：从 `on-foreign` 点下的第一次 `enable` 当时还不是 `watching`，送 `false` 会被助手继续回 `foreign-setting`，A 就永远进不去 |
| `lid_controller.go:enable`（外部值预检） | 现值 1 且 `s.state != lidOn` 时不再直接回 `LidForeign`。`c.connection == nil` 有两种含义：本次启动还没拨过号，或助手真的连不上。先尝试一次 `connect()`；连上了就把这次 `enable` 交给助手（它会回 `watching`），连不上仍按 `readStale` + `LidForeign` 返回，**不弹框、不安装**——没有助手就没有观察者，不能登记意图。修订号不符时 `connect` 会留下 `connection` 并返回 `errLidHelperUpdate`，这种组合不算「连不上」，继续走升级路径 |
| `lid_controller.go:enable`（成功条件） | 助手回来之后：`r.OK && (r.State == "on-ours" \|\| r.State == "watching")` 才算成功；`on-ours` 仍要求 `r.Value == 1`（续期宽限 `grace` 那条保留），`watching` 不要求读回 1（值本来就是别人的）。**`watching` 成功时不调用 `writeMarker`，并删除可能残留的标记**；`writeMarker` 只在确认我方读回 1 之后调用。这样助手随后不在时，`readStale` + `canForce` 不会给出「强制恢复睡眠」，更不会用管理员脚本把别人的 1 写成 0 |
| `lid_controller.go:enable`（升级路径） | 助手修订号不符时 `connect` 已留下 `connection` 并返回 `errLidHelperUpdate`；随后 `needsInstall` 分支会先 `stopLocked`。外部持有 1、没有我方 journal 时 `disable` 回 `on-foreign`、值仍是 1，`stopLocked` 返回 `LidForeign`，安装就被这一句挡掉了。改为：这次 `disable` 的结果是 `on-foreign`（`r.State == "on-foreign"` 且没有我方标记）时，**跳过「必须读回 0」**，继续走用户主动点击（`authorize == true`）的那一次 `Register`；`c.connection == nil` 时维持现有的提前 `LidForeign`，不弹框 |
| `lid_controller.go:apply` | 新增 `case "watching"`：`state = lidOn`、`watching = true`、`reason = ""`、`removeMarker()`；`case "on-ours"` 时把 `watching` 置回 false。`code` 新增两条映射：`contested` → `LidContested`、`external-release-failed` → `LidExternalReleaseFailed` |
| `lid_controller.go:stopLocked` | `watching` 时结束条件放宽：`r.OK && r.State == "off"` 即成功（此时 `value` 仍是 1，是别人的 1），**不要求 `value == 0`**，也不删标记（本来没有）；其余分支不变 |
| `lid_controller.go:lost` | 仅在 `watching` 会话断连时置 `snapshotValue.rearmPending = true` 并记录起始时刻；`online = false` 等既有行为不变。我方已经写成 1 的会话仍按 004 的既有规则收敛，不保留无人看管的意图 |
| `lid_app.go:finishLidPoll` | 分两轮处理。**断连那一轮**：`rearmPending` 为真且助手不在线时，先 `return`，**不执行** `s.state != lidOn` 时 `setSessionLid(false)` 的那条清理，保留 `Session.Lid`；超过 `4 × Lease = 60` 秒仍未重连则放弃并回到既有清理。**重连那一轮**：`rearmPending` 为真、会话活跃且 `Session.Lid` 为真、助手在线且报 `on-foreign` → 先调 `enableLid(session.End, false)`（`authorize=false`，不写值），紧接着清 `rearmPending` 并 `return`（完成回调会再进一次 `finishLidPoll`）；重连后是别的状态（`off`、需要授权等）则清掉 `rearmPending` 后按既有规则清理。顺序上重挂写在清理之前：助手重启后 `Engine.Start` 删掉 `writer=foreign` 的 journal，界面变成 `on-foreign`（不是 `lidOn`），若先跑 `setSessionLid(false)`，重挂就再也看不到 `Session.Lid`。`contested`／`external-release-failed` 之后不再因为助手重连而发 `enable`：那时值已确认是 0，助手报 `off`，重挂条件不成立；预算也不会被重挂重新装满 |

### 3.3 关键顺序（硬约束）

观察 → 接手的顺序（`watching` → `on-ours`）：

```
1. 读到值 0（此时我方没有任何写入）
2. 预算允许
3. journal 原地改写为 writer=ours、started=now（deadline、minPercent 不动），并落盘
4. pmset -a disablesleep 1
5. 读回，必须是 1；不是 1 或读失败 → 保留 journal（我方已声明所有权），下一轮由
   observe/restore 收敛；绝不在「声明了 ownership 却没写成功」时删 journal
6. state=on-ours, detail=adopted
```

重写的顺序（`on-ours` + 读到自己不是 1）：

```
1. 读到值 0
2. 预算允许 → 只把计数先落盘（started/deadline 不动）
3. pmset -a disablesleep 1 → 读回 1
4. 读回不是 1 或写失败 → detail=rewrite-failed，保持 on-ours 与 journal，等下一轮
5. 只有「本次 Read 明确返回 0」才允许以 contested / external-release-failed 收尾并删 journal
```

「先落盘再写」的理由与 004 §3.2 相同：崩溃点都必须能收敛到「值 0 且无 journal」或「值 1 且有 journal」，不允许出现「值 1 而无人负责」。

### 3.4 防抢参数

| 参数 | 取值 | 理由 |
| --- | --- | --- |
| 只读观察 | 1s | 搭在助手已有的 1 秒 `Tick` 上（`internal/lid/transport.go:Server.Serve` → `Engine.Tick` → `Engine.tick` → `Engine.observe`），不依赖应用在线。每次只做一次 `Sleep.Read`（一次 `pmset -g` 只读），不写值，因此**不会放大和外部工具的对写次数**：写入仍被下面的 10 秒间隔挡住。应用每 5 秒的 `ping` 也会触发同一路径，但共用 `lastObserve`，不额外读 |
| `RewriteGap` | 10s | 一次外部释放只花一次重写；两个观察不会连写两次，也给对方留出完成它自己那次写入的时间 |
| `RewriteWindow` / `RewriteWindowLimit` | 10 分钟 / 3 次 | 现场里外部写入的间隔是分钟到小时级（09:50、11:53、13:50、21:13）。10 分钟内被改回 3 次已不属于正常阶段切换，而是两个工具在抢 |
| `RewriteSessionLimit` | 12 次 | 12 小时硬上限内最多每小时一次，覆盖「慢速来回」这种不会触发窗口上限、但同样属于抢的形态 |
| `RewriteFailLimit` | 3 次 | 连续写不进去就是环境问题（权限、pmset 异常），继续试只会让状态解释不清；与 `readFailureLimit` 取同一个数、同一个理由（短暂波动不结束，持续失败就结束） |
| 超限后的行为 | 停止重写 → `contested`（预算耗尽）或 `external-release-failed`（连续写失败）→ **确认值是 0 之后**删 journal → 应用提示一次 → 普通常亮继续 | 自动重试循环正是要避免的故障形态；让人按一次比让程序无限试更便宜、也更可解释 |
| 预算重置 | 只由用户关掉再打开合盖开关（新 journal）重置。续期不清 `Rewrites`／`WindowCount`；`contested` 之后也不做时间上的自动恢复 | 静默自愈会把一次真实的冲突藏起来 |

### 3.5 明确不做

- 不因为「看到 1」就写 0：`watching`、`on-foreign` 都不写值。
- 不在 `watching` 时伪造「我方遗留」标记（`lid_controller.go:writeMarker` 只在我方确认 1 之后调用）。
- 不把「外部 1 + 用户想要」直接变成「我方 1」：改写成我方 1 等于替对方解除它的设置，违反「不改别人的设置」。
- 不在 URL／CLI 路径上引入任何授权或安装。
- 不引入第二套「谁想要合盖」的记录：意图仍然只有 `config.AwakeLid` 与会话 `Lid` 位。

## 4. B：插电时不触发低电量保护

### 4.1 现状定位

`internal/lid/engine.go:Engine.tick` 每 30s 采一次 `Power.Source()`，只要 `p <= journal.MinPercent` 就 `restore("battery-low")`，完全不看适配器——**今天在 AC 供电上也会恢复**。`Engine.Handle` 的 `enable` 分支只在 `kind == "battery" && p <= min` 时拒绝，所以 AC 上电量低仍能开。应用侧 `lid_controller.go:enable` 的预检更宽：种类不是 `ac`／`battery` 时，只要百分比可读且不是「电池且过低」就放行，而助手侧会回 `battery-low`——两侧今天就不完全一致。

`internal/lid/power_darwin.go:SystemPower.Source` 只读内置电池的 `Power Source State`（`AC Power`／`Battery Power`）与 `Current Capacity`／`Max Capacity`（`IOPSKeys.h` 的 `kIOPSPowerSourceStateKey`、`kIOPSCurrentCapacityKey`、`kIOPSMaxCapacityKey`）。

也就是说：判断依据是「谁在供电」，不是「适配器在不在」。插着电由外部工具强制放电时「谁在供电」就是电池，于是保护误触发——这正是需要修的地方，但修法受 §0 的已证实限制（那一段公开接口答不了）。

### 4.3 判定规则（v1，唯一的公式）

```
Adapter 的三态（internal/lid/power.go:AdapterState）：
  IOPSCopyExternalPowerAdapterDetails() 返回非 NULL          → AdapterAttached
  返回 NULL（IOPowerSources.h：没接或出错都返回 NULL）        → AdapterAbsent
  符号绑定失败／调用不可用                                    → AdapterUnknown

plugged := (Kind == "ac") || (Adapter == AdapterAttached)
保护触发 := !plugged && Percent <= minPercent
读不到 Percent  → 沿用 004 的 battery-unknown 计数（不变）
```

规则说明（评审「必须改」9 收口的地方）：

- **NULL 一律收成 `AdapterAbsent`**，不是 `Unknown`：`IOPowerSources.h` 写明没接或出错都返回 NULL，而 NULL 的两种含义都要求「按未插电对待，保护保留」，所以不必分出第三态。`AdapterUnknown` 只留给符号绑定失败／调用不可用，两者在判定上等价（都不是插电）。
- **「矛盾」不再是一种情况，而是上述公式的直接结果**：种类不是 `ac`，且详情为 NULL 或绑定失败 → 不插电；种类是 `ac`，或详情非 NULL → 插电。没有第二条判断，也没有第三个分支。
- **不使用任何私有键**：`FedDetails`、`PowerDistribution`、`AppleSmartBattery` 的 `AdapterDetails` 缓存、USB-C `CC` 全部不进入 v1 判定（§0 结论 2、3）。
- 已证实的限制：插着电强制放电时 `Kind` 是 `battery`、详情是 NULL → `plugged=false` → 保护照旧触发。这是有意选择，缓解手段是 5% 阈值档（§4.6），不是私有信号。

### 4.5 放在哪一侧、要不要升修订号

**推荐：判定放助手侧，应用侧只做预检与展示，助手修订号 `4`→`5`。**

- 保护必须在助手：合盖后应用看不到界面，也不保证自己在跑（004 §5.5 已为低电量下限写过同样的理由），电量采样本来就在 `Engine.tick`。
- 应用侧仍保留同一套预检（同一份 `Plugged`）：开启前就告诉用户「电量太低」，而不是先开 1 再被助手立刻恢复（004 §5.5 的既有行为）。
- 修订号必须升：004「合盖开启失败修正（2026-11-04）」写明「以后改变助手行为必须同步递增修订号」。本次改变了 `enable` 的受理条件、`tick` 的恢复条件、下限取值域，属于行为变更。
- 升级代价：应用与助手修订号不等时，`lid_controller.go:connect` 已有 `errLidHelperUpdate` 闸门，界面显示 `LidHelperUpdate`，用户下一次主动点开关时走一次授权安装（004 §3.6，且需 §3.2b 那条 `stopLocked` 修正）。轮询、CLI、URL 都不会自动安装。

- `LidForeign`（「系统里已有别的工具关闭了合盖睡眠，Cubbix 不会覆盖」）**保留并继续只用于「用户没表态」的情形**；用户表态之后换成 `LidWatching`。两条不能混用：一条是「我不动别人的」，一条是「我记着，等它放手」。

- 不新增任何要求用户复制命令的文案（沿用 004 第 2 版的决定）。

`internal/cli/protocol.go:LidState` 新增两个字段：


`state.awake.lid.state` 新增枚举值 `watching`。它的来源是 `cli_server.go:cliState` 的显式覆盖（`s.state == lidOn && snapshot.watching`），不是 `lidStateName` 的新分支——`lidStateName` 只把 `lidState` 映射成名字，没有 `watching` 可判。

| --- | --- | --- |

## 6. 兼容与升级

| 项 | 处理 |
| --- | --- |
| 旧 journal（无 `writer` 字段） | 一律视为 `writer=ours`。旧版助手只在「自己要写 1」之后才写 journal（`engine.go:Handle` 的 `enable` 分支先 `Store.Save` 再 `Set(1)`），所以空值只能是旧的我方记录。**不能**把缺省值当成 `foreign`——那会让一次真实的我方遗留失去恢复者。注意 `internal/lid/journal.go:FileJournal.Load` 在 JSON 解析失败时仍返回非 nil 的 journal（带 error），今天 `Engine.Start` 会把它当我方责任并 `restore`；分流时不要因为 `err != nil` 就跳过「空 `Writer` 按 ours」的判断 |
| 旧配置里的下限 | 10／20／30 原样有效，不迁移；新增的 5 需要用户主动选（§4.6） |
| IPC protocol | `Protocol` 保持 `1`。只新增字段与新枚举值；`state="watching"` 只会出现在修订 5 的助手上，而修订号不等的组合会被 `lid_controller.go:connect` 的 `errLidHelperUpdate` 挡住（应用侧要求 `r.Helper == lid.Version`），不存在「旧应用解析新状态」的路径 |
| 助手修订号 | `internal/lid/protocol.go:Version` `"4"`→`"5"`。理由见 §4.5 |
| 升级时是否再授权一次 | **要一次**，且只在用户下一次主动点合盖开关／命令面板动作时发生（004 §3.6 的既有流程：恢复 → 授权安装 → 同版 hello）。轮询、CLI、URL、启动都不安装、不授权。外部工具正持有 1 时的这一次安装依赖 §3.2b 的 `stopLocked` 修正：否则 `disable` 回 `on-foreign`、`stopLocked` 返回 `LidForeign`，授权框永远等不到 |
| 首次安装恰逢外部持有 1 | `c.connection == nil`，走既有的提前 `LidForeign`（不弹框、不安装），开关保持可点但本次无法进入 `watching`；等外部释放后可正常安装并开启。这是「没有助手就没有观察者」的直接后果，不做例外 |
| 升级顺序 | 应用与助手同一版本发布：新应用 + 旧助手 = `LidHelperUpdate`（可用性不受影响，只是合盖保持需要更新）；旧应用 + 新助手 = 同样被版本闸门挡住，行为不会「半新半旧」 |
| `config.AwakeLid` | 语义不变（下次会话是否带合盖）。`watching` 时用户表态成功就记 true；`contested`／`external-release-failed` 只结束本次会话，不清偏好 |
| 标记文件 `lid-restore-required` | 只在我方确认写 1 之后创建；`watching` 不创建，进入 `watching` 时若存在则删除（意味着过去的我方遗留已被处理）。`canForce` 的判定不变，因此 `watching` 期间永远不会出现「强制恢复睡眠」 |
| 降级路径 | 助手不在线时的 `readStale`（`lid_controller.go:readStale`）行为不变：读到 1 且无标记 → 只提示、不提供按钮。这一条正好与 A 相容：没有助手就没有观察者，不能登记意图 |
| 006 的成功判定 | 以 006「合盖异步结果（2026-11-04 修正）」那段为准（`applyCLIAsync` 等 `completeLid` 才构造响应）。本设计把成功的定义扩为「读回 1」**或**「助手已受理 `watching`」；`watching` 时**不写标记**（未写值即无遗留），其余（会话仍有效、失败退出 4、不授权）不变。006 §3.6 的异步表里「成功响应可能是 `lid.state = "enabling"`」那句与它矛盾，回改时以等待完成的那条为准，删掉这句 |
| 需要回改的既有规格 | 004 §3.7（应用状态机与 `on-foreign` 的描述）、§5.2 第 11、12 行（电量保护改为插电不触发）、§5.3 启动表（`foreign` journal 不恢复）、§5.5（适配器判定与 5% 档、助手 `minPercent` 范围 5..50）、§8.1（新增四个键、`LidForeign` 只用于未表态情形）、§8.4（新增待决项）；006「合盖异步结果（2026-11-04 修正）」（成功判定）与 §3.6 异步表（删掉 `enabling` 那句）、§4.5 的 `lid.state` 枚举与 `batteryMin` 取值说明。两份规格的其余条款不变，冲突时以 009 为准 |

## 8. 待维护者决定（已定的标「已定」）

| # | 问题 | 结论／推荐 |
| --- | --- | --- |
| 1 | 放电不可识别时怎么办（本轮已证实不可识别） | **已定：接受现状**。放电期间按「未插电」保留保护，缓解手段是 5% 阈值档（§4.6），不为此引入 USB-C 私有类、SMC 键或私有电源键（§0 结论 3）。若 §7.3 第 2 项证明 5% 仍不够，再另开一版讨论私有信号，并接受随系统更新失效的风险 |
| 2 | 防抢数值（1s / 10s / 3 次/10min / 12 次/租约 / 连续失败 3 次） | **已定：按 §3.4 采用**。现场写入是小时级，完整校准大约两次「写回 1」，到不了窗口或租约上限；更密的对写会在窗口内第 4 次停住并 `contested`，不会无限写。续期不清预算，`contested` 之后只由用户重开一次新 journal 重置预算。若真实节奏更密（例如某工具每秒写一次），把 `RewriteWindowLimit` 降到 1 就退化成「一次机会 + 人工」，不需要改结构 |
| 3 | 预算耗尽后是否需要自动恢复 | **已定：不自动**。等用户重开一次合盖开关（新租约）。自动恢复会把真实冲突藏起来 |
| 4 | 助手重启后是否自动重挂观察 | **已定：自动重挂一次**（每次重连一次）。丢掉登记会让用户以为仍在保持；`contested` 之后不重挂。不自动重开的是「我方已写成 1 的会话」（004 §5.3 的既有规则不变） |
| 5 | 接手/重写要不要发系统通知 | **已定：不发**。只在状态行与 tooltip 体现；异常的两条（`contested`、`external-release-failed`）各发一次 |
| 6 | 接手后 12 小时上限从哪算 | **已定：从接手时刻起算**（`Started` 重置；重写不重置）。此前没有 1，若沿用外部写入时间，用户会得到一个被外部工具「吃掉」的时限 |
| 7 | `watching` 能否由 URL/CLI 触发 | **已定：可以，但没有新的放宽**。CLI 仍要求显式时长（006 §3.6），URL 仍要求 `minutes` 1..480；`palette.go:awakeLidGate` 与 `awake_app.go:startAwake`（`authorize = lidAuthorize && !lidURL`）保证这两条路径不调用 `Register`，最坏后果只是一次「接管登记」 |
| 8 | 是否接受助手修订号 `4`→`5` 带来的再一次授权 | **已定：接受**。004 已定的规则（改行为必升修订号），且只影响下一次主动点开关；外部持有 1 时能否走到授权框取决于 §3.2b 的 `stopLocked` 修正 |
| 9 | `watching` 时猫标是否要第三态图标 | **已定：不要**。004 §8.2 已把第三态留给品牌资产；本次用第二行文字，等资产到位再说 |
| 10 | 5% 档是否够用（唯一仍需回答的实际问题） | 推荐先按 §7.3 第 2 项实测一次完整校准。若 5% 仍被打断（例如放电目标被设成 5% 以下），再决定是放宽到 1%（同时要放开 `Request.Validate` 与设置页第五段），还是在放电段引入私有信号——两者都留到那一轮再定 |

### 附 A：`adapter-probe`（只读，供 §7.3 第 1 项使用）

编译：`clang -framework IOKit -framework CoreFoundation -o adapter-probe adapter-probe.c`。它只调用两个文档化的 IOPS 函数并打印结果，不写任何设置、不读任何用户数据。

```c
#include <stdio.h>
#include <stdlib.h>
#include <CoreFoundation/CoreFoundation.h>
#include <IOKit/ps/IOPowerSources.h>
#include <IOKit/ps/IOPSKeys.h>

int main(void) {
    CFTypeRef snapshot = IOPSCopyPowerSourcesInfo();          // 调用方持有，需 release
    CFStringRef kind = IOPSGetProvidingPowerSourceType(snapshot);
    char buf[128] = "<nil>";
    if (kind) CFStringGetCString(kind, buf, sizeof buf, kCFStringEncodingUTF8);
    printf("ProvidingPowerSourceType = %s\n", buf);

    CFDictionaryRef adapter = IOPSCopyExternalPowerAdapterDetails();
    if (!adapter) {
        printf("ExternalPowerAdapterDetails = <NULL>\n");
    } else {
        CFStringRef text = CFCopyDescription(adapter);
        char *out = NULL;
        CFIndex size = CFStringGetMaximumSizeForEncoding(CFStringGetLength(text),
                                                         kCFStringEncodingUTF8) + 1;
        out = malloc(size);
        if (out && CFStringGetCString(text, out, size, kCFStringEncodingUTF8)) {
            printf("ExternalPowerAdapterDetails = %s\n", out);
        }
        free(out);
        CFRelease(text);
        CFRelease(adapter);
    }
    if (snapshot) CFRelease(snapshot);
    return 0;
}
```

判读：`ExternalPowerAdapterDetails` 非 NULL 就是「读到了适配器」；NULL 同时覆盖「没接」与「出错」两种情况，因此实现里两者都按未插电处理，必须与同一时刻的 `ProvidingPowerSourceType` 一起看（§4.3）。
