## 结论摘要

| 项 | 结论 |
| --- | --- |
| 实现手段 | `pmset -a disablesleep 1/0`，需要 root，是系统设置，进程退出不自动复原 |
| 执行者 | 独立的特权助手（root LaunchDaemon），由 launchd 托管 |
| 系统要求 | 只在 **macOS 13+** 提供；macOS 12 上整行显示不支持（`LidUnsupported`）。**不改 `mygo.json`** 的最低系统版本（§2.1） |
| 与现有常亮的关系 | **附加开关**，不是第三种模式；`caffeinate` 会话与 `disablesleep` 会话同生命周期、同截止时间 |
| 供电策略 | 接电源与电池都能开启；会话中拔电**不**恢复；电量 ≤ 下限（默认 20%，可调 10/20/30%）或连续读不到可信电量时由**助手**强制恢复（§5.5） |
| 时长上限 | **助手强制 12 小时**：所有会话（含不限时、跟随进程）的 `disablesleep` 最多维持 12 小时，到点由助手自己恢复，界面说明一次（§3.2）。这是已定项，不再待决定 |
| 安装层 | **只用 T3（legacy `/Library/LaunchDaemons` 安装层）**：安装时那一次管理员密码**就是**授权，之后不需要在系统设置再放行一次（§2.2、§4.4）。`lidService` 接口保留，将来 MyGo 若支持 bundle 内 LaunchDaemon，可只替换安装层 |
| IPC | `/var/run` 下的 Unix domain socket，换行分隔 JSON；**必须**用 audit token + SecCode 校验对端是同 Team ID 的 Cubbix |
| 恢复触发 | 到期、用户停止、正常退出、连接断开（含强杀）、心跳过期、电量低于下限、电量读不到（连续 3 次采样）、助手重启、开机 |
| 最坏情况 | 助手起不来（被关掉、被卸载、副本被删、安装损坏）时，`disablesleep=1` 可能一直留着——没有任何进程会自己恢复它。应用启动时用只读 `pmset -g` 告警，并提供一个**不依赖助手进程**的「强制恢复睡眠」入口（异常态才出现，一次管理员授权，§3.8） |
| 关键阻塞 | **`mygo build` 目前产不出 `Contents/Library/LaunchDaemons/`**（§4.3），所以只用 §4.4 的 T3 安装层；SMAppService 标准布局（T1）不再推进 |
| 未证实项 | 实体合盖、拔电、强杀、重启、真实助手、授权弹窗全部只列在维护者实测清单（§7.3）里，自动化测试一律打桩；另有 11 项「需实测」集中在 §4.6 |

## 实现核对（2026-11-03）

实现与验证结果见 [维护者验收指南](../lid-keep-awake.md)。安全要求保持：复制后校验副本、签名失败拒绝、先 journal 后写设置、读回 0 才删除、无 journal 不覆盖、URL 不授权。以下是实现时发现的事实修正与保守处理：

- **含按钮的提示必须使用可交互浮层**。MyGo v0.6.2 的 `ui/tooltip.go` 明确让 tooltip 指针穿透，离开锚点即关闭，不能承载可点击按钮。恢复／允许按钮改为点击状态行 alert 打开的 `ui.PopoverBase`，支持键盘、Esc、点击外部关闭；静态说明仍用 tooltip。本文其它章节中“tooltip 里的按钮”均以此修正为准，按钮显隐条件不变。
- **Go 助手的初始 identifier 实测为 `a.out`**。`codesign` 重签会保留它；不能仅凭文件名推断。`build-helper.sh` 对生成的资源显式以 ad-hoc 签名固定 `cubbix-helper`，随后 MyGo 再施加最终嵌套签名。安装 requirement 不放宽；包内签名与 identifier 的构建断言已通过。
- MyGo 有**编译前** `buildCommand`，适合构建助手；没有 bundle 建立后、整体签名前插入任意路径的钩子，因此仍只实现 T3。资源用默认 `resources/darwin-<arch>/bin/` 平台目录，不重复列入额外 `resources`（否则会重复复制）。
- 电量直接取 IOKit 内置电池的 `Current Capacity / Max Capacity × 100`；不依赖未文档化的 `pmset -g batt` 百分比格式，也不在缺失 Max 时降级。AC 开启也必须读到可信电量（可信读数不受开启下限限制）；会话采样低于下限或连续三次未知都会恢复。
- 命令动作列表中的合盖勾选先暂存；**确认 1 后才持久化** `AwakeLid`。这解决“动作列表立即改记忆”与 §5.1“确认后才写记忆”的冲突，失败不留下假的记忆。合盖开启失败仍按 §5.3 保留普通常亮，因此 `AwakeSession` 可更新为 `Lid=false` 的普通会话；不能将 §7.1 的“不变”解释为保存一条假的 `Lid=true` 会话。快捷键只使用已保存偏好，不能发起安装；只有卡片／命令面板的主动操作可授权。
- §7.3 实际有 **23 项**（1–20 加 1b、6b、6c）。它们全部保留为需维护者实测；自动化、截图和 ad-hoc 实验不替代实测。

## 合盖开启失败修正（2026-11-04）

- **已定位的分支**：`FileJournal.Save` 创建目录后校验 `root:wheel`。macOS 新目录会继承父目录的组；若得到 `root:admin`、权限仍为 `0700`，旧实现会拒绝保存 journal，助手回 `pmset-failed`，应用 `enable` 的助手响应校验分支再回 `LidEnableFailed`。这条路径发生在写 `disablesleep` 之前，因此值仍为 0。修正后，助手用不跟随符号链接的文件描述符检查属主、类型、权限；仅对已确认 root 独占的目录／文件用 `fchown` 将继承组修正为 wheel，已有安全目录无需手工删除或改权限。错误属主、错误权限、符号链接与文件硬链接仍被拒绝。
- **更新识别**：`helper` 是实现修订号，独立于 IPC `protocol` 和应用版本；旧实现一直回 `"1"`，0.5.2 与 0.5.3 的助手源代码相同，单凭二进制不同不能认定不兼容。首次修正的助手修订号为 `"2"`；安装可靠性与日志降噪修订为 `"3"`，应用版本不变。以后改变助手行为必须同步递增修订号。启动／轮询发现不匹配只显示既有 `LidHelperUpdate`（中英资源已有）；用户下一次主动点合盖开关时，先恢复旧租约并确认 0，再走一次授权更新，最后用同版 hello 确认就绪。CLI、URL、快捷键始终不授权，版本不匹配返回 `LidHelperUpdate`。
- **读回**：`pmset -a disablesleep 1` 成功不代表开启成功，仍须读回 1；不为 1 或读取失败时撤销，读回 0 后才删 journal。`SleepDisabled` 的空格／制表符解析兼容当前输出；测试覆盖 0、1、缺失、非法值和多余字段，不放宽为解析 `sleep` 行。
- **诊断**：助手日志写到 `HelperLogPath`（`/Library/Logs/Cubbix/helper.log`），root:wheel，文件 `0644`；单文件最多 1 MiB，保留当前与 `.1` 两份。成功的 enable／disable、restore 与写入保留操作日志；其余请求（包括非 ok 回应）仅在 ok、code、state、value 或 detail 变化时记录。pmset 读取只记首次、结果码或值变化及恢复，连续相同错误不重复记录。无 journal 时偶发读取失败仅影响当前回应；下一次成功读取后清除该观察错误，恢复实际状态与原有会话终止原因。请求日志仍只含固定 op、ok、code、state、value、detail。不写请求 ID、client、reason、文件路径、命令输出或进程信息。日志不可用时回退 stderr，不能阻止 journal 恢复。
- **失败保留**：`cubbix status --json` 的 `state.awake.lid` 增加 `lastCode`、`helperVersion`、`hello`、`helperCode`、`helperState`、`helperValue`、`helperDetail`，详见 006。开启失败的助手响应保留到下一次成功开启，不被后续 ping 擦掉。`pmset-read-failed`、`helper-pmset-failed`／其它助手错误、`helper-invalid-enable-response`、`marker-write-failed`、`lid-busy` 分别对应原来共用 `LidEnableFailed` 的分支。助手 `detail` 区分 journal 保存、写 1、读回、续租读回等失败。
- **升级后操作**：更新应用后在卡片中点一次合盖开关；预期显示“助手需要更新”并申请一次管理员授权（系统可能缓存凭据）。新助手自动修正可信 journal 的继承组，无需手动运行系统命令。自动化使用临时目录、假属主／组与假电源接口；真实授权、已安装助手替换、真实电源写入及实体合盖仍由维护者验收。

## 读取容忍与合盖降级修正（2026-11-05）

- 助手实现修订号由 `3` 递增为 `4`，IPC protocol 与应用版本不变。旧助手按上述升级流程，在用户下一次主动操作时申请一次管理员授权；轮询、CLI、URL 不自动授权。
- `pmset -g` 单次读取上限为 5 秒，IPC 请求上限为 14 秒，覆盖开启前检查与写后读回并留出余量。已连接助手的健康轮询直接使用助手读数，不再先做一次应用侧本地读取。有效请求处理完成时更新心跳，避免将正在处理请求的耗时误算为连接空闲。
- 已有合盖租约的观察读取与续期共用连续失败计数：前两次超时、命令失败、解析失败或未知值回 `on-ours`／`pmset-failed`／未知 value，保留 journal 和当前设置，不写 0；成功读取重置计数。连续第三次失败才恢复合盖，回 `pmset-failed`；恢复失败则保留 journal、回 `restore-failed` 并按原退避重试。已确认读回 0 则立即收敛，不把确知关闭当成未知。首次开启仍必须严格读回 1；恢复仍必须严格读回 0。
- 应用收到未知 value（省略或 -1）和一次 `pmset-failed` 时保留此前确认的合盖状态及恢复标记，不将未知解释为关闭。确认的合盖终止、断连、保护恢复或恢复失败只把当前会话降级为 `Lid=false`，保存普通常亮会话；原 caffeinate 进程、模式、截止时间和跟随目标保持不变，合盖偏好保留。恢复责任未确认解除前仍保留标记与异常提示。用户停止、常亮自身到期、跟随目标结束或退出才停止 caffeinate。

## 009 回改（合盖保持与外部工具共存）

009 已合并并取代本文里与之冲突的条款；以下改动以实现为准，其余条款不变。

- **助手修订号**：`4` → `5`（`internal/lid/protocol.go` 的 `Version`）。改变了 `enable` 的受理条件、`tick` 的恢复条件与 `minPercent` 取值域，按本文「合盖开启失败修正」的既定规则必须升号；升级后下一次由用户主动点合盖开关时再授权一次。
- **§3.7 应用状态机**：`on-foreign` 不再是「不可点」的终止状态。用户表态后助手新增 `state=watching`，应用把它映射成 `lidOn` + `lidSnapshot.watching`（第二行提示 `LidWatching`），开关保持可点；`LidForeign` 只用于用户还没表态的情形。新增 `contested`／`external-release-failed` 两条终止码（`LidContested`／`LidExternalReleaseFailed`）。
- **§5.2 第 11、12 行与 §5.5 供电规则**：低电量保护只在**没插电**时触发。唯一判据是 `Plugged(sample) = (kind == "ac") || (adapter == AdapterAttached)`，`AdapterAbsent`（详情 NULL，含出错）与 `AdapterUnknown`（符号绑定失败）都按未插电处理。接电源时低电量不恢复，但电量仍必须可信；`enable` 预检与助手采样共用同一条公式。下限由 `10／20／30` 扩为 `5／10／20／30`（默认仍 20，旧值不迁移），助手 `minPercent` 由 `10..50` 放宽为 `5..50`。插着电被外部工具强制放电时公开接口一律报未插电，这一档仍会触发保护，靠 5% 档缓解，不引入私有信号。
- **§5.3 启动表**：journal 新增 `writer` 字段。`writer=ours`（含旧版留空、以及损坏但仍非 nil 的 journal）启动时照旧写 0 → 读回 0 → 删 journal；`writer=foreign` 只删登记、**一个字节都不写**，随后观察一次。谁写的 1 谁负责恢复。
- **§8.1 文案**：新增 `LidWatching`、`R05LidHeld`、`LidContested`、`LidExternalReleaseFailed`、`LidBatteryFiveHint`，并改写 `LidBatteryHint`；异常通知白名单加入 `LidContested` 与 `LidExternalReleaseFailed`。
- **§8.4 待决定项**：009 §8 已定下防抢数值、预算耗尽不自动恢复、助手重启后自动重挂一次观察、接手不发通知、12 小时上限从接手时刻重算、CLI/URL 可进入 `watching` 但不授权、以及接受升修订号带来的一次授权。

## 1. 使用场景与用户路径

### 1.1 场景

维护者的原话是「盒盖保持任务继续的功能很重要，现在用起来总是忘记当前不支持盒盖工作」。因此本功能的第一目标不是「多一个开关」，而是**让「合盖是否安全」这件事在开启的那一刻就看得见**。

| 场景 | 诉求 | 现状 |
| --- | --- | --- |
| 合盖跑 Agent 任务（最常见） | 合上盖子，`codex`/`claude` 这类终端任务继续跑完 | 不合盖就等于中断，只能开着盖子离开 |
| 会议室/背包里短时编译 | 合盖带走，几分钟后回来继续 | 同上 |
| 桌面 Mac（无内置电池） | 无此需求 | 不应出现任何相关控件 |

### 1.2 入口与步数

合盖保持只有一个动作：**打开或关闭**。它跟随当前常亮会话，不单独计时。

| # | 入口 | 操作 | 步数 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | 卡片面板的合盖开关 | 点猫标 → 点合盖开关 | 2 | 未开启常亮时点它 = 用记忆设置开启常亮 + 打开合盖保持（§5.2 规则 4） |
| 2 | 先开常亮再开合盖 | 点猫标 → 点 `[1h]` → 点合盖开关 | 3 | 常见路径；第二次点击就是「别再忘了」的检查点 |
| 3 | 命令面板 | `⌥.` → 输入 `常亮 2h 合盖` → `↩` | 3 | 参数后缀 `合盖`／`lid`（§5.4） |
| 4 | 命令面板动作 | `⌥.` → `常亮 2h` → `⌘K` → 点「合盖也保持」→ 点「仅保持任务」 | 5 | 动作列表里两行都是勾选项，先勾合盖再执行主操作 |
| 5 | 全局快捷键 + 已记住的合盖 | `⌃⌥⌘K` | 1 | 快捷键不开合盖；只有 `config.AwakeLid` 为真时才连带开启（§5.2 规则 6） |
| 6 | URL scheme | `cubbix://awake?minutes=120&lid=1` | 1 | 给 Raycast／快捷指令用，限制见 §5.4 |

关闭路径：点合盖开关、点总开关（停止常亮）、按 `⌃⌥⌘K` 停止、`cubbix://awake/stop`、退出 Cubbix；以上任何一条都同时恢复 `disablesleep`（§5.3 的顺序要求）。

| 命令面板 | `awake.start` 的动作列表 Group 1 增加勾选项「合盖也保持」（`Checked` = `config.AwakeLid`），图标 `laptop`；行内 hint 不变（hint 只讲时长，见 003 §4.3） |
| 设置页 · 常亮格子 | 只加一行「低电量下限」（`LidBatteryLimit`），三段小控件 10%／20%／30%，默认 20%，写入 `config.AwakeLidBatteryMin`。这是唯一需要一个偏好的参数；合盖开关本身仍是会话开关，不跟着去设置页 |

卡片内的顺序固定为：标题行 + 总开关 → 模式分段器 → 时长药丸 → **合盖行** → 状态行。合盖行放在药丸之后、状态行之前：用户先决定「多久」，再决定「这次要不要合盖」，最后一行就是这件事的结果与提醒。高度：`menubar_panel.go` 的 `menubarPanelRows` 增加一个 `lid bool`（这一帧画不画合盖行），`awakeCardHeight` 现在的签名是 `(t tokenValues, status bool)`、**没有** `rows`——本轮给它加一个 `lid bool` 参数（`awakeCardHeight(t, rows.status, rows.lid)`），为真时补 `Space8 + SizeNavHeight`，并同步 `menubarPanelHeight` 与 `menubar_panel_test.go` 里写死的高度期望。

合盖行的显隐规则只有一条：`lidCapable()` 为真（有内置电池、打包运行、helper 二进制存在）就**一直画**；暂时不可开启（未授权、电量不高于下限、外部设置）时置灰可读，**不隐藏**——隐藏会让卡片高度跳动，也会让「为什么会睡」变得无从发现。只有 `lidCapable()` 为假（桌面 Mac、开发构建、未打包、helper 二进制缺失）时整行不画。**系统 < 13 属于「暂时不可开启」而不是「没这个功能」**：行照画、置灰、tooltip 为 `LidUnsupported`——「这台机器上不提供」必须说出来，不能默默消失（`lidCapable()` 只判断硬件与打包形态，不判断系统版本）。

异常态一律复用既有约定：`triangle-alert`（`ColorDanger`）+ tooltip 讲原因（`panelStatus` 已有这套代码），不用整句错误行。开启过程中在开关位置画 `loader-circle`（AGENTS「进行中 loader」）。

### 1.4 为什么这样能「不再忘记」

1. **开关常驻在卡片里**，不是藏在子菜单：想合盖之前点一次猫标就能看见它是开还是关。
2. **有会话未开合盖时，状态行多一个可点图标**：这是唯一会在用户「已经开了常亮」这个正确时机主动出现的东西。
3. **开启瞬间的状态行与 tooltip 带「合盖也保持」**：用户合盖前最后一次看菜单栏图标时，tooltip 里有答案。
4. **明确不做**：常亮未开启时推送「你还没开合盖保持」这类通知——那是骚扰，而且没有会话时合盖保持本来就没有意义。

### 1.5 明确做不到的事

**软件无法在合盖前提示。** 没有任何公开 API 在「用户即将合盖」时通知应用；`NSWorkspaceWillSleepNotification` 之类的通知发生在系统已经决定睡眠之后（本规格未使用它）。因此「忘记开」只能靠 §1.4 的事前显眼，不能靠事前弹窗。这一条必须写进验收说明，避免维护者以为是缺陷。

## 2. 首次授权流程

### 2.1 事实前提

| 事实 | 依据 |
| --- | --- |
| 需要 macOS 13+（`SMAppService` 自 13.0 起可用） | Apple `SMAppService` 文档的 availability：macOS 13.0+；本机 SDK 头文件 `SMAppService.h` 的 `API_AVAILABLE(macos(13.0))` |
| 应用必须是签名的，含 LaunchDaemon 的应用必须被公证 | `SMAppService.h` 类注释：「Apps that use SMAppService APIs must be code signed.」「Apps that contain LaunchDaemons must be notarized.」；Cubbix 走 Developer ID + 公证，见 `mygo.json` 的 `macos.signingIdentity`／`notarize` 与 ADR 004 |

| 用户可以在系统设置里关掉它 | 同上；状态变成 `SMAppServiceRequiresApproval` |
| 应用要引导用户去对应设置页 | `SMAppService.openSystemSettingsLoginItems()`，Apple 建议在提示用户后调用 |
| 应用更新了 plist 或可执行文件后必须重新注册 | `SMAppService.h` 类注释：「If an app updates either the plist or the executable for a LaunchAgent or LaunchDaemon, the SMAppService must be re-registered or it may not launch」 |
| 应用当前声明的最低系统是 12.0 | `mygo.json` 没有 `macos.minimumSystemVersion`，MyGo 默认 12.0（`mygo@v0.6.2/docs/configuration.md` 的 `macos` 表） |
| 本功能只在 macOS 13+ 提供 | T3 也离不开 13.0 的 API：`statusForLegacyPlist(at:)`（ObjC `statusForLegacyURL:`）与 `openSystemSettingsLoginItems` 都是 `API_AVAILABLE(macos(13.0))`（`SMAppService.h`）。**不改 `mygo.json`**：12 上其它功能照旧，只有合盖保持显示 `LidUnsupported`（§7.3 第 15 项） |
| legacy `/Library/LaunchDaemons` 不需要在系统设置里再放行一次 | `SMAppService.h` 类注释：「Legacy LaunchDaemons installed in /Library/LaunchDaemons will continue to be bootstrapped without explicit approval in System Settings since writing to /Library is protected with filesystem permissions」 |
| `registerAndReturnError:` 的失败码不能单独定状态 | 同一段 `SMAppService.h` 讨论写：「If the service is not approved by the user, this API will return error kSMErrorLaunchDeniedByUser」；而 `SMErrors.h` 对该常量只写「The user declined to allow the job to launch」，`status` 的讨论又写「If the user has denied execution, the return value will be SMAppServiceRequiresApproval」。两处措辞不一致，取消弹窗后的精确 `status` **需实测**（§4.6 第 10 项） |

### 2.2 授权状态机（应用侧）

`lidService` 抽象出五件事：`Status()`、`Register()`、`Unregister()`、`OpenSettings()`、`HelperPath()`（第 3 版的唯一实现是 §4.4 的 T3 安装层；保留接口只为将来 MyGo 若支持 bundle 内 LaunchDaemon 时可只替换安装层）。T3 的**首次授权只有一次**：

| 项 | T3（legacy 安装层） |
| --- | --- |
| 首次授权 | 安装脚本那一次管理员密码**就是**授权；`launchctl bootstrap` 之后 daemon 即可运行，不需要在系统设置里再放行一次（`SMAppService.h` 类注释） |
| `requiresApproval` 的含义 | **只表示事后被用户在系统设置里关掉**，不用于首次安装 |
| 放行按钮（`LidAllow` → `OpenSettings()`） | 只在事后被关掉时出现（`statusForLegacyPlist(at:)` 返回 `requiresApproval`） |
| 状态来源 | `statusForLegacyPlist(at:)`（`SMAppService.h` 的 `statusForLegacyURL:`，macOS 13+） |

| 状态 | 触发 | 界面 | 允许开启合盖保持 |
| --- | --- | --- | --- |
| `svcUnavailable` | `mygo.IsDev()` 为真、非打包运行、无内置电池、系统 < 13、helper 二进制缺失、或应用不在 `/Applications/Cubbix.app` | 合盖开关注灰，tooltip `LidUnsupported`／`LidDevBuild`（系统 < 13 与应用位置不对时行照画，其余情况不画，见 §1.3） | 否 |
| `svcNotRegistered` | 副本与 plist 都不存在 | 开关可点；点击先走安装（§4.4 脚本） | 否，需先安装 |
| `svcNotRunning` | 副本与 plist 存在，但 `statusForLegacyURL:` 为 0（notRegistered）或 3（notFound）；3 的含义由 `SMAppService.h` 枚举确认 | alert：`LidHelperNotRunning`；合盖开关可点，重试走一次授权安装 | 否，需确认助手可用 |
| `svcEnabling` | 安装中／等 daemon 起来 | 开关位置画 loader | 否 |
| `svcRequiresApproval` | `Status()` 为 `requiresApproval`（事后被用户在系统设置里关掉） | 开关回到关闭，状态行 alert：`LidAuthNeeded`，tooltip 里带「去系统设置允许」按钮（`LidAllow`），点击调 `OpenSettings()` | 否 |
| `svcDenied` | 安装脚本被取消（`osascript` 返回用户取消或 `kSMErrorLaunchDeniedByUser` 之类的错误），**且随后读到的 `Status()` 不是 `requiresApproval`** | alert：`LidDenied`；不再自动弹鉴权，必须用户再点开关 | 否 |
| `svcBroken` | `kSMErrorInvalidSignature`／`kSMErrorToolNotValid`／`kSMErrorInvalidPlist`／`kSMErrorJobPlistNotFound`，或副本签名校验失败（§4.4.1） | alert：`LidServiceBroken`，明确说明安装或启动失败，点合盖开关可授权重试 | 否 |
| `svcEnabled` | `Status()` 为 `enabled` 且 `hello` 握手成功 | 正常 | 是 |

要点：

- **安装／注册只在用户主动点击时发生**，不在启动、不在 URL 路径（§6.2 第 6 条）。启动时只读状态，不弹授权。
- **注册／安装返回后必须再读一次 `status`，不能只看错误码。** 服务尚未批准时 `registerAndReturnError:` 同样会返回 `kSMErrorLaunchDeniedByUser`（`SMAppService.h` 的讨论），而 `status` 此时是 `requiresApproval`，不是 `notRegistered`；只看错误码会把第一次注册画成「已取消授权」，`LidAllow` 就不出现了（`svcDenied` 与 `svcRequiresApproval` 就分错）。
- **实现不能照抄 `login.go`。** `mygo@v0.6.2/internal/darwin/login.go` 的 `SetOpenAtLogin` **只在 `registerAndReturnError:` 返回 true 之后**才读 `status`；返回 false 时直接 `return`，错误码有了、`status` 没读。这正好是 §2.2 要避免的形状：本功能的实现必须按上表先读状态码、再读 `status`（失败分支也一样），否则取消一次弹窗就会落到错误的 `svcDenied`／`svcRequiresApproval` 分支。可复用的是同一个 `mainAppService`／`status` 选择器与 objc 通道，不是它的控制流。
- 安装成功之后若 `Status()` 为 `requiresApproval`：那是用户事后在系统设置里把这个助手关掉了。界面不写整段说明，只给一个按钮（`R05LidAllow`）+ tooltip 两句话。
- 用户重新放行后**不需要重启 Cubbix**：应用每 5 秒（会话中）或每次展开面板时重读一次 `status`，变 `enabled` 就更新。
- 授权状态与被禁状态都要在**下一次开启时**重新读，不能缓存成「已授权」一辈子。

### 2.3 未授权/被拒/被关闭时的表现

| 场景 | 表现 |
| --- | --- |
| 未注册／未安装，用户点开关 | T3：一次管理员密码完成安装 + bootstrap，没有第二次放行；取消则按上面「错误码 + `status`」一起判定，落在 `svcDenied` 或 `svcRequiresApproval`，`disablesleep` 保持 0 |
| 已安装、事后被关掉，用户点开关 | 不弹鉴权，只亮 alert 与「去系统设置允许」按钮 |
| 已放行、正在运行时用户在系统设置关掉开关 | daemon 被 launchd 卸载 → socket 断开。应用侧：会话中每 5 秒 `status` 失败 → `lidHelperGone`，状态行 alert「合盖保持已中断」，tooltip 里出现「强制恢复睡眠」入口（§3.8）；`disablesleep` 的恢复由助手下一次启动时的启动恢复完成（§3.5），这也是 §6.3 的残余风险之一 |
| 被拒后再次点击 | 允许再次安装；管理员密码可能因系统缓存而不弹框（Apple TN2065 说明鉴权可能被缓存，见调研材料），因此只提示不改状态 |

## 3. 特权助手设计

### 3.1 职责边界（白名单）

助手只做五件事，多一件都不做：

1. 读 `disablesleep` 现值（`pmset -g` 的 `SleepDisabled` 行）。
2. 写 `disablesleep`（`pmset -a disablesleep 1|0`），并**读回确认**。
3. 读电源与电量（`pmset -g batt`，备选 IOKit；只读，不写任何电源设置），仅用于 §5.5 的低电量下限。
4. 维护会话日志（root 拥有的 journal），含截止时间、`minPercent` 与恢复目标值。
5. 在 §3.4 的触发条件下自行恢复。

明确不做：不读用户文件、不执行用户提供的命令或参数、不代理任意 `pmset` 参数、不接受路径、不联网、不监听 TCP、不写日志到用户可写的目录、不做 sleep/wake 之外的电源设置（`sleep`、`disksleep`、`hibernatemode` 一律不碰）。

助手由 launchd 的**系统域**启动，因此以 root 运行（launchd 语义；本机未安装真实 daemon 验证，见 §7.3）。它的会话状态只有一个 journal 文件与一条连接（低电量下限也不单独存储：它写在 journal 里，随会话消亡）；运行诊断另写有大小上限的 helper 日志，不参与租约判断。

调用 `pmset` 时参数是写死的常量：`exec.Command("/usr/bin/pmset", "-a", "disablesleep", value)`，不经 shell，不带任何来自 IPC 的字符串。

### 3.2 会话模型

一次「合盖保持」= 助手里的一个会话，它有六个要素：

| 要素 | 规则 |
| --- | --- |
| 租约 | 只在一条**活着的连接**上存在。应用每 5 秒发一次 `ping`；助手 15 秒收不到任何请求即判定租约过期 → 恢复 |
| 截止时间 | 由应用在 `enable` 里给出，等于当前常亮会话的 `End`；不限时／跟随进程时为空 |
| 助手侧硬上限 | 实际生效的恢复时刻 = `min(客户端 deadline, 会话开始 + 12h)`；客户端没给 deadline 时就是 `开始 + 12h`。到点由助手自己恢复，`status` 回 `code = max-duration`，应用按 §5.3 收敛并显示 `LidMaxDuration`。这一条**不是**待决定项：不限时与跟随进程都必须有助手侧兜底，否则用户忘了关就是一个永不睡的机器 |
| 电量下限 | `enable` 里的 `minPercent`（设置页可选 10／20／30，默认 20，助手接受 10..50）。助手每 30 秒自己采一次电源与电量（不看应用的采样，因为合盖后应用看不到界面、也没法保证自己还在跑）；电量 ≤ `minPercent` 就立即恢复，`code = battery-low`（§5.5）。**百分比一律按 `Current Capacity / Max Capacity × 100` 计算**（`IOPSKeys.h` 的 `kIOPSCurrentCapacityKey` 讨论：单位由电源自己指定，Apple 电源是百分比、其它电源可能是 mAh，「Clients may derive a percentage … by dividing “Current Capacity” by “Max Capacity”」；`kIOPSMaxCapacityKey` 的 Apple 电源取值通常是 100）。直接把 Current 当百分比会把下限绕开（mAh 值要么恒大于 100、要么与阈值无关）。**读不到可信电量（命令失败、缺 `Max Capacity`、`Max Capacity` 为 0、结果不在 0..100）连续 3 次采样（约 90 秒）就恢复**，`code = battery-unknown`；单次失败不恢复，但不设「一直继续」这一档——继续等于让下限对一个看不见的数失效 |
| 恢复目标值 | `previous` 字段，必须是 0（开启前读到的值）；非 0 一律拒绝，绝不覆盖别人的设置 |
| 日志（journal） | `/Library/Application Support/com.conteman.cubbix.helper/session.json`，目录 0700、文件 0600，root:wheel。内容：会话开始时间、客户端 `deadline`（可为空）、`minPercent`、`previous`（恢复目标值） |

journal 写入顺序是硬约束：

```
1. 读现值 → 必须是 0，否则回 foreign-setting 并退出
2. 读电源与电量（百分比按 `Current Capacity / Max Capacity × 100`）：在电池上且电量 ≤ minPercent，或读不到可信电量 → 回 battery-low 并退出（开启路径一律不写任何东西）
3. journal 落盘（tmp 文件 → fsync → rename → fsync 目录）
4. pmset -a disablesleep 1
5. 读回，必须为 1；否则回 pmset-failed，并撤销：pmset -a disablesleep 0 → 读回必须为 0
6. 只有「读回 0 成功」才删 journal；撤销本身失败（写失败或读回不是 0）就**保留 journal**，转 restore-failed 按 §3.4 重试
7. 回 ok（只在读回 1 成功之后）
```

恢复顺序同样固定：

```
1. pmset -a disablesleep 0
2. 读回，必须为 0
3. 只有读回 0 之后才删 journal（先 unlink，再 fsync 目录）
4. 失败则保留 journal，按 §3.4 重试
```

**「要不要恢复」只看 journal 在不在，不看现值是不是 0。** 崩溃点逐个对：

| 崩溃发生在 | 落盘状态 | 下次启动 |
| --- | --- | --- |
| journal 落盘之前 | 无 journal、值仍是 0 | 无事可做（报 `foreign-setting` 的那条路径也走这里） |
| journal 落盘之后、`pmset … 1` 之前 | journal 在、值仍是 0 | 有 journal 就恢复：写 0 → 读回 0 → 删 journal（幂等，**不是**「只删 journal」） |
| `pmset … 1` 之后、回 ok 之前 | journal 在、值是 1 | 恢复 0 → 读回 → 删 journal |
| 恢复途中、`pmset … 0` 之前 | journal 在、值仍是 1 | 同上：**值仍是 1，必须真的写一次 0**，不能因为「以为已经撤过」就只删 journal |
| `pmset … 0` 之后、读回 0 之前 | journal 在、值可能已是 0 | 写 0 → 读回 → 删 journal（覆盖式，不预设现值） |
| 读回 0 之后、删 journal 之前 | journal 在、值是 0 | 写 0 → 读回 0 → 删 journal；写 0 幂等，代价是两次 `pmset` |

所以「值 1 且没有 journal」**只可能由本功能自己造成一种情况**：journal 目录写不进去（安装损坏、磁盘满）。这种情况在开启第 3 步就会被拒绝（回 `pmset-failed`，从不写系统设置）。除此之外剩下的「值 1 且没有 journal」都**不属于本进程**（外部设置），照 `on-foreign` 只报告。

但还有一个必须写明的失效面：journal 在，**助手却不再起来**。用户可以在系统设置里关掉助手；副本可能被删；安装可能损坏。这时值可能停在 1，而应用读不到 journal（root `0700`），也无法自己判断是不是我方遗留。对策见 §3.8：应用用自己在用户目录记的标记文件判断，读 `pmset -g` 告警，并提供一条**不依赖助手进程**的管理员恢复入口。

### 3.3 IPC

**推荐 Unix domain socket，不推荐 XPC Mach service。** 理由与依据：

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| XPC Mach service | 系统级对端身份令牌（`xpc_connection_get_audit_token`）、launchd 按需唤醒 | 要在无 CGO 的 Go 里手写 `libxpc` 全流程：`xpc_connection_create_mach_service`、`dispatch_queue_create`、`xpc_connection_set_event_handler`（block）、`xpc_dictionary_*` 序列化。`objc.NewBlock` 与 `purego.NewCallback` 都存在（`purego@v0.11.1` 的 `objc/objc_block_darwin.go`、`syscall_unix.go` 的 `NewCallback`），MyGo 也已有 `dispatch_queue_create`／`dispatch_sync_f` 的绑定（`mygo@v0.6.2/internal/darwin/watch.go`），**但没有一行 XPC 代码可参考，且整条链无法在本机验证** | 不选 |
| Unix domain socket + `LOCAL_PEERTOKEN` | Go 标准库 `net.Listen("unix")`／`net.Dial("unix")` 承担全部传输；连接断开由 `read` 返回 0 直接感知，天然满足「客户端被强杀要恢复」；对端身份用 `getsockopt(SOL_LOCAL, LOCAL_PEERTOKEN)` 拿到 audit token（本机 SDK `sys/un.h` 定义 `LOCAL_PEERTOKEN 0x006`），再交给 SecCode 校验，效果与 XPC 的 audit token 等价；协议是纯文本，测试可以完全脱网跑 | 需要一次 `getsockopt` 的 syscall 与五个 Security 函数绑定 | **采用** |

XPC 的 Mach service 少一个「目录谁可写」的攻击面（launchd 自己按名字投递连接，socket 路径不经文件系统），但代价是整条 `libxpc` + block 链没有任何可参考的绑定、也无法在本机验证；而 socket 路径的权限面已经核清（下表）。**结论不变：留 socket，不改成 XPC，也不改成「只查 uid」。** 若 §4.6 第 1 项（audit token + SecCode）跑不通，退路只有一条：不上这个功能，不做降级。

传输细节：

| 项 | 规定 |
| --- | --- |
| 路径 | `/var/run/com.conteman.cubbix.helper.sock`（`/var/run` 是指向 `/private/var/run` 的符号链接） |
| 目录权限（已核对） | `/private/var/run` 是 `root:daemon`、`drwxrwxr-x`（0775）、**没有 sticky 位**。本机当前用户不在 `daemon` 组，普通用户不能在该目录里建文件；但**属于 `daemon` 组的进程可以删掉并抢绑 socket**。所以文件权限不能当作安全边界，反向校验（应用校验对端签名）必须保留 |
| 权限 | 0666。**故意**放开连接，安全由代码签名校验兜底，而不是靠文件权限（多用户机上没有共同组可用） |
| 创建顺序 | 助手先 `os.Remove` 残留 socket → `net.Listen` → **只有 `Listen` 成功之后才 `chmod 0666`**。顺序不能反：`Listen` 之前那个路径上可能还是别人的 inode（`daemon` 组可以抢绑），先 `chmod` 会改到别人的文件上 |
| 抢绑竞态 | `Remove` 与 `Listen` 之间对手若抢先 `bind` 进来，我们的 `Listen` 会拿到 `EADDRINUSE`：助手不重试、不删对方文件，直接按启动失败记一条日志（launchd 按 `ThrottleInterval` 10 秒再拉起）；应用侧连不上 socket，走 `lidHelperGone`。**同一个竞态反向也能被利用**，这就是应用侧必须校验对端签名（Team ID）而不是只看 uid 的原因 |
| 编码 | 换行分隔的 JSON，一行一条；单行上限 8 KiB，超过即断开；不使用 HTTP |
| 超时 | 连接建立 3s；单次读写 5s；空闲 15s 视为租约过期（§3.2） |
| 并发 | 同时只服务一条连接。新连接到来时：旧连接已断开或租约已过期 → 接管；否则 `enable` 回 `busy` |
| 校验失败的连接 | **不得挤掉已有会话**：对端校验在「这条连接是否接管会话」的判定之前完成，失败即关连接，既不顶掉旧连接，也不触发任何恢复或状态变化；失败原因不记对端信息（§6.2 第 1、2 条） |
| 常量 | 全部来自固定常量，不接受任何来自对端的路径、命令、`pmset` 参数 |

请求／响应（固定字段，未知字段忽略）：

```json
{"v":1,"id":"8f3c…","op":"hello","client":"cubbix/0.4.0"}
{"v":1,"id":"8f3c…","op":"status"}
{"v":1,"id":"8f3c…","op":"enable","deadline":"2026-11-03T12:30:00Z","minPercent":20}
{"v":1,"id":"8f3c…","op":"disable","reason":"user"}
{"v":1,"id":"8f3c…","op":"ping"}
```

```json
{"v":1,"id":"8f3c…","ok":true,"protocol":1,"helper":"0.4.0","state":"off",
 "value":0,"power":"ac","percent":80,"minPercent":20,"deadline":null,"code":""}
```

| 字段 | 取值 |
| --- | --- |
| `op` | 只接受 `hello`、`status`、`enable`、`disable`、`ping`，其余回 `bad-request` 并断开 |
| `state` | `off`、`on-ours`、`on-foreign`、`restoring`、`restore-failed` |
| `code` | `ok`、`foreign-setting`、`battery-low`、`battery-unknown`、`busy`、`max-duration`、`pmset-failed`、`restore-failed`、`bad-request`、`protocol-mismatch` |
| `value` | 读回的 `disablesleep`，0 或 1；读不到时为 `null` |
| `power` | `ac`、`battery`、`unknown` |
| `percent` | 助手算出的电量百分比，0..100（`Current Capacity / Max Capacity × 100`，见 §3.2）；读不到或值不可信时为 `null` |
| `minPercent` | 本次会话的低电量下限，10..50；与 `enable` 里的一致（回 `status` 时回带当前会话的值） |
| `deadline` | 已是 RFC3339（UTC）；`enable` 时允许 `null`（不限时） |
| `helper` | 助手实现修订号，用于 §3.6 的「助手需要更新」判断，独立于应用版本和 `protocol` |
| `detail` | 可选内部诊断：如 `journal-save-failed`、`enable-write-failed`、`enable-readback-failed`、`renew-readback-failed`、`preflight-read-failed`；不包含原始错误文本 |

`deadline` 校验：必须晚于 `now`，且不超过 `now + awakeMinutesMaximum 分钟`（`commands.go` 的 525659 分钟＝8760 小时 59 分，与 003 §4.1 的时长上限同一口径；越界即 `bad-request`）。这只是**协议上界**，不是实际运行时长度：助手一律再压一个 12 小时硬上限（§3.2），所以客户端给的 `deadline` 再远，实际恢复也不会晚于 `开始 + 12h`。不限时用 `null`，同样受 12 小时上限看管。`minPercent` 超出 10..50 回 `bad-request`；缺省按助手常量 20 处理（兼容旧客户端）。`disable` 的 `reason` 只用于日志与下次 `status` 的说明，不影响行为。

**对端校验（硬要求）**：

1. `getsockopt(fd, SOL_LOCAL /*0*/, LOCAL_PEERTOKEN /*0x006*/)` → 32 字节 `audit_token_t`（`sys/un.h` 本轮已核对：`SOL_LOCAL 0`、`LOCAL_PEERTOKEN 0x006`）。
2. 构造 attributes 字典：`SecCode.h` 声明这个参数的类型是 `CFDictionaryRef`，所以要 `CFDictionaryCreate`（键 `[kSecGuestAttributeAudit]`、值 `[CFData(32B)]`，key callbacks 用 `kCFTypeDictionaryKeyCallBacks`），不能只写一个 `{…}` 字面量。`kSecGuestAttributeAudit` 的取值是含 audit token 的 `CFData`——这条来自 Apple 文档；本机 SDK 头文件只声明符号，**需实测**（§4.6 第 11 项）。
3. `SecRequirementCreateWithString("anchor apple generic and certificate leaf[subject.OU] = \"P93GN4N3DC\" and identifier \"com.conteman.cubbix\"", 0, &req)`。
4. `SecCodeCheckValidity(guest, 0, req)`；非 `errSecSuccess` → 立刻断开，不读请求内容，不记 payload。
5. 校验放在 `Accept()` 之后、读第一行之前；**这一步先于「是否接管会话」的判定**，未通过校验的连接既不顶掉已有会话，也不触发恢复（§3.3 上表）。
6. 校验通过后连接可以长期使用（audit token 不受 PID 复用影响，这是相对 `LOCAL_PEERPID` 的关键优势）。签名 identifier 在**签名时**写进签名里，之后改文件名不会变，所以校验 identifier 不受安装位置影响。

Team ID `P93GN4N3DC` 与 identifier `com.conteman.cubbix` 写成助手侧常量。ad-hoc 签名的开发构建因此天然被拒——这正是我们要的（§2.2 的 `LidDevBuild`）。

反向校验（应用 → 助手）用**只校验 Team ID** 的宽松版本。理由按复核更正：`mygo` 的嵌套签名（`cmd/mygo/resources.go` 的 `signNestedCode`）不传 `--identifier`，裸 Mach-O 在没有既有签名、没有 Info.plist 时可由文件名派生 identifier；Go 初始签名则是 `a.out`，本实现先显式固定为 `cubbix-helper`（`codesign(1)` 的行为）；安装只是复制文件，副本保留源签名，所以 identifier 仍是构建时那个值（例如 `cubbix-helper`）。它与源文件、资源布局、副本名确定性地绑在一起，写死一个值能对上，但**只能对上一种布局**：改名、换资源目录、或将来嵌进 bundle 都会让它失效，而它并不提供 Team ID 之外的额外保护——同一 Team ID 下的签名二进制都是我们自己发布的。反面的风险由「`/var/run` 下抢绑需要 `daemon` 组或 root」兜住，因此反向只校验 Team ID 已经够；**不**降级成只查 uid（任意同用户进程都能关掉系统睡眠，§6.2 第 1 条）。正向（助手校验应用）不受此影响：应用是 bundle，Info.plist 固定了 identifier，所以那里仍是 Team ID + identifier 双校验。

`CFData`／`CFDictionary`／`CFString` 的构造走 `purego` 绑定 CoreFoundation（`CFDataCreate`、`CFDictionaryCreate`、`CFDictionaryAddValue`、`CFStringCreateWithCString`、`CFRelease`），与 `mygo@v0.6.2/internal/darwin/cf.go` 的 `loadCF` 同一手法；`kSecGuestAttributeAudit` 这类**导出常量是变量**，必须 `Dlsym` 后二次解引用（`**(**uintptr)`），MyGo 读 `kCFRunLoopCommonModes` 时就是这么做的（同文件）。这条链**未在本机跑通**，见 §4.6 第 1、11 项。

### 3.4 恢复与重试

| 触发 | 处理 |
| --- | --- |
| `disable` 请求 | 立即恢复，回 `ok`（含读回值） |
| 连接 EOF（应用正常退出、崩溃、被 `SIGKILL`） | 立即恢复 |
| 租约过期（15 秒无请求） | 恢复 |
| 截止时间到 | 恢复 |
| 改用电池（拔电） | **不恢复**，会话继续。这是与第 2 版的行为差异：电池上允许合盖保持（§5.5） |
| 电量 ≤ 下限（30 秒一次采样） | 恢复，`code = battery-low`，`status` 里带上电量与原因 |
| 电量读不到或不可信（同上采样，连续 3 次） | 恢复，`code = battery-unknown`；单次失败只计数、不恢复，一次成功采样把计数清零（常量 `batteryUnknownLimit = 3`，实现里只有这一个数字；取 1 就是「一读不到就恢复」） |
| 助手启动（launchd 重启、开机） | 若有 journal → 先恢复，再开始监听；见 §3.5 |
| 恢复本身失败 | **保留 journal**，按 1s、2s、5s、10s、30s、之后每 60s 重试，`state = restore-failed`；每次 `status`／`ping` 都回这个状态，应用侧据此显示异常 |

恢复失败不静默：应用侧会话中每 5 秒 `ping` 一次，`state` 不是 `on-ours`／`off` 就切到异常界面，tooltip 里给出「强制恢复睡眠」按钮（§3.8），按钮旁一行小字说明它需要用管理员密码执行一次。**不再**给可复制的 `sudo pmset …` 命令文本：用户要的是「按一下就好」，一段要自己找终端粘贴的文本在合盖场景里等于没有。按钮只在**确认是本功能遗留**时出现：助手在线且回 `lidRestoreFailed`（journal 在），或助手**不在线**且应用自己的标记文件存在；助手在线报 `on-foreign`（无 journal）时以助手为准，只提醒、不提供按钮，并把过期标记删掉（§3.8）。

### 3.5 助手重启与开机

launchd 配置（T3 的 plist，`Program` 用绝对路径）包含 `RunAtLoad` 与 `KeepAlive`，所以助手在开机、被强杀、退出非 0 时都会重新起来（`launchd.plist(5)` 的 `KeepAlive`／`RunAtLoad` 两节）。

启动顺序是硬约束：

```
1. 读 /Library/Application Support/com.conteman.cubbix.helper/session.json
2. 不存在 → 读现值；值为 1 → state=on-foreign（只报告，绝不修改；此时无法区分「别的工具设的」与「我们上次没恢复成功」）
3. 存在 → 无论截止时间是否已过、也无论现值是不是 0，一律先恢复：写 0 → 读回必须为 0 → 才删 journal
4. 恢复失败 → 保留 journal，state=restore-failed，继续跑重试；**此时仍然监听**（应用连上来能看到真实状态）
5. 起监听、起计时器
```

「助手重启要恢复」优先于「保持会话连续性」：宁可让合盖保持短暂失效，也不留下一个没人负责的 `disablesleep=1`。应用侧不自动重开（§5.3 的「应用重启后的恢复」），由用户点一次开关，避免「助手反复崩溃 + 应用反复重开」的循环把异常藏起来。

开机时助手还会在无 journal 的情况下读一次现值，用于 `on-foreign` 报告；这里**不做**任何修复——判断权在用户（§3.8 的强制恢复入口是用户按的，不是助手自作主张）。

### 3.6 更新、卸载与停用

| 时机 | 顺序 |
| --- | --- |
| 应用正常退出 | `disable`（等读回确认）→ 确认 0 后删标记（§3.8）→ 停 `caffeinate`（`main.go` 的 `beforeQuit` 现在先停常亮，本轮改为先停合盖）→ 不 `unregister`（下次开机还要它做补救恢复） |
| 应用更新（ADR 004 的「重启更新」） | 重启前：`disable` + 读回确认 + 删标记 → 更新 → 重启后：读 `Status()`；若 `requiresApproval`，或在 `hello` 里发现 `helper` 版本与内嵌版本不一致，显示「助手需要更新」，用户点一次开关触发一次「恢复 → 更新脚本（§3.6.2）」 |
| 卸载／停用 | 关闭「常亮」格子（`changeAwakeEnabled` 的 `false` 分支）→ `disable` + 读回确认 + 删标记 → 确认 0 之后才执行卸载脚本（§3.6.3）→ 恢复失败就**不允许**停用，并提示原因（否则会留下一个没人能恢复的 1） |
| 助手二进制更新 | 应用启动时比对 `hello` 返回的 `helper` 与内嵌版本；不一致 → 状态行 alert「助手需要更新」，点击后一次授权按 §3.6.2 重新安装 |

安装、更新、卸载三处动作共用同一套常量：源路径、副本路径、plist 路径、requirement 串、`LaunchDaemon` label 全部写在应用二进制里（要求串只被安装／更新使用），运行时只读 `Status()`／`hello` 的返回值做判断，**不拼接任何来自外部输入的字符串**。

#### 3.6.1 复制 → 校验 → 才 bootstrap（安装与更新共用）

安装、更新都是同一条信任链，顺序固定：

```
1. 复制源到临时副本（同一目录：/Library/PrivilegedHelperTools/ 下带 .new 后缀）
2. codesign -v -R=<常量 requirement> <临时副本>
       失败 → /bin/rm -f <临时副本> → 非 0 退出；旧副本与旧 plist 原样保留
3. 校验通过 → /bin/mv -f <临时副本> <副本路径>（同一目录 rename，原子替换）
4. 写 /Library/LaunchDaemons/com.conteman.cubbix.helper.plist（常量内容），chown root:wheel 0644
5. bootout；失败且服务仍存在时，固定 launchctl kill SIGTERM 后再 bootout；服务已不存在则继续
6. 每 100ms 用 launchctl print 检查旧服务是否消失；最多等待 300 次（30 秒），仍存在则非 0 退出
7. bootstrap 最多尝试 5 次，失败间隔 1 秒；全部失败则非 0 退出
8. launchctl print 再确认服务已加载；确认失败则非 0 退出
```

校验的 requirement 串固定为（identifier 的值取构建期断言的值，见 §4.4.1）：

```
anchor apple generic and certificate leaf[subject.OU] = "P93GN4N3DC" and identifier "cubbix-helper"
```

#### 3.6.2 更新（常量化，与安装共用同一个常量）

更新的源、目标、校验、plist、bootstrap 与安装**逐字相同**，所以只维护一份常量字符串：下面这份就是它，§4.4 的安装也引用同一份。更新只多两件事：

1. 调用前先 `disable` 并读回 0、删标记（顺序见 §3.6 表）；

```sh
    step=terminate
    printf 'cubbix-step=terminate\n'
    /bin/launchctl kill SIGTERM system/com.conteman.cubbix.helper || true
    /bin/launchctl bootout system/com.conteman.cubbix.helper || true
  fi
fi
step=unload-wait
printf 'cubbix-step=unload-wait\n'
unload_attempt=0
while /bin/launchctl print system/com.conteman.cubbix.helper >/dev/null 2>&1; do
  if [ "$unload_attempt" -ge 300 ]; then
    printf 'cubbix-error=unload-timeout\n' >&2
    exit 1
  fi
  unload_attempt=$((unload_attempt + 1))
  /bin/sleep 0.1
done
step=bootstrap
printf 'cubbix-step=bootstrap\n'
bootstrap_attempt=0
while :; do
  bootstrap_rc=0
  /bin/launchctl bootstrap system /Library/LaunchDaemons/com.conteman.cubbix.helper.plist || bootstrap_rc=$?
  if [ "$bootstrap_rc" -eq 0 ]; then break; fi
  printf 'cubbix-command-exit=%s\n' "$bootstrap_rc" >&2
  bootstrap_attempt=$((bootstrap_attempt + 1))
  if [ "$bootstrap_attempt" -ge 5 ]; then
    printf 'cubbix-error=bootstrap-failed\n' >&2
    exit 1
  fi
  /bin/sleep 1
done
step=confirm
printf 'cubbix-step=confirm\n'
if ! /bin/launchctl print system/com.conteman.cubbix.helper >/dev/null 2>&1; then
  printf 'cubbix-error=confirm-failed\n' >&2
  exit 1
fi
```

为什么不在更新时另写一条脚本：两份几乎一样的 root 脚本迟早会走得不一样（一份记得校验，一份忘了）。因此**安装与更新在代码里是同一个常量字符串**，差异只在调用时机（§3.6 表），单测里断言两者取值相等（纯字符串比较，不执行脚本，§7.1 第 23 项）。

要点：

- **旧版在新副本校验通过之前一直可用**。校验失败时 `exit 1`，旧副本、旧 plist、正在跑的 daemon 都不动，应用把它映射成 `svcBroken`（`LidServiceBroken`）。
- 新副本先落到 `.new` 而不是直接覆盖：否则校验失败时旧副本已被破坏，下一次开机谁也恢复不了 `disablesleep`。
- `mv` 与 `cat` 都发生在校验之后；校验返回后脚本**不再读** `/Applications/Cubbix.app` 里的源文件，因此“校验后被换掉”的窗口不存在。
- 更新前必须已经 `disable` 并读回 0，否则会出现“换二进制时 `disablesleep` 还是 1”的窗口。

**安装启动失败的依据与边界（2026-11-04）**：

| 判断 | 依据与确定程度 |
| --- | --- |
| 旧流程存在一次性失败窗口 | `lidInstallScript` 原先在 `bootout` 后直接执行一次 `bootstrap`，没有卸载等待、重试和加载确认。`set -e` 下后者非 0 会终止脚本，但已写好的副本和 plist 会留下；第二次点击仍走同一条脆弱路径。这是源码可确认的缺口。 |
| 现场是安装后服务未加载 | 已安装文件与签名检查通过，而服务查询找不到；手动 bootstrap 随后成功。这些现象支持“bootstrap 阶段未完成”，但没有原安装进程的退出码／stderr，不能认定某个具体错误码或唯一根因。 |
| bootout 后异步清理／残留注册竞态 | 需要防御的候选：卸载返回后立即加载可能遇到清理窗口；错误 5／37 已由模拟测试覆盖。`launchctl(1)` 只说明装卸服务定义，不足以证明现场时序；是否为本次触发原因、残留何时消失及具体返回码均**需实测**。等待卸载和 bootstrap 有限重试分别覆盖“仍能查询到旧定义”与“定义消失后尚未就绪”。 |
| 授权 shell 的环境差异 | 原脚本已设置并导出固定 PATH，外部命令与目标域／文件路径均显式指定；源码不依赖交互 shell、工作目录或用户输入。不能据此完全排除授权环境差异；与手动执行的身份／环境差异仍**需实测**，本轮不执行管理员授权。 |
| 失败反馈不完整 | 原适配器把非取消的脚本错误归为 `LidServiceBroken`，但 `notifyLid` 没有该键；状态 3 也落入通用 broken。现在分别显示安装／启动失败、已安装未运行的中英文提示，两者都纳入异常通知白名单；仍复用原有 alert、tooltip 和合盖开关，不增加布局。 |

**安装可靠性与失败诊断修正（2026-11-04）**：

- 现场提供的证据是：磁盘副本已更新，但旧进程和旧修订仍在运行；随后手动卸载、加载成功。这支持“副本替换不等于进程已更新”，不能定位原脚本究竟在 bootout、等待卸载还是 bootstrap 失败。原适配器丢弃退出码和输出，具体系统错误码已无法追溯。
- 原卸载等待仅 5 秒，与现场观察到的退出等待处于同一量级，容易撞到清理边界。本机 `launchd.plist(5)` 将默认 `ExitTimeOut` 写为系统定义，因此不能把“所有系统默认 5 秒”当作已证实事实。新 plist 显式设置 15 秒，安装器等待卸载 30 秒，再做原有 5 次 bootstrap 尝试；bootout 非 0 且定义仍存在时，使用固定 `launchctl kill SIGTERM` 和第二次 bootout，不从输出解析 PID 或拼接命令。卸载超时仍失败退出，不带着旧定义继续加载。
- `mv` 是将已校验的 `.new` 原子替换到目标名称，避免原地截断正在运行的可执行文件；它不会要求旧进程自动执行新映像。替换后仍必须完成卸载、加载与同修订 hello。真实系统的映像与 launchd 时序仍需验收。
- 助手接到 SIGTERM／SIGINT 后关闭 listener 和所有连接，等待请求及采样协程结束，再统一恢复，包括没有连接但 journal 仍在的恢复失败状态。pmset 读取上限 5 秒、写入上限 2 秒；20 秒 watchdog 防止框架、文件系统或校验卡住导致进程无限挂起。正常退出等待恢复写入、读回和 journal 清理；失败或超时保留未清理的 journal 供下次启动恢复，不能把强制退出描述成恢复成功。
- `admin` 收集解释器的 stdout／stderr 与退出码，兼容 `\r`、`\r\n`；脚本 EXIT trap 在 stderr 补写固定阶段和 shell 退出码，避免 shell 失败时 stdout 丢失。应用只保存白名单标记，丢弃原始输出、路径、账号、授权文本和错误字符串。取消授权仍映射 `LidDenied`。
- `cubbix status --json` 的 `state.awake.lid` 增加 `installStep`、`installError`、`installExitCode`（解释器）、`installScriptExitCode`（shell）、`installCommandExitCode`（已记录的命令失败码）。阶段包括 copy／verify／replace／plist／bootout／terminate／unload-wait／bootstrap／confirm；应用侧另有 authorize／hello。错误包括 script-failed、authorization-cancelled、unload-timeout、bootstrap-failed、confirm-failed、helper-not-ready。没有取得的退出码省略，解释器无法启动时为 -1。失败诊断不被轮询覆盖，下次安装尝试重置；成功安装清除旧错误并保留 confirm 与解释器退出码 0，握手未就绪则记录 hello。界面继续使用原有简短文案。
- 自动化只执行替换过全部外部命令的脚本夹具、假电源接口和隔离子进程。真实授权、系统服务装卸、已安装文件替换、真实电源写入与实体合盖没有执行，仍由维护者验收。

安装与更新继续共用全文常量；`lidInstallScriptApple` 的反转义必须与正文逐字节一致。脚本确认的是 launchd 定义已加载，应用再以经过身份校验的 `hello` 确认进程可用；两者不能互相替代。启动与轮询只读，不会自动执行授权安装。

```sh
/bin/rm -f /Library/LaunchDaemons/com.conteman.cubbix.helper.plist
/bin/rm -f /Library/PrivilegedHelperTools/com.conteman.cubbix.helper
```

前置条件是**应用已经确认 `disablesleep` 为 0、并已删除自己的标记**（§3.8）：脚本删掉 journal 之后，就再没有东西知道“本来该恢复”。因此 `Unregister()` 在恢复未确认时**不执行**这个脚本，而是回 `lidRestoreFailed`。

### 3.7 完整状态机

应用侧 `lidController` 只用这几个状态，界面完全由它派生：

| 状态 | 含义 | 入口 | 出口 |
| --- | --- | --- | --- |
| `lidOff` | 未开启 | 初始；`disable` 成功；会话结束 | 用户点开关 → `lidEnabling` |
| `lidEnabling` | 已发 `enable`，等读回 | 点开关／命令／URL | 读回 1 → `lidOn`；失败 → `lidError` |
| `lidOn` | 读回确认 1，租约有效 | `lidEnabling` 成功 | 会话结束／用户关闭／异常 → `lidStopping` |
| `lidStopping` | 正在恢复 | 所有结束路径 | 读回 0 → `lidOff`；失败 → `lidRestoreFailed` |
| `lidRestoreFailed` | 恢复未确认，助手在重试 | `lidStopping` 失败 | 助手恢复成功 → `lidOff`；用户点「重试」→ `lidStopping` |
| `lidHelperGone` | 连接断开且无法重连 | 心跳失败、`status` 连续失败 | 助手回来 → `lidOn`（若仍是我们的会话）或 `lidOff` |
| `lidBlocked` | 条件不满足（未安装／需要允许／电量不高于下限／外部设置／不支持） | 开启前检查 | 条件变化后用户再试 |
| `lidError` | 开启或恢复失败并带原因 | 各失败路径 | 用户重试 |

`on-foreign` 是 `lidBlocked` 的一种：`code=foreign-setting`，界面提示「系统里已有别的工具把合盖睡眠关掉了，Cubbix 不会覆盖」，且**不**提供「强行覆盖」按钮（即使用户目录里的标记文件存在，§3.8）。`battery-low` 也是 `lidBlocked` 的一种（开启时电量已 ≤ 下限或读不到）：显示 `LidBatteryTooLow`，不写任何东西。

四个不属于状态机的输入：

- **`max-duration`**：助手到 12 小时上限自己恢复，回 `status` 时 `code=max-duration`、`state=off`。应用仅结束合盖扩展并显示 `LidMaxDuration`，普通常亮按自身截止时间或跟随目标继续。它**不是**错误，不进入 `lidError`／`lidRestoreFailed`。
- **`battery-low`（会话中）**：助手自己恢复后回 `code=battery-low`、`state=off`，应用仅结束合盖扩展，保留普通 `caffeinate` 会话，提示 `LidBatteryLow`。
- **`battery-unknown`（会话中）**：读不到电量连续 3 次，助手同样自己恢复后回 `code=battery-unknown`、`state=off`；收敛路径与上一条相同，只多一句 `LidBatteryUnknown`。它不是错误（恢复本身成功），不进 `lidError`／`lidRestoreFailed`。
- **启动告警**（§3.8）：启动时自己读一次 `pmset -g` 与标记文件，结果是一个 `lidController` 之外的只读快照（`lidStaleSetting bool`、`lidStaleIsOurs bool`），它只控制「强制恢复睡眠」入口出不出现：只有「助手不在线且 `lidStaleIsOurs` 为真」或「助手在线且报 `lidRestoreFailed`」才出，助手在线报 `on-foreign` 时只提醒（§3.8）。一旦有了活跃会话，就由 `lidOn`／`lidRestoreFailed` 接管，这条告警不再显示。

### 3.8 强制恢复睡眠（不依赖助手，不改别人的设置）

背景是 §3.2 末尾那条失效面：`disablesleep=1` 可能停在系统里，而唯一会自动恢复它的助手此刻不在了（用户在系统设置里关掉了它、安装损坏、副本被删）。应用读不到 root `0700` 的 journal，也不该去猜，因此需要两样东西：**一个应用自己能读写的「我方遗留」标记**，和**一条不经过助手进程的恢复路径**。后者是**手动**入口，不是自动恢复。

标记文件：`config.toml` 同目录下的 `lid-restore-required`（`main.go` 里 `configPath` 所在目录；内容只写会话开始时间与客户端会话 ID，不写用户名、不写路径）。它和助手的 root journal 互为补充：

- journal 在 root 下，证明「是我们开的」但应用读不到；标记在用户目录，应用读得到，但只有应用自己会写。
- **写入时机**：助手 `enable` 回 `ok` 且读回 1 确认之后，与 `config.AwakeLid = true` 同一刻。
- **删除时机**：只有在读回 0 确认之后——`disable` 的响应值、或应用自己只读 `pmset -g` 读到 0；另一种是**助手在线报 `on-foreign`（无 journal）时**，把这个过期标记顺手删掉（§3.8 下表）。其余任何时候都不删。
- 标记不是安全边界（用户可写），而且**它不能压过助手**：助手在线时以助手的结论为准（它能读 root journal，标记只能证明「应用曾写过一行」）。伪造标记最多诱导用户按一次「强制恢复睡眠」，把外部设置改回开启一次，无其它权限（残余风险见 §6.2 第 11 条）。

| 项 | 规定 |
| --- | --- |
| 谁说了算 | **助手在线时以助手为准**。助手能读 root journal，它说「没有 journal」就是没有我们留下的会话：`on-foreign` → 只提醒、**不提供强制恢复**，即使标记文件在（此时顺手删掉这个过期标记，它只会把下一次判断带偏）；`restore-failed`（journal 在）→ 提供按钮，不看标记 |
| 出现条件（只有两种） | ① 助手**不在线**（`lidHelperGone` 且重连失败、`svcNotRegistered`、`svcBroken`、或 `hello` 失败）：标记文件在 + 只读 `pmset -g` 读到 `SleepDisabled=1`；② 助手**在线**且回 `lidRestoreFailed`、值仍为 1（journal 在，来自本功能自己的会话，不依赖标记）。除此之外一律不出现 |
| **不**出现的地方 | 值已经是 0 时一律不出现（启动读到 0 同时删标记，说明助手已做过启动恢复）；正常会话中读到 1 也不出现（那正是 `lidOn` 的合法状态）；**助手在线报 `on-foreign` 时不出现**（§3.7：外部设置，只提醒不提供按钮），**即使标记在**——此时标记被当作过期删除。它不是常驻按钮，也不进设置页（低信息密度） |
| 外部设置的处理 | 助手回 `on-foreign`（无 journal）：状态行只提示 `LidForeign`（「已有别的工具关闭了合盖睡眠，Cubbix 不会覆盖」），**不提供任何按钮、不自动改**；有无标记都一样。助手不在线且无标记时同样只提醒 |
| 位置 | 点击状态行 alert 打开的锚定浮层里（`ui.PopoverBase`），`Danger` 色的次要按钮 + 一行说明（`LidForceRestore` / `LidForceRestoreHint`） |
| 动作 | 一次 `osascript -e 'do shell script "<常量>" with administrator privileges'`，常量脚本只有一条命令：`/usr/bin/pmset -a disablesleep 0` |
| 读回 | 授权返回后，应用自己再只读跑一次 `pmset -g`（不需要 root）读 `SleepDisabled`；为 0 → 成功，删标记、清异常状态；仍为 1 → `LidForceRestoreFailed`，按钮保留 |
| 取消授权 | 与其它鉴权一致：什么都不改、不留状态，按钮保留 |
| 不做 | 不改 `sleep`／`disksleep`／`hibernatemode`／任何其它键；不接受任何来自 URL、命令面板或文件的输入；不因为「看到 1」就自动执行 |

`osascript` 脚本仍然是**全常量**：不拼接路径、不拼接时间、不接收参数。需要管理员授权的**动作**共**四处**（安装、更新、卸载、强制恢复），但常量脚本正文只有**三份**：安装与更新共用 §3.6.2 那一份，卸载是 §3.6.3，本节这一条是第三份。三份都只做常量动作，都不在后台、不在 URL、不在定时器里。

为什么不用「复制一条 sudo 命令给用户」（第 1 版的做法）：合盖保持的异常态恰好发生在用户**已经合上盖子**、回来才发现机器没睡的时候；这时让用户去开终端、粘贴、再确认，等于把安全提示变成一个没人执行的提示。按钮 + 一次授权把这件事变成一次点击。§6.4 的告知口径随之调整。

**为什么必须用标记而不是「读到 1 就给按钮」**：那样会把别的工具（或用户自己 `sudo pmset`）设的值也一并改掉。收到「不是我方」的信号时，应用只能提醒、不能提供一键恢复：它不知道那个 1 是为了什么（例如另一个电池工具的策略）。只有助手在线时的 `restore-failed`（journal 在），以及**助手不在线时**的标记文件（我们自己写过、自己没删）才把责任指向本功能。**标记是最后的退路，不是第一优先级**：助手一旦在线并说「没有 journal」，标记就作废（删掉），因为它自己也可能被别人写过（§6.2 第 11 条）。

| 读电源 | `pmset -g batt` 的 `'AC Power'`／`'Battery Power'`（仓库已有 `batteryPower`）；或 purego 调 IOKit `IOPSGetProvidingPowerSourceType` | `awake_app.go` 的 `batteryPower`；`mygo@v0.6.2/internal/darwin/cf.go` 的 `iopsGetProvidingPowerSourceType` 绑定 | **可行** |
| 读电量（低电量下限用） | 首选 `pmset -g batt` 同一段输出里的百分比：本轮只读跑了一次，格式为 `80%; AC attached; not charging`（`NN%;` 是固定前缀），`batteryPower` 已经在用同一个命令 | 本机只读观察；`pmset(1)` 未文档化该输出格式，**解析需实测**（§4.6 第 2 项）。百分比一律用 `Current Capacity / Max Capacity × 100` 计算并交叉校验（`IOPSKeys.h` 的 `kIOPSCurrentCapacityKey` 讨论：单位由电源自己定，Apple 电源是百分比，其它电源可能是 mAh；`kIOPSMaxCapacityKey` 的 Apple 电源取值通常为 100）；两者不一致时以 IOKit 为准。备选 purego：`IOPSCopyPowerSourcesInfo`（`mygo@v0.6.2/internal/darwin/cf.go` 已绑定）→ `IOPSCopyPowerSourcesList` → `IOPSGetPowerSourceDescription` → 取 `kIOPSCurrentCapacity`／`kIOPSMaxCapacity`／`kIOPSIsCharging`，但这条链**未在本机验证**，同样见 §4.6 第 2 项 | **可行，未跑通** |
| Unix socket 服务 | `net.Listen("unix", …)` | Go 标准库 | **可行** |
| 对端 audit token | `syscall.Syscall6(SYS_GETSOCKOPT, …)` 或 purego 调 libc `getsockopt` | 本机 SDK 的 `sys/un.h` 定义 `LOCAL_PEERTOKEN 0x006`（注释为「retrieve peer audit token」） | **可行，未跑通** |
| 代码签名校验 | purego 绑定 Security 框架（`SecCodeCopyGuestWithAttributes`、`SecRequirementCreateWithString`、`SecCodeCheckValidity`）与 CoreFoundation（`CFDataCreate`、`CFDictionaryCreate`、`CFDictionaryAddValue`、`CFStringCreateWithCString`、`CFRelease`）。`SecCodeCopyGuestWithAttributes` 的 attributes 参数类型是 `CFDictionaryRef`（`SecCode.h`），少了 `CFDictionaryCreate` 这条链根本拼不起来 | 本机 SDK `SecCode.h` 声明这些函数与 `kSecGuestAttributeAudit`；MyGo 已有 CoreFoundation/IOKit/libdispatch 的 purego 绑定先例。`kSecGuestAttributeAudit` 在头文件里只有符号，「取值是 32 字节 audit token 的 `CFData`」来自 Apple 文档，**需实测** | **可行，未跑通** |
| 定时器／信号 | Go 标准 | — | **可行** |

结论：**助手可以是纯 Go、`CGO_ENABLED=0` 的 Mach-O 可执行文件**，但「Security 框架 + audit token」这一段是本规格唯一的高风险 FFI。实现已在临时 socket 与 ad-hoc 签名进程上验证 identifier 匹配通过、不匹配拒绝；生产 Team ID + identifier 的正向通过仍需 Developer ID 实测。跑不通时**没有降级方案**（§4.6 末尾）。

### 4.2 `SMAppService.daemonServiceWithPlistName:` 需要的 bundle 结构（T1 布局，本文档不采用，留作对照）

| 要求 | 依据 |
| --- | --- |
| plist 必须在**调用方 app bundle** 的 `Contents/Library/LaunchDaemons/` 下 | `SMAppService.h` 的 `daemonServiceWithPlistName:` 讨论；Apple 迁移文档示例 `$APP.app/Contents/Library/LaunchDaemons/com.example.daemon.plist` |
| plist 里的可执行文件用 `BundleProgram` 给出 **app bundle 相对路径** | `launchd.plist(5)` 的 `BundleProgram`：「an app-bundle relative path to the executable for the job. This key is only supported for plists that are installed using SMAppService」 |
| 相对路径的基准是 `.app` 根（不是 `Contents`），所以值以 `Contents/` 开头 | 取值实例：多个公开项目把 `BundleProgram` 写成 `Contents/Resources/bin/<helper>`（本轮查看的三个公开仓库一致，属第三方实现证据，不是 Apple 文档） |
| 助手二进制可以放在 `Contents/Resources/` 里 | 同上；另外 `mygo build` 会把资源放进 `Contents/Resources`（§4.3） |
| 应用要能被**登录前**访问到，否则开机不会引导 daemon | `SMAppService.h`：「For a LaunchDaemon to be bootstrapped during boot, the containing application must be accessible before a user logs in… recommended that the application bundle live in /Applications」 |
| 需要 `AssociatedBundleIdentifiers`（只有 legacy plist 需要） | Apple 迁移文档；`launchd.plist(5)` 同名键 |

因此 T1 的目标布局是（**第 3 版不采用**，只用 §4.4 的 T3）：

```
Cubbix.app/
├── Contents/
│   ├── MacOS/Cubbix
│   ├── Library/LaunchDaemons/com.conteman.cubbix.helper.plist   ← mygo build 产不出（§4.3）
│   ├── Resources/
│   │   ├── bin/cubbix-helper                                    ← mygo build 会签名（§4.5）
│   │   └── …（图标、语言、前端）
│   └── Info.plist
```

plist 内容。**T3（本文档采用）用 `Program` 绝对路径**，安装脚本见 §4.4；`BundleProgram` 形式只属于 T1，留作对照：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key><string>com.conteman.cubbix.helper</string>
  <key>Program</key><string>/Library/PrivilegedHelperTools/com.conteman.cubbix.helper</string>
  <key>RunAtLoad</key><true/>
  <key>KeepAlive</key><true/>
  <key>ThrottleInterval</key><integer>10</integer>
```

### 4.3 `mygo build` 能否把额外二进制与 plist 打进包并正确签名、公证

**二进制：能。plist：不能。** 逐条依据：

| 问题 | 结论 | 依据 |

| 能不能把助手二进制放进包 | 能，放 `resources/` 或配置的 `resources` 列表里，落到 `Contents/Resources`，`App.Path(mygo.PathResources)` 取路径 | `mygo@v0.6.2/docs/distribution.md` 的「Resources」「Platform resources」「Helper executables」三节；`cmd/mygo/resources.go` 的 `copyResources`（目标目录固定为 `Contents/Resources`） |

| 上游现状 | 当前 MyGo 主线文档里也没有 LaunchDaemon／launchd 布局的支持 | 公开仓库 `mygo` 最新的 `docs/distribution.md` 检索 `launchd`／`LaunchDaemon` 无结果（本轮只读核对） |
| 开发构建 | `mygo dev` 的资源直接放在可执行文件旁，没有 `.app`；没有 bundle 时连 `SMAppService.mainAppService` 都用不了 | `mygo@v0.6.2/docs/distribution.md` 的「Resources」；`mygo@v0.6.2/internal/darwin/login.go` 的 `bundlePath` 在非 bundle 情况返回错误 |

### 4.4 做不到时的替代方案

| 方案 | 做法 | 优点 | 代价／风险 | 结论 |
| --- | --- | --- | --- | --- |
| **T1 bundle 内 LaunchDaemon** | 等 MyGo 能把文件放进 `Contents/Library/LaunchDaemons/` 并一并签名 | 保留 Apple 推荐的布局（系统校验 bundle 内外签名、系统设置里有开关） | 时间不可控；升级本身要一轮回归。**本文档不推进（维护者已定）**：不向 MyGo 提需求 | **不采用**；将来 MyGo 若自行支持，可只替换安装层 |
| **T2 发布脚本后处理** | `mygo build` 之后插入 plist、重新签名、重新公证、重做 DMG | 不改 MyGo | 更新包（`mygo build` 生成的签名归档）与处理后的应用不再一致，ADR 004 的应用内更新会把「没有 plist 的应用」装回去；公证与 DMG 也要自己重做 | **不选**（会破坏 ADR 004 的信任链） |
| **T3 legacy 安装层** | plist 走 `/Library/LaunchDaemons/`，助手复制到 `/Library/PrivilegedHelperTools/`，用**一次**管理员授权完成；`Program` 用绝对路径；plist 带 `AssociatedBundleIdentifiers`；**复制与签名校验在同一条 root 脚本里，校验不过就删副本、不 bootstrap**（§4.4.1） | **现在就能落地**，不动 MyGo、不动更新链；除「安装」外，会话、IPC、恢复、状态机与 bundle 内布局完全相同 | 需要自己写安装器，并且要自己写签名校验；`/Library/PrivilegedHelperTools` 副本在助手版本变化时要一次重新授权；Apple 视其为 legacy 布局；系统设置里照样有开关（`launchd.plist(5)` 的 `AssociatedBundleIdentifiers`），用户关掉后的状态用 `SMAppService.statusForLegacyPlist(at:)`（macOS 13+）读 | **采用（唯一实现）** |
| **T4 只做 `caffeinate`** | 不碰 `disablesleep` | 零风险 | 不满足需求（调研与 Apple QA1340 都说明 assertion 挡不住合盖） | 不选 |

实现上把「安装」抽成接口；保留它只为一件事：**将来 MyGo 若支持 bundle 内 LaunchDaemon，可只替换安装层**，其余代码不动：

```go
// lidService is the one install layer: the legacy /Library install today,
// a bundle LaunchDaemon if MyGo ever supports one.
type lidService interface {
	Status() lidServiceStatus   // unavailable / notRegistered / requiresApproval / enabled / notRunning / broken
	Register() error            // 安装：一次管理员授权（§4.4 脚本）
	Unregister() error          // 卸载：§3.6.3 脚本，调用前必须已确认恢复
	OpenSettings()              // 打开系统设置的登录项页（macOS 13+）
	HelperPath() (string, bool) // 已安装副本的路径与是否存在
}
```

T3 的安装脚本必须是**全常量**，用一次 `osascript -e 'do shell script "<常量>" with administrator privileges'` 完成全部步骤，脚本里不拼接任何来自文件系统或 IPC 的字符串（避免引号注入）。正文见 §3.6.2（安装与更新是同一个常量字符串，第 23 项测试断言两者相等）；`codesign` 的 requirement 串含双引号，外层 `do shell script` 又是一层双引号，转义由应用里的常量一次性写定，不在运行时拼接。

因为路径是常量，T3 要求应用位于 `/Applications/Cubbix.app`；不在该位置时合盖保持显示 `LidUnsupported`（tooltip 说明把应用放进「应用程序」文件夹）。

#### 4.4.1 为什么校验这一步不能省（§3.6.1 第 2 步）

第 1 版的脚本只有「复制 + bootstrap」，没有校验。这等于把**用户可写的文件**提权成 root：用户把 `Cubbix.app` 拖进 `/Applications` 时，包归他自己所有，`Contents/Resources/bin/cubbix-helper` 可写；任何以普通用户身份运行的进程都能在安装前把它换成别的 Mach-O，然后等用户点一次「合盖保持」。root 脚本会忠实地把它复制到 `/Library/PrivilegedHelperTools`、以 root 启动。

同一条 `SMAppService.h` 类注释也说明了 legacy 布局的性质：`/Library/LaunchDaemons` 里的 plist 凭「写 `/Library` 需要文件系统权限」直接引导，系统设置里不再要求批准。也就是说 T3 的那一次管理员密码是**唯一**的关口，校验必须发生在关口里面。

校验的四条要求：

| 要求 | 取值 |
| --- | --- |
| 校验对象是**副本**，不是源 | 复制完成后再校验。副本是 `root:wheel 0755`，校验通过之后普通用户改不动它，因此不存在「校验完再被换掉」的窗口；源文件归用户所有，校验源本身没有意义 |
| 按 **Team ID + identifier** 校验 | 要求串为 `anchor apple generic and certificate leaf[subject.OU] = "P93GN4N3DC" and identifier "cubbix-helper"`（identifier 的取值见下一行）；`codesign -v -R="…" <path>` 非 0 即失败（`codesign --help` 的 verify 形式，本轮只读核对） |
| identifier 以 `codesign -dv` 为准 | `mygo` 的 `codesignArgs` 不传 `--identifier`，重签会保留已有 identifier。Go 生成的助手已有 `a.out` 签名；构建脚本必须先显式签成 `cubbix-helper`，再交 MyGo 重签。不能从文件名推断，也不能拿应用的 `com.conteman.cubbix` 代替。这个常量不能拍脑袋写：`scripts/build-helper.sh`／`scripts/release.sh` 在 `mygo build` 之后对包内助手跑一次 `codesign -dv --verbose=4`，把 `Identifier=` 读出来与脚本里的常量比对，不一致就让发布失败（构建期断言，不需要 root） |
| 失败必须自清 | 校验不过 → 删副本 → 非 0 退出；应用侧把 `osascript` 的失败映射成 `svcBroken`（`LidServiceBroken`），不重试、不 bootstrap |

下面这些**不**是本条的保护范围，写清楚避免误解：脚本不校验 `Cubbix.app` 整体签名（用户自己拖进来的包本来就归他所有，校验整体签名只会在用户用替代方式安装时误伤）；不要求 `/Applications` 下的包归 root；不防「root 已被攻击」。威胁模型见 §6.1。

## 5. 与现有常亮的关系

### 5.1 附加开关，不是第三种模式

**推荐：附加开关。** 理由：

1. 「保持屏幕常亮／仅保持任务」是 `caffeinate` 的两个参数组合（`keepawake.go` 的 `awakeArgs`：`-d -i` / `-i`），互斥；而 `disablesleep` 是**另一套机制**，与这两者正交，「合盖也保持 + 仅保持任务」是最有用的组合，用互斥的分段器表达不了。
2. 卡片面板的分段器（`panelModeSwitch`）已经承载模式语义；把合盖塞进去会变成三选一，语义错误且让会话状态更难读。
3. 合盖保持是**安全敏感**决策：它应该是一个可以被单独看见、单独关掉的开关，而不是藏在模式里的隐含后果。
4. 停止语义简单：关总开关 = 两者一起停；关合盖开关 = 只恢复 `disablesleep`，`caffeinate` 会话继续。

数据结构：

| 位置 | 字段 | 含义 |
| --- | --- | --- |
| `awakeSession`（`keepawake.go`） | `Lid bool` `toml:"lid,omitempty"` | 本次会话是否带合盖保持 |
| `Config`（`config.go`） | `AwakeLid bool` `toml:"awake_lid"` | 记忆开关；`⌃⌥⌘K` 与「记忆会话」路径据此决定是否连带开启 |
| `Config`（`config.go`） | `AwakeLidBatteryMin int` `toml:"awake_lid_battery_min"` | 低电量下限（10／20／30，默认 20）；设置页的唯一一行偏好 |
| `lidController`（新） | `state`、`sessionID`、`reason` | 运行时状态（§3.7） |

`config.AwakeLid` **只在助手读回确认 1 之后**才写入；失败一律不写（否则下次快捷键会拿一个假的记忆去开）。标记文件（§3.8）与它同一刻写、同一刻删。

### 5.2 组合规则

`awakeSession.Lid` 保存本次选择的合盖意图：普通入口从已保存的 `AwakeLid` 偏好构造新会话，模式热切换保留当前会话意图，URL／CLI 的显式关闭优先于偏好。开启或重建 `caffeinate` 时不得用旧会话的 Active／Lid 位反向清除本次选择；异步开启中和复用已开启租约时也保持该意图。只有助手确认开启后才持久化合盖偏好；开启失败回退为普通会话。

| # | 情况 | 规则 |
| --- | --- | --- |
| 1 | 合盖 + 定时（30m/1h/2h/自定义/直到） | helper 的 `deadline` = `session.End`；两边同时到点 |
| 2 | 合盖 + 不限时 | 无客户端 `deadline`，靠租约 + 助手强制 12 小时上限（§3.2）；到 12 小时助手自己恢复并回 `max-duration`，界面用 `LidMaxDuration` 说明一次 |
| 3 | 合盖 + 跟随进程 | 无 `deadline`（跟随会话的 `End` 为空）；应用 `poll` 发现目标进程消失 → 停会话 → 恢复。助手不看进程，但同样受 12 小时上限 |
| 4 | 合盖开关在常亮未开启时被点击 | 用 `selectedSession()` 开启常亮，成功后开合盖；任一步失败都回到 `lidBlocked`／不写入记忆 |
| 5 | 运行中切换模式（`setMode`） | 只重建 `caffeinate`（既有行为），合盖保持不动。重建成功 → 会话仍活跃，合盖保持照旧；重建失败 → `awakeController.start` 已经把会话置为未激活，`syncLid` 随即将合盖恢复并显示错误（一致性优先于「尽量保住合盖」） |
| 6 | 运行中点时长药丸（`setDuration`） | `caffeinate` 重建（既有行为）。**新截止时间晚于助手的 `deadline` 时必须重发一次 `enable` 续期**（带新 `deadline`，助手只更新 journal 里的时间并读回，不动 `disablesleep`），否则助手会按旧时间提前恢复；有限时长改为不限时也须续期。新截止时间相同或更早、不限时改为有限时长均不改助手，由应用在 `session.End` 到点时统一停止；重复点击当前药丸不重启。续期保留助手的原始开始时间与 12 小时硬上限 |
| 7 | `⌃⌥⌘K` 快捷键开启／停止 | 开启时按 `config.AwakeLid` 连带合盖；停止时两者一起停 |
| 8 | 会话自然到期 | `awakeController.poll` 判到期 → `awakeChanged` → 合盖恢复（§5.3） |
| 9 | 跟随的进程结束 | 同上（`ProcessEnded` 错误的显示优先级不变） |
| 10 | 会话中拔电（改用电池） | **不恢复**：会话继续，`disablesleep` 保持 1，界面不变（§5.5）。这与第 2 版正相反 |
| 11 | 会话中电量 ≤ 下限 | 助手 30 秒采样发现后立即恢复（`code=battery-low`）；应用只结束合盖扩展，确认 0 后删标记、保留普通 `caffeinate` 会话，由 `awakeChanged` 保存降级结果，文案 `LidBatteryLow` |
| 12 | 会话中读不到电量 | 连续 3 次采样读不到或不可信 → 助手恢复（`code=battery-unknown`）；应用只结束合盖扩展（确认 0 后删标记、保留普通 `caffeinate` 会话），文案 `LidBatteryUnknown`。单次失败不恢复 |

### 5.3 生命周期对齐（顺序是硬要求）

**开启**（`startAwake` 内，`caffeinate` 成功之后）：

```
1. 前置检查：AwakeEnabled、内置电池、lidService 状态、无外部设置、电量（电池上需 > 下限）
2. caffeinate 启动（既有代码）
3. 连助手（必要时先安装 + 起 daemon，最多等 15 秒）
4. enable(deadline, minPercent) → 读回 1
5. 写 config.AwakeLid = true、config.AwakeSession = 本次会话、标记文件（§3.8）
6. 刷新界面：猫标 tooltip、卡片状态行、合盖开关
```

第 4 步失败：会话保留为普通常亮（`Lid=false`），`config.AwakeLid` 与标记都不写，界面 alert 对应原因（`battery-low` → `LidBatteryTooLow`）。**绝不**出现「合盖保持开了但常亮没开」。

**停止**（用户停止、常亮到期、跟随目标结束或退出）：

```
1. disable → 读回 0（失败则进入 lidRestoreFailed 并重试，界面常驻 alert；标记文件存在时才出现「强制恢复睡眠」入口，§3.8）
2. 读回 0 确认后才删标记文件
3. 停 caffeinate（既有 stopLocked）
4. 清 config.AwakeSession；config.AwakeLid 保留（记忆）
5. 刷新界面
```

先停合盖再停 `caffeinate`：中途崩溃时最坏结果是「普通常亮还在」这种无害状态，而不是「没有会话却 `disablesleep=1`」。

**统一收敛点**：普通常亮结束时，由 `awakeChanged`（`awake_app.go`）与 `syncLid` 恢复合盖。反向故障只降级合盖：`finishLidPoll` 遇到确认的合盖终止／助手异常时清除当前会话的 Lid 位并经 `awakeChanged` 保存，不调用 `awake.stop()`；未知读数在容忍期间保持此前状态。电量保护与助手硬上限仍由助手恢复合盖，普通常亮继续服从自己的截止时间／跟随目标。拔电不触发恢复。

**应用重启后的恢复**：`restoreAwakeAfterLaunch` 现在会按剩余时间恢复 `caffeinate`。合盖保持**不自动重开**：助手启动时已经无条件恢复过一次（§3.5），自动重开会在「助手反复崩溃」时形成循环且掩盖故障。改为：若上次会话带 Lid，界面在状态行给一次说明（`R05LidRestored`：上次的合盖保持已结束），用户点开关再开。**启动时无论上次有没有会话，都只读跑一次 `pmset -g`，并读一次自己的标记文件**：

| 标记文件 | `SleepDisabled` | 助手（在线时） | 启动后的行为 |
| --- | --- | --- | --- |
| 有 | 1 | 连不上／`svcBroken`／`svcNotRegistered` | 亮 `LidStaleSetting` + 「强制恢复睡眠」按钮（§3.8）；标记不删 |
| 有 | 1 | 在线且报 `on-foreign`（无 journal） | **以助手为准**：只提示 `LidForeign`，**不提供**按钮；标记是过期的，删掉（§3.8） |
| 有 | 1 | 在线且报 `restore-failed`（journal 在） | 亮 `LidRestoreFailed` + 按钮（不看标记） |
| 有 | 0 | 任意 | 删标记，不告警（助手已做过启动恢复） |
| 无 | 1 | 任意 | 只提示 `LidForeign`（可能不是我们设的），**不提供**按钮、不改值 |
| 无 | 0 | 任意 | 什么都不做 |

启动时助手可能还没起来：先只读跑一次 `pmset -g` 拿到值，并尝试连接助手；暂时连不上就按「助手不在线」处理（有标记且值为 1 才给按钮），后续轮询连上后按上表收敛。若发现 `on-foreign`，再把按钮撤掉并删标记。只有主动安装后的就绪确认使用 15 秒重试窗口。

这是助手起不来时唯一能告诉用户「你的机器现在不睡」的路径，全程只读，不改任何设置。

**更新（ADR 004）**：`update_view.go` 里 `RestoreAwake` 的记录方式不变，`awakeSession.Lid` 随之持久化；「重启更新」前先按上面「停止」的顺序恢复，恢复失败时不允许重启更新（与「有未保存 JSON 时先提示」同一类保护）。

### 5.5 供电与低电量下限（第 3 版采用，第 4 版补「读不到即恢复」）

| 项 | 内容 |
| --- | --- |
| 开启条件 | 接电源、电池都能开启。电池上开启要求电量 **>** 下限 |
| 开启时电量已 ≤ 下限 | 拒绝：助手回 `battery-low`，不开 journal、不写系统设置；应用显示 `LidBatteryTooLow`（「电量太低，先充电」）。此路径不弹任何授权 |
| 下限取值与百分比 | `config.AwakeLidBatteryMin`：10／20／30，默认 20；以 `enable.minPercent` 传给助手。助手另做 10..50 的协议校验。百分比一律 `Current Capacity / Max Capacity × 100`（`IOPSKeys.h`），不能把 Current 直接当百分比：它的单位由电源自己定，其它电源可能是 mAh（§3.2） |
| 电量读不到 | **偏向恢复，不偏向继续**，两个时刻分开。**开启时**读不到按 `battery-low` 拒绝（文本同 `LidBatteryTooLow`，不做任何写入：连「有没有超过下限」都不知道）；**会话中**读不到或读到的值不可信（命令失败、缺 `Max Capacity`、`Max Capacity` 为 0、算出值不在 0..100）时，助手**连续 3 次采样（约 90 秒）都读不到就恢复** `disablesleep=0` 并读回，`code=battery-unknown`；应用只结束合盖扩展、保留普通常亮，只说明一次 `LidBatteryUnknown`。单次抖动不恢复（避免一次读数失败就中断合盖任务），但**没有「一直继续」这一档**：继续等于让下限对一个看不见的电量失效 |
| 会话中拔电 | **不恢复**。`disablesleep` 保持 1，`caffeinate` 会话不变，界面不变。这是第 3 版与第 2 版最大的行为差异 |
| 会话中电量 ≤ 下限 | 助手每 30 秒采样一次（`pmset -g batt` 的 `NN%;`，百分比用 `Current Capacity / Max Capacity × 100` 交叉校验，备选 IOKit `IOPSCopyPowerSourcesInfo`，§4.1）；发现即自己恢复 `disablesleep=0`，`code=battery-low`。应用只结束合盖扩展（确认 0 后删标记、保留普通 `caffeinate` 会话），文案 `LidBatteryLow`。**为什么必须助手做**：合盖后应用看不到界面、也不保证自己还在跑，下限不能依赖应用侧的采样 |
| 12 小时硬上限 | 不变（§3.2）。两个上限取先到者：电量先到就 `battery-low`，时间先到就 `max-duration` |
| 风险 | 忘关 → 电池耗尽；`disablesleep` 让系统不进入「低电量休眠」，可能比预期更快没电；合盖 + 电池时机器可能在包里发热（§6.4 第 5 条一句说明，界面不加大段文案） |

## 6. 安全分析

### 6.1 资产与威胁模型

| 资产 | 被谁威胁 | 后果 |
| --- | --- | --- |
| root 权限（助手进程） | 本地其他进程（同用户或其他用户） | 提权到 root 就是全系统沦陷 |
| `disablesleep` 设置 | 任意本地进程、包装成 URL 的网页 | 机器不睡、耗电、过热；合盖散热受限 |
| 「谁在替用户做决定」 | 任意本地进程 | 用户以为系统会睡，实际不睡 |

模型假设：单用户 Mac、用户是管理员、应用放在 `/Applications`；攻击者能做的仅限于「以普通用户身份运行的本地进程」。**不**把「root 已被攻陷」或「内核被攻陷」纳入防护范围（防护不了）。

### 6.2 攻击面

| # | 攻击面 | 防护 |
| --- | --- | --- |
| 1 | 其他本地进程连接 socket 并冒充 Cubbix | `LOCAL_PEERTOKEN` + SecCode 校验 Team ID `P93GN4N3DC` 与 identifier `com.conteman.cubbix`；不通过即断开，不读请求体（§3.3） |
| 2 | 其他进程抢先绑定 socket 冒充助手，骗取 Cubbix 的连接 | `/private/var/run` 是 `root:daemon` `0775`、无 sticky：普通用户不能写，但 `daemon` 组成员可以删掉并抢绑（本轮已核对该目录权限位）。因此安全边界**不在文件权限**：应用连上后校验对端签名（只校验 Team ID，§3.3），不一致即断开并只记一条不带对端信息的日志——不给用户看，避免被刷成噪音。`chmod 0666` 只在 `Listen` 成功后做，避免改到别人抢先建的 inode |
| 3 | 通过 IPC 注入命令／参数 | 协议只有 5 个固定 `op`、字段值全部枚举、整数范围或 RFC3339（`max-duration`、`battery-low` 只是响应值）；`pmset` 参数是常量；**助手**从不调用 shell；单行上限 8 KiB；拒绝后立刻断开。应用侧的常量脚本只有三份（§4.4 安装与更新、§3.6.3 卸载、§3.8 强制恢复），脚本字符串里没有任何来自外部输入的部分 |
| 4 | 伪造 journal 让助手恢复（或阻止恢复） | journal 在 root 0700 目录、0600 文件；普通用户无法写；写盘顺序（journal 先落盘、读回 0 之后才删）保证本功能不会留下「值 1 且无 journal」的自有会话；助手起不来的情况由 §3.8 兜住（只读告警 + 用户手动恢复） |
| 5 | 网页／其他应用用 `cubbix://awake?lid=1` 静默开启 | 必须已授权；必须带 1..480 的 `minutes`；不弹鉴权；开启后状态行与 tooltip 可见；`FeedbackMode` 关闭时也强制一条系统通知——这是 §8.1 例外清单里的**第二条**（异常类之外唯一被列入例外的成功提示）。`present()` 现在对 `mode == "off"` 直接返回，所以这条通知要走一条显式的强制路径，实现时别只加个 `Danger` 字段 |
| 6 | 用 URL 反复触发鉴权弹窗骚扰 | URL 路径**永不**调用 `Register()`；注册只能由用户点击卡片／命令面板产生 |
| 7 | 助手二进制被替换 | 复制后在**同一条 root 脚本里**校验副本的 Team ID 与签名 identifier，失败即删副本、不 bootstrap（§4.4.1）；副本落在 root 拥有的 `/Library/PrivilegedHelperTools`（root:wheel 0755），校验后普通用户改不动；应用更新后由「助手需要更新」提示再走一次同一脚本 |
| 8 | 应用成为「通用提权代理」 | 助手不接受路径、命令、任意 `pmset` 参数（§3.1 白名单）；应用侧不接受 URL 传入的任何标识或参数名 |
| 9 | 拒绝服务（一直占着 `enable`） | 每个连接只能有一个会话；`busy` 时不重复改动系统设置；连接与请求都有超时 |
| 10 | 日志泄露 | 助手日志只写状态迁移、`reason` 码与读回值，不写进程名、路径、用户名、IPC 原文 |
| 11 | 伪造「我方遗留」标记，诱导一次「强制恢复睡眠」（残余风险） | 标记在用户目录、可写，普通进程能伪造。**助手在线时以助手为准**：助手报 `on-foreign`（无 journal）就只提醒、不提供按钮，并删掉那个过期标记（§3.8），伪造路线在此失效。只有助手**不在线**（被关掉、副本被删、安装损坏）时分不出伪造与真遗留，此时后果上限是一次常量 `/usr/bin/pmset -a disablesleep 0`：把**别的工具**设的 1 改回 0**一次**（用户可自己再设回），不能关掉睡眠、不能执行其它命令、不能提权；root `0700` 的 journal 伪造不了，所以不会变成「无限期不睡」。这是有意接受的残余风险：换来的是一条不依赖助手的恢复退路，而合盖不睡时 alert 看不见 |

### 6.3 最坏情况

| 情况 | 结果 | 界面必须做的 |
| --- | --- | --- |
| 应用被强杀 | 助手在 15 秒内（EOF 通常 < 1 秒）恢复 | 无（应用已死） |
| 应用与助手同时被强杀 | `disablesleep` 保持 1；launchd 会在 `ThrottleInterval`（10 秒）后重启助手，重启时无条件恢复 | 无（两者都不在），但下次启动应用要读回并说明 |
| 用户在系统设置里关闭／停用助手，会话进行中 | daemon 被卸载 → 立刻没人负责恢复；`disablesleep` 可能保持 1，直到助手下次启动 | 应用检测到断连 → 常驻 alert「合盖保持已中断」，标记还在时 tooltip 里出现「强制恢复睡眠」按钮（§3.8）；应用同时尝试一次重新安装 |
| helper 被 `unregister` 且不再启动（卸载） | 同上，且无人恢复 | §3.6 规定「恢复成功才允许停用」；做不到时拒绝停用并解释 |
| 助手起不来（用户关掉、副本被删、安装损坏） | 值可能停在 1，而且**没有进程会自己恢复它**；合盖之后不睡，alert 也看不见（盖着） | 下次启动应用时：标记文件在 + 只读 `pmset -g` 为 1 → `LidStaleSetting` + 「强制恢复睡眠」按钮（§3.8）。这是本文档唯一承认的「必须靠用户按一下」的路径 |
| 系统冻结／内核崩溃 | 断电重启后值是否仍为 1 取决于设置是否持久（**需实测**，§4.6 第 5 项） | 应用启动时只读 `pmset -g` 与标记：两者都在按上一条处理；只有 1 无标记则只提醒（`LidForeign`），不提供按钮；有标记但助手在线报 `on-foreign` 时也只提醒（以助手为准，§3.8） |
| 电量耗尽 | 关机；合盖 + 电池时机器可能在包里持续发热 | 下限默认 20% 由助手强制恢复（§5.5）；界面不为此加常驻说明，只在恢复时发一次 `LidBatteryLow` |

### 6.4 残余风险如何告知

1. 首次授权（安装）前，卡片状态行的 alert tooltip 写明「合盖保持需要一次系统授权，之后就绪」——不写长段说明。
2. 异常状态下 tooltip 给出**「强制恢复睡眠」按钮**（一次管理员授权，§3.8），不是一段要用户自己粘贴的命令。不加常驻说明行：只在异常时出现，符合 AGENTS 的低信息密度；按钮旁一行小字说明它只把合盖睡眠改回开启。**外部设置（助手报 `on-foreign`）只提醒不提供按钮**，有没有标记都一样，避免一键改掉别人的设置。
3. `README.md` 与 CHANGELOG 里各一句：合盖保持会修改系统设置；异常时用应用里的「强制恢复睡眠」。
4. 不承诺「一定能恢复」：文档与文案都不用「保证」。助手消失时确实需要用户按一次，文案要说清「现在需要你按一下」，不暗示系统会自己好。
5. 合盖 + 电池时机器可能在包里发热、耗电更快：只在 README / CHANGELOG 的同一句里带一笔（“电池上电量降到下限会自动结束”），**界面不加大段说明**。低信息密度优先，风险由低电量下限与 12 小时上限兜住。

### 6.5 明确禁止的做法

- 不用 `sudoers` 白名单或任何长期免密规则（调研已评估：授权长期存在，且仍需 watchdog）。
- 不把 `osascript with administrator privileges` 当作**自动**恢复手段（每次都要密码、且没人保证用户会按）。允许的只有**四处手动授权动作、三份常量脚本**：安装（§4.4）、更新（§3.6.2，与安装同一条脚本）、卸载（§3.6.3）与「强制恢复睡眠」（§3.8）。四处都不在后台、不在 URL、不在定时器里。
- 不把强制恢复做成“读到 1 就给按钮”：标记不能压过助手，助手在线报 `on-foreign` 时只提醒（即使标记在），不改外部设置（§3.8）。
- 不把 `disablesleep` 的恢复挂到「应用退出回调」上当成唯一手段。
- 不让助手接受任何形式的「执行命令」「设置其他电源参数」。
- 不在测试里真的调用 `pmset`、不在测试里注册任何 daemon（§7.4）。
