## 结论摘要

| 项 | 结论 |
| --- | --- |
| 实现手段 | `pmset -a disablesleep 1/0`，需要 root，是系统设置，进程退出不自动复原 |
| 执行者 | 独立的特权助手（root LaunchDaemon），由 launchd 托管 |
| 与现有常亮的关系 | **附加开关**，不是第三种模式；`caffeinate` 会话与 `disablesleep` 会话同生命周期、同截止时间 |
| 供电策略（先按此写） | 只在接电源时可开启；会话中改用电池立即恢复。备选「允许电池」见 §5.5 与 §8.4 |
| 授权 | 需要用户一次管理员授权（SMAppService 注册 + 系统设置允许）；未授权时功能不可用，界面只用图标与 tooltip 表达 |
| IPC | `/var/run` 下的 Unix domain socket，换行分隔 JSON；**必须**用 audit token + SecCode 校验对端是同 Team ID 的 Cubbix |
| 恢复触发 | 到期、用户停止、正常退出、连接断开（含强杀）、心跳过期、改用电池、助手重启、开机 |
| 最坏情况 | 助手与应用都被杀或助手被禁用时，`disablesleep=1` 可能保留到下次助手启动；界面必须给出可复制的修复命令 |
| 关键阻塞 | **`mygo build` 目前产不出 `Contents/Library/LaunchDaemons/`**（§4.3），SMAppService 标准布局要等 MyGo 支持或改用 §4.4 的 T3 安装层 |
| 未证实项 | 实体合盖、拔电、强杀、重启、真实助手、授权弹窗全部只列在维护者实测清单（§7.3）里，自动化测试一律打桩 |

## 1. 使用场景与用户路径

### 1.1 场景

维护者的原话是「盒盖保持任务继续的功能很重要，现在用起来总是忘记当前不支持盒盖工作」。因此本功能的第一目标不是「多一个开关」，而是**让「合盖是否安全」这件事在开启的那一刻就看得见**。

| 场景 | 诉求 | 现状 |
| --- | --- | --- |
| 合盖跑 Agent 任务（最常见） | 合上盖子，`codex`/`claude` 这类终端任务继续跑完 | 不合盖就等于中断，只能开着盖子离开 |
| 会议室/背包里短时编译 | 合盖带走，几分钟后回来继续 | 同上 |
| 桌面 Mac（无内置屏） | 无此需求 | 不应出现任何相关控件 |

### 1.2 入口与步数

合盖保持只有一个动作：**打开或关闭**。它跟随当前常亮会话，不单独计时。

| # | 入口 | 操作 | 步数 | 说明 |
| --- | --- | --- | --- | --- |
| 1 | 卡片面板的合盖开关 | 点猫标 → 点合盖开关 | 2 | 未开启常亮时点它 = 用记忆设置开启常亮 + 打开合盖保持（§5.2 规则 4） |
| 2 | 先开常亮再开合盖 | 点猫标 → 点 `[1h]` → 点合盖开关 | 3 | 常见路径；第二次点击就是「别再忘了」的检查点 |
| 3 | 命令面板 | `⌥.` → 输入 `常亮 2h 合盖` → `↩` | 3 | 参数后缀 `合盖`／`lid`（§5.4） |
| 4 | 命令面板动作 | `⌥.` → `常亮 2h` → `⌘K` → 点「合盖也保持」→ 点「仅保持任务」 | 5 | 动作列表里两行都是勾选项，先勾合盖再执行主操作 |
| 5 | 全局快捷键 + 已记住的合盖 | `⌃⌥⌘K` | 1 | 快捷键不开合盖；只有 `config.AwakeLid` 为真时才连带开启（§5.2 规则 6） |
| 6 | URL scheme | `cubbix://awake?minutes=120&lid=1` | 1 | 给 Raycast／快捷指令用，限制见 §5.4 |

关闭路径：点合盖开关、点总开关（停止常亮）、按 `⌃⌥⌘K` 停止、`cubbix://awake/stop`、退出 Cubbix；以上任何一条都同时恢复 `disablesleep`（§5.3 的顺序要求）。

### 1.3 界面表达（低信息密度，图标为主）

| 位置 | 表达 |
| --- | --- |
| 卡片面板 · 常亮卡片新增的一行 | `[laptop 图标]` + 开关（右对齐）。常态无文字标签，tooltip 为「合盖也保持」（键 `R05Lid`，英文 `Awake with lid closed`，见 §8.1）。开关打开时底色 `ColorAccent`、拇指 `ColorThumb`，与总开关同一套写法（`menubar_panel_view.go` 的 `panelAwakeCard`） |
| 卡片面板 · 状态行 | 会话运行且合盖保持中：`仅保持任务 · 合盖也保持 · 剩余 1:24`（模式 · `R05Lid` · 既有后缀）。超出面板宽度时按 `panelStatus` 既有的 `SingleLine().Ellipsis("…")` 截断 |
| 卡片面板 · 状态行右侧的提醒按钮 | **会话运行、合盖保持未开**时，状态行右端出现一个 `laptop` 图标按钮（`SizeIcon`，`ColorTextSecondary`），tooltip 为「合盖后会睡，点此保持」（键 `R05LidHint`），点击即打开合盖保持。这是「不再忘记」的主载体：不写句子，只在有会话且未开时出现一个可点的图标 |
| 猫标 | 第一版**不加第三态图标**（见 §8.2 的品牌前提）；猫标 tooltip 用 `awakeStatus` 的完整文案，含「合盖也保持」，这是零成本且不依赖品牌资产的状态出口 |
| 命令面板 | `awake.start` 的动作列表 Group 1 增加勾选项「合盖也保持」（`Checked` = `config.AwakeLid`），图标 `laptop`；行内 hint 不变（hint 只讲时长，见 003 §4.3） |
| 设置页 · 常亮格子 | 不加行，`awake_view.go` 不改。合盖保持是会话开关，不是偏好设置（唯一可能的偏好在 §8.4 第 2 项） |

卡片内的顺序固定为：标题行 + 总开关 → 模式分段器 → 时长药丸 → **合盖行** → 状态行。合盖行放在药丸之后、状态行之前：用户先决定「多久」，再决定「这次要不要合盖」，最后一行就是这件事的结果与提醒。`menubar_panel.go` 的 `awakeCardHeight` 在 `rows` 增加 `lid` 时补上 `Space8 + SizeNavHeight`。

合盖行的显隐规则只有一条：`lidCapable()` 为真（有内置屏、打包运行、helper 二进制存在）就**一直画**；暂时不可开启（未授权、电池、外部设置）时置灰可读，**不隐藏**——隐藏会让卡片高度跳动，也会让「为什么会睡」变得无从发现。只有 `lidCapable()` 为假（桌面 Mac、开发构建）时整行不画。

异常态一律复用既有约定：`triangle-alert`（`ColorDanger`）+ tooltip 讲原因（`panelStatus` 已有这套代码），不用整句错误行。开启过程中在开关位置画 `loader-circle`（AGENTS「进行中 loader」）。

### 1.4 为什么这样能「不再忘记」

1. **开关常驻在卡片里**，不是藏在子菜单：想合盖之前点一次猫标就能看见它是开还是关。
2. **有会话未开合盖时，状态行多一个可点图标**：这是唯一会在用户「已经开了常亮」这个正确时机主动出现的东西。
3. **开启瞬间的状态行与 tooltip 带「合盖也保持」**：用户合盖前最后一次看菜单栏图标时，tooltip 里有答案。
4. **明确不做**：常亮未开启时推送「你还没开合盖保持」这类通知——那是骚扰，而且没有会话时合盖保持本来就没有意义。

### 1.5 明确做不到的事

**软件无法在合盖前提示。** 没有任何公开 API 在「用户即将合盖」时通知应用；`NSWorkspaceWillSleepNotification` 之类的通知发生在系统已经决定睡眠之后（本规格未使用它）。因此「忘记开」只能靠 §1.4 的事前显眼，不能靠事前弹窗。这一条必须写进验收说明，避免维护者以为是缺陷。

## 2. 首次授权流程

### 2.1 事实前提

| 事实 | 依据 |
| --- | --- |
| 需要 macOS 13+（`SMAppService` 自 13.0 起可用） | Apple `SMAppService` 文档的 availability：macOS 13.0+；本机 SDK 头文件 `SMAppService.h` 的 `API_AVAILABLE(macos(13.0))` |
| 应用必须是签名的，含 LaunchDaemon 的应用必须被公证 | `SMAppService.h` 类注释：「Apps that use SMAppService APIs must be code signed.」「Apps that contain LaunchDaemons must be notarized.」；Cubbix 走 Developer ID + 公证，见 `mygo.json` 的 `macos.signingIdentity`／`notarize` 与 ADR 004 |
| 注册 LaunchDaemon 需要用户管理员授权 | `SMAppService.h` 的 `registerAndReturnError:` 讨论：「the LaunchDaemon will not be bootstrapped until an admin approves the LaunchDaemon in System Settings」；Apple 迁移文档：「Launch daemons require authentication by the user because the user is authorizing a system level-process」 |
| 用户可以在系统设置里关掉它 | 同上；状态变成 `SMAppServiceRequiresApproval` |
| 应用要引导用户去对应设置页 | `SMAppService.openSystemSettingsLoginItems()`，Apple 建议在提示用户后调用 |
| 应用更新了 plist 或可执行文件后必须重新注册 | `SMAppService.h` 类注释：「If an app updates either the plist or the executable for a LaunchAgent or LaunchDaemon, the SMAppService must be re-registered or it may not launch」 |
| 应用当前声明的最低系统是 12.0 | `mygo.json` 没有 `macos.minimumSystemVersion`，MyGo 默认 12.0（`mygo@v0.6.2/docs/configuration.md` 的 `macos` 表）。因此 T1 形态下合盖保持只在 13+ 可用；若维护者愿意把最低版本提到 13.0，可以省掉一个分支 |

### 2.2 授权状态机（应用侧）

`lidService` 抽象出五件事：`Status()`、`Register()`、`Unregister()`、`OpenSettings()`、`HelperPath()`（§4.4 给了两套实现）。

| 状态 | 触发 | 界面 | 允许开启合盖保持 |
| --- | --- | --- | --- |
| `svcUnavailable` | `mygo.IsDev()` 为真、非打包运行、无内置屏、系统 < 13、或 helper 二进制缺失 | 合盖开关注灰，tooltip `LidUnsupported`／`LidDevBuild` | 否 |
| `svcNotRegistered` | `status == notRegistered` | 开关可点；点击先走注册 | 否，需先注册 |
| `svcEnabling` | 注册中／等待 daemon 起来 | 开关位置画 loader | 否 |
| `svcRequiresApproval` | `status == requiresApproval`，或注册后仍未生效 | 开关回到关闭，状态行 alert：`LidAuthNeeded`，tooltip 里带「去系统设置允许」按钮（`LidAllow`），点击调 `OpenSettings()` | 否 |
| `svcDenied` | `register()` 返回 `kSMErrorLaunchDeniedByUser`（用户点了取消） | alert：`LidDenied`；不再自动弹鉴权，必须用户再点开关 | 否 |
| `svcBroken` | `kSMErrorInvalidSignature`／`kSMErrorToolNotValid`／`kSMErrorInvalidPlist`／`kSMErrorJobPlistNotFound` | alert：`LidServiceBroken`（安装损坏），tooltip 给修复指引 | 否 |
| `svcEnabled` | `status == enabled` 且 `hello` 握手成功 | 正常 | 是 |

要点：

- **注册只在用户主动点击时发生**，不在启动、不在 URL 路径（§6.2 第 6 条）。启动时只读状态，不弹鉴权。
- 注册成功后 `status` 可能仍是 `requiresApproval`：这是系统要求用户去「系统设置 › 通用 › 登录项」放行。界面不写整段说明，只给一个按钮（`R05LidAllow`）+ tooltip 两句话。
- 用户放行后**不需要重启 Cubbix**：应用每 5 秒（会话中）或每次展开面板时重读一次 `status`，变 `enabled` 就更新。
- 授权状态与被禁状态都要在**下一次开启时**重新读，不能缓存成「已授权」一辈子。

### 2.3 未授权/被拒/被关闭时的表现

| 场景 | 表现 |
| --- | --- |
| 未注册，用户点开关 | 弹系统鉴权（Touch ID／密码）→ 成功则继续开启流程；取消则 `svcDenied`，`disablesleep` 保持 0 |
| 已注册未放行，用户点开关 | 不弹鉴权，只亮 alert 与「去系统设置允许」按钮 |
| 已放行、正在运行时用户在系统设置关掉开关 | daemon 被 launchd 卸载 → socket 断开。应用侧：会话中每 5 秒 `status` 失败 → `lidHelperGone`，状态行 alert「合盖保持已中断」，tooltip 给原因与修复命令；`disablesleep` 的恢复由助手下一次启动时的启动恢复完成（§3.5），这也是 §6.3 的残余风险之一 |
| 被拒后再次点击 | 允许再次注册（系统可能不再弹框而是直接拒绝，Apple TN2065 说明鉴权可能被缓存，见调研材料），因此只提示不改状态 |

## 3. 特权助手设计

### 3.1 职责边界（白名单）

助手只做四件事，多一件都不做：

1. 读 `disablesleep` 现值（`pmset -g` 的 `SleepDisabled` 行）。
2. 写 `disablesleep`（`pmset -a disablesleep 1|0`），并**读回确认**。
3. 维护会话日志（root 拥有的 journal），含截止时间与恢复目标值。
4. 在 §3.5 的触发条件下自行恢复。

明确不做：不读用户文件、不执行用户提供的命令或参数、不代理任意 `pmset` 参数、不接受路径、不联网、不监听 TCP、不写日志到用户可写的目录、不做 sleep/wake 之外的电源设置（`sleep`、`disksleep`、`hibernatemode` 一律不碰）。

助手由 launchd 的**系统域**启动，因此以 root 运行（launchd 语义；本机未安装真实 daemon 验证，见 §7.3）。它的全部状态只有一个 journal 文件与一条连接，没有其他持久状态。

调用 `pmset` 时参数是写死的常量：`exec.Command("/usr/bin/pmset", "-a", "disablesleep", value)`，不经 shell，不带任何来自 IPC 的字符串。

### 3.2 会话模型

一次「合盖保持」= 助手里的一个会话，它有四个要素：

| 要素 | 规则 |
| --- | --- |
| 租约 | 只在一条**活着的连接**上存在。应用每 5 秒发一次 `ping`；助手 15 秒收不到任何请求即判定租约过期 → 恢复 |
| 截止时间 | 由应用在 `enable` 里给出，等于当前常亮会话的 `End`；不限时／跟随进程时为空，此时只有租约与 §8.4 待决定 3 的硬上限 |
| 恢复目标值 | `previous` 字段，必须是 0（开启前读到的值）；非 0 一律拒绝，绝不覆盖别人的设置 |
| 日志（journal） | `/Library/Application Support/com.conteman.cubbix.helper/session.json`，目录 0700、文件 0600，root:wheel |

journal 写入顺序是硬约束：

```
1. 读现值 → 必须是 0，否则回 foreign-setting 并退出
2. 确认电源是 AC，否则回 battery 并退出
3. journal 落盘（tmp 文件 → fsync → rename → fsync 目录）
4. pmset -a disablesleep 1
5. 读回，必须为 1，否则回 pmset-failed 并尝试撤销 0、删 journal
6. 回 ok（只在读回成功之后）
```

恢复顺序同样固定：

```
1. pmset -a disablesleep 0
2. 读回，必须为 0
3. 删 journal（先 unlink，再 fsync 目录）
4. 失败则保留 journal，按 §3.4 重试
```

第 3 步之前崩溃 → journal 在、值已是 0 → 下次启动只删 journal（幂等）。第 3 步之后崩溃 → 值仍是 1 但 journal 在 → 恢复。任何时刻都不存在「值 1 且没有 journal」的自有会话。

### 3.3 IPC

**推荐 Unix domain socket，不推荐 XPC Mach service。** 理由与依据：

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| XPC Mach service | 系统级对端身份令牌（`xpc_connection_get_audit_token`）、launchd 按需唤醒 | 要在无 CGO 的 Go 里手写 `libxpc` 全流程：`xpc_connection_create_mach_service`、`dispatch_queue_create`、`xpc_connection_set_event_handler`（block）、`xpc_dictionary_*` 序列化。`objc.NewBlock` 与 `purego.NewCallback` 都存在（`purego@v0.11.1` 的 `objc/objc_block_darwin.go`、`purego.go` 的 `NewCallback`），MyGo 也已有 `dispatch_queue_create`／`dispatch_sync_f` 的绑定（`mygo@v0.6.2/internal/darwin/watch.go`），**但没有一行 XPC 代码可参考，且整条链无法在本机验证** | 不选 |
| Unix domain socket + `LOCAL_PEERTOKEN` | Go 标准库 `net.Listen("unix")`／`net.Dial("unix")` 承担全部传输；连接断开由 `read` 返回 0 直接感知，天然满足「客户端被强杀要恢复」；对端身份用 `getsockopt(SOL_LOCAL, LOCAL_PEERTOKEN)` 拿到 audit token（本机 SDK `sys/un.h` 定义 `LOCAL_PEERTOKEN 0x006`），再交给 SecCode 校验，效果与 XPC 的 audit token 等价；协议是纯文本，测试可以完全脱网跑 | 需要一次 `getsockopt` 的 syscall 与五个 Security 函数绑定 | **采用** |

传输细节：

| 项 | 规定 |
| --- | --- |
| 路径 | `/var/run/com.conteman.cubbix.helper.sock`（目录 root:wheel，普通用户不可创建） |
| 权限 | 0666。**故意**放开连接，安全由代码签名校验兜底，而不是靠文件权限（多用户机上没有共同组可用） |
| 创建者 | 助手自己 `net.Listen` 前先 `os.Remove` 残留 socket，再 `chmod 0666` |
| 编码 | 换行分隔的 JSON，一行一条；单行上限 8 KiB，超过即断开；不使用 HTTP |
| 超时 | 连接建立 3s；单次读写 5s；空闲 15s 视为租约过期（§3.2） |
| 并发 | 同时只服务一条连接。新连接到来时：旧连接已断开或租约已过期 → 接管；否则 `enable` 回 `busy` |
| 常量 | 全部来自固定常量，不接受任何来自对端的路径、命令、`pmset` 参数 |

请求／响应（固定字段，未知字段忽略）：

```json
{"v":1,"id":"8f3c…","op":"hello","client":"cubbix/0.4.0"}
{"v":1,"id":"8f3c…","op":"status"}
{"v":1,"id":"8f3c…","op":"enable","deadline":"2026-11-03T12:30:00Z"}
{"v":1,"id":"8f3c…","op":"disable","reason":"user"}
{"v":1,"id":"8f3c…","op":"ping"}
```

```json
{"v":1,"id":"8f3c…","ok":true,"protocol":1,"helper":"0.4.0","state":"off",
 "value":0,"power":"ac","deadline":null,"code":""}
```

| 字段 | 取值 |
| --- | --- |
| `op` | 只接受 `hello`、`status`、`enable`、`disable`、`ping`，其余回 `bad-request` 并断开 |
| `state` | `off`、`on-ours`、`on-foreign`、`restoring`、`restore-failed` |
| `code` | `ok`、`foreign-setting`、`battery`、`busy`、`pmset-failed`、`restore-failed`、`bad-request`、`protocol-mismatch` |
| `value` | 读回的 `disablesleep`，0 或 1；读不到时为 `null` |
| `power` | `ac`、`battery`、`unknown` |
| `deadline` | 已是 RFC3339（UTC）；`enable` 时允许 `null`（不限时） |
| `helper` | 助手版本，用于 §3.6 的「助手需要更新」判断 |

`deadline` 校验：必须晚于 `now`，且不超过 `now + awakeMinutesMaximum 分钟`（与 003 §4.1 的时长上限同一口径；越界即 `bad-request`）；不限时用 `null`，助手按租约与硬上限看管。`disable` 的 `reason` 只用于日志与下次 `status` 的说明，不影响行为。

**对端校验（硬要求）**：

1. `getsockopt(fd, SOL_LOCAL /*0*/, LOCAL_PEERTOKEN /*6*/)` → 32 字节 `audit_token_t`。
2. `SecCodeCopyGuestWithAttributes(NULL, {kSecGuestAttributeAudit: CFData(32B)}, 0, &guest)`（该属性的取值是含 audit token 的 `CFData`，见 Apple 对 `kSecGuestAttributeAudit` 的说明；本机 SDK 头文件只声明符号）。
3. `SecRequirementCreateWithString("anchor apple generic and certificate leaf[subject.OU] = \"P93GN4N3DC\" and identifier \"com.conteman.cubbix\"", 0, &req)`。
4. `SecCodeCheckValidity(guest, 0, req)`；非 `errSecSuccess` → 立刻断开，不读请求内容，不记 payload。
5. 校验放在 `Accept()` 之后、读第一行之前；校验通过后连接可以长期使用（audit token 不受 PID 复用影响，这是相对 `LOCAL_PEERPID` 的关键优势）。

Team ID `P93GN4N3DC` 与 identifier `com.conteman.cubbix` 写成助手侧常量。ad-hoc 签名的开发构建因此天然被拒——这正是我们要的（§2.2 的 `LidDevBuild`）。

反向校验（应用 → 助手）用**只校验 Team ID** 的宽松版本：助手是裸 Mach-O，`codesign` 会给它一个由文件名派生的 identifier，写死 identifier 会在改名或换安装层时误伤；而在 `/var/run` 下绑定该 socket 本身就需要 root（§6.2 第 2 条），冒充者已经越出本规格的威胁模型。

`CFData`／`CFString` 的构造走 `purego` 绑定 CoreFoundation（`CFDataCreate`、`CFStringCreateWithCString`、`CFRelease`），与 `mygo@v0.6.2/internal/darwin/cf.go` 的 `loadCF` 同一手法；`kSecGuestAttributeAudit` 这类**导出常量是变量**，必须 `Dlsym` 后二次解引用（`**(**uintptr)`），MyGo 读 `kCFRunLoopCommonModes` 时就是这么做的（同文件）。这条链**未在本机跑通**，见 §4.6。

### 3.4 恢复与重试

| 触发 | 处理 |
| --- | --- |
| `disable` 请求 | 立即恢复，回 `ok`（含读回值） |
| 连接 EOF（应用正常退出、崩溃、被 `SIGKILL`） | 立即恢复 |
| 租约过期（15 秒无请求） | 恢复 |
| 截止时间到 | 恢复 |
| 改用电池（5 秒一次采样） | 恢复，`reason = battery`，`status` 里带上原因 |
| 助手启动（launchd 重启、开机） | 若有 journal → 先恢复，再开始监听；见 §3.5 |
| 恢复本身失败 | **保留 journal**，按 1s、2s、5s、10s、30s、之后每 60s 重试，`state = restore-failed`；每次 `status`／`ping` 都回这个状态，应用侧据此显示异常 |

恢复失败不静默：应用侧会话中每 5 秒 `ping` 一次，`state` 不是 `on-ours`／`off` 就切到异常界面，tooltip 里给出可复制的手工修复命令 `sudo pmset -a disablesleep 0`（这是安全提示，允许出现文字）。

### 3.5 助手重启与开机

launchd 配置（T3 用 `Program`，SMAppService 用 `BundleProgram`）包含 `RunAtLoad` 与 `KeepAlive`，所以助手在开机、被强杀、退出非 0 时都会重新起来（`launchd.plist(5)` 的 `KeepAlive`／`RunAtLoad` 两节）。

启动顺序是硬约束：

```
1. 读 /Library/Application Support/com.conteman.cubbix.helper/session.json
2. 不存在 → 读现值；值为 1 且不是我们的 → state=on-foreign（只报告，绝不修改）
3. 存在 → 无论截止时间是否已过，一律先恢复 0 并读回，成功才删 journal
4. 恢复失败 → 保留 journal，state=restore-failed，继续跑重试；**此时仍然监听**（应用连上来能看到真实状态）
5. 起监听、起计时器
```

「助手重启要恢复」优先于「保持会话连续性」：宁可让合盖保持短暂失效，也不留下一个没人负责的 `disablesleep=1`。应用侧不自动重开（§5.3 的「应用重启后的恢复」），由用户点一次开关，避免「助手反复崩溃 + 应用反复重开」的循环把异常藏起来。

开机时助手还会在无 journal 的情况下读一次现值，用于 `on-foreign` 报告；这里**不做**任何修复。

### 3.6 更新、卸载与停用

| 时机 | 顺序 |
| --- | --- |
| 应用正常退出 | `disable`（等读回确认）→ 停 `caffeinate`（`main.go` 的 `beforeQuit` 现在先停常亮，本轮改为先停合盖）→ 不 `unregister`（下次开机还要它做补救恢复） |
| 应用更新（ADR 004 的「重启更新」） | 重启前：`disable` + 读回确认 → 更新 → 重启后：读 `status`；若 `requiresApproval` 或在 `hello` 里发现 `helper` 版本与内嵌版本不一致，显示「助手需要更新」，用户点一次开关触发重新安装／重新注册（`SMAppService.h`：plist 或可执行文件更新后必须重新注册） |
| 卸载／停用 | 关闭「常亮」格子（`changeAwakeEnabled` 的 `false` 分支）→ `disable` + 读回 → `unregister()`（T3 为 `bootout` + 删除 plist 与 `/Library/PrivilegedHelperTools` 副本，同样一次授权）→ 只有恢复成功才继续；恢复失败就**不允许**停用，并提示原因（否则会留下一个没人能恢复的 1） |
| 助手二进制更新（T3） | 应用启动时比对 `hello` 返回的 `helper` 与内嵌版本；不一致 → 状态行 alert「助手需要更新」，点击后一次授权完成「恢复 → 停 daemon → 覆盖副本 → 重新 bootstrap」 |

### 3.7 完整状态机

应用侧 `lidController` 只用这几个状态，界面完全由它派生：

| 状态 | 含义 | 入口 | 出口 |
| --- | --- | --- | --- |
| `lidOff` | 未开启 | 初始；`disable` 成功；会话结束 | 用户点开关 → `lidEnabling` |
| `lidEnabling` | 已发 `enable`，等读回 | 点开关／命令／URL | 读回 1 → `lidOn`；失败 → `lidError` |
| `lidOn` | 读回确认 1，租约有效 | `lidEnabling` 成功 | 会话结束／用户关闭／异常 → `lidStopping` |
| `lidStopping` | 正在恢复 | 所有结束路径 | 读回 0 → `lidOff`；失败 → `lidRestoreFailed` |
| `lidRestoreFailed` | 恢复未确认，助手在重试 | `lidStopping` 失败 | 助手恢复成功 → `lidOff`；用户点「重试」→ `lidStopping` |
| `lidHelperGone` | 连接断开且无法重连 | 心跳失败、`status` 连续失败 | 助手回来 → `lidOn`（若仍是我们的会话）或 `lidOff` |
| `lidBlocked` | 条件不满足（未授权／电池／外部设置／不支持） | 开启前检查 | 条件变化后用户再试 |
| `lidError` | 开启或恢复失败并带原因 | 各失败路径 | 用户重试 |

`on-foreign` 是 `lidBlocked` 的一种：`code=foreign-setting`，界面提示「系统里已有别的工具把合盖睡眠关掉了，Cubbix 不会覆盖」，且**不**提供「强行覆盖」按钮。

## 4. Go / MyGo 可行性（查证结果）

### 4.1 助手能否用 Go 写、不用 CGO

| 助手要做的事 | 无 CGO 的做法 | 依据 | 结论 |
| --- | --- | --- | --- |
| 读写 `disablesleep` | `exec.Command("/usr/bin/pmset", …)` | 调研轮已在本机用 root 验证 0→1→0；`pmset` 写设置需要 root | **可行** |
| 读现值 | `pmset -g` 输出里的 `SleepDisabled` 行（本轮以普通用户只读确认会打印该行） | 本机只读观察 | **可行** |
| 读电源 | `pmset -g batt` 的 `'AC Power'`／`'Battery Power'`（仓库已有 `batteryPower`）；或 purego 调 IOKit `IOPSGetProvidingPowerSourceType` | `awake_app.go` 的 `batteryPower`；`mygo@v0.6.2/internal/darwin/cf.go` 的 `iopsGetProvidingPowerSourceType` 绑定 | **可行** |
| Unix socket 服务 | `net.Listen("unix", …)` | Go 标准库 | **可行** |
| 对端 audit token | `syscall.Syscall6(SYS_GETSOCKOPT, …)` 或 purego 调 libc `getsockopt` | 本机 SDK 的 `sys/un.h` 定义 `LOCAL_PEERTOKEN 0x006`（注释为「retrieve peer audit token」） | **可行，未跑通** |
| 代码签名校验 | purego 绑定 Security 框架（`SecCodeCopyGuestWithAttributes`、`SecRequirementCreateWithString`、`SecCodeCheckValidity`）与 CoreFoundation（`CFDataCreate`、`CFStringCreateWithCString`、`CFRelease`） | 本机 SDK `SecCode.h` 声明这些函数与 `kSecGuestAttributeAudit`；MyGo 已有 CoreFoundation/IOKit/libdispatch 的 purego 绑定先例 | **可行，未跑通** |
| 定时器／信号 | Go 标准 | — | **可行** |

结论：**助手可以是纯 Go、`CGO_ENABLED=0` 的 Mach-O 可执行文件**，但「Security 框架 + audit token」这一段是本规格唯一的高风险 FFI，必须在实现时先做一个隔离的小实验跑通（不进仓库、不留本机路径），再写进产品代码。跑不通时的退路见 §4.6。

### 4.2 `SMAppService.daemonServiceWithPlistName:` 需要的 bundle 结构

| 要求 | 依据 |
| --- | --- |
| plist 必须在**调用方 app bundle** 的 `Contents/Library/LaunchDaemons/` 下 | `SMAppService.h` 的 `daemonServiceWithPlistName:` 讨论；Apple 迁移文档示例 `$APP.app/Contents/Library/LaunchDaemons/com.example.daemon.plist` |
| plist 里的可执行文件用 `BundleProgram` 给出 **app bundle 相对路径** | `launchd.plist(5)` 的 `BundleProgram`：「an app-bundle relative path to the executable for the job. This key is only supported for plists that are installed using SMAppService」 |
| 相对路径的基准是 `.app` 根（不是 `Contents`），所以值以 `Contents/` 开头 | 取值实例：多个公开项目把 `BundleProgram` 写成 `Contents/Resources/bin/<helper>`（本轮查看的三个公开仓库一致，属第三方实现证据，不是 Apple 文档） |
| 助手二进制可以放在 `Contents/Resources/` 里 | 同上；另外 `mygo build` 会把资源放进 `Contents/Resources`（§4.3） |
| 应用要能被**登录前**访问到，否则开机不会引导 daemon | `SMAppService.h`：「For a LaunchDaemon to be bootstrapped during boot, the containing application must be accessible before a user logs in… recommended that the application bundle live in /Applications」 |
| 需要 `AssociatedBundleIdentifiers`（只有 legacy plist 需要） | Apple 迁移文档；`launchd.plist(5)` 同名键 |

因此本规格的目标布局是：

```
Cubbix.app/
├── Contents/
│   ├── MacOS/Cubbix
│   ├── Library/LaunchDaemons/com.conteman.cubbix.helper.plist   ← mygo build 产不出（§4.3）
│   ├── Resources/
│   │   ├── bin/cubbix-helper                                    ← mygo build 会签名（§4.5）
│   │   └── …（图标、语言、前端）
│   └── Info.plist
```

plist 内容（`BundleProgram` 形式；T3 换成 `Program` 绝对路径，其余不变）：

```xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key><string>com.conteman.cubbix.helper</string>
  <key>BundleProgram</key><string>Contents/Resources/bin/cubbix-helper</string>
  <key>RunAtLoad</key><true/>
  <key>KeepAlive</key><true/>
  <key>ThrottleInterval</key><integer>10</integer>
  <key>ProcessType</key><string>Background</string>
  <key>AssociatedBundleIdentifiers</key><array><string>com.conteman.cubbix</string></array>
</dict>
</plist>
```

（`RunAtLoad` 在 `launchd.plist(5)` 里被建议避免「speculative launch」，但开机补救恢复必须靠它；`ThrottleInterval` 防止崩溃抖动。）

### 4.3 `mygo build` 能否把额外二进制与 plist 打进包并正确签名、公证

**二进制：能。plist：不能。** 逐条依据：

| 问题 | 结论 | 依据 |
| --- | --- | --- |
| 能不能把助手二进制放进包 | 能，放 `resources/` 或配置的 `resources` 列表里，落到 `Contents/Resources`，`App.Path(mygo.PathResources)` 取路径 | `mygo@v0.6.2/docs/distribution.md` 的「Resources」「Platform resources」「Helper executables」三节；`cmd/mygo/resources.go` 的 `copyResources`（目标目录固定为 `Contents/Resources`） |
| 会不会签名 | 会，`mygo build` 从里到外签每个 Mach-O 与含代码的 bundle，Developer ID 时带 hardened runtime 与时间戳 | 同文档「Helper executables」一节；`cmd/mygo/resources.go` 的 `signNestedCode`（遍历 `Contents/Resources`，逐个 `codesign --options runtime --timestamp`） |
| universal 包怎么办 | 助手按平台目录放（`resources/darwin-arm64/bin/…` 与 `darwin-amd64/…`），`darwin/universal` 会用 lipo 合成通用二进制 | 同文档「Platform resources」一节 |
| 能不能写 `Contents/Library/LaunchDaemons/` | **不能**。`writeBundle` 只建 `Contents/MacOS`、`Contents/Resources`，可选写 `Contents/embedded.provisionprofile`；`copyResources` 的目标恒为 `Contents/Resources`；配置结构体里没有任何「额外 bundle 路径」字段 | `cmd/mygo/bundle.go` 的 `writeBundle`；`cmd/mygo/resources.go` 的 `copyResources`；`cmd/mygo/config.go` 的 `Config`／`MacOS` 字段清单（`resources`、`urlSchemes`、`fileAssociations`、`macos.*`，无 bundle 文件项） |
| 有没有构建钩子 | 没有。`mygo build` 一次跑完「编译 → 建 bundle →（资源签名）→ 整体签名 → DMG/公证 → 更新包」，没有插入点 | `cmd/mygo/build.go` 的主流程顺序；`codesign`（`bundle.go` 的 `codesignArgs`）紧随 `writeBundle` |
| 上游现状 | 当前 MyGo 主线文档里也没有 LaunchDaemon／launchd 布局的支持 | 公开仓库 `mygo` 最新的 `docs/distribution.md` 检索 `launchd`／`LaunchDaemon` 无结果（本轮只读核对） |
| 开发构建 | `mygo dev` 的资源直接放在可执行文件旁，没有 `.app`；没有 bundle 时连 `SMAppService.mainAppService` 都用不了 | `mygo@v0.6.2/docs/distribution.md` 的「Resources」；`mygo@v0.6.2/internal/darwin/login.go` 的 `bundlePath` 在非 bundle 情况返回错误 |

### 4.4 做不到时的替代方案

| 方案 | 做法 | 优点 | 代价／风险 | 结论 |
| --- | --- | --- | --- | --- |
| **T1 等 MyGo 支持** | 向 MyGo 提需求（例如 `macos.bundleFiles`，在签名前把文件放进 `Contents/` 指定相对路径）；升级 MyGo 需单独 Issue（AGENTS「MyGo 固定 v0.6.2」） | 保留 Apple 推荐的布局与全部安全属性（系统校验 bundle 内外签名、系统设置里有开关） | 时间不可控；升级本身要一轮回归 | **目标形态，推荐优先推进** |
| **T2 发布脚本后处理** | `mygo build` 之后插入 plist、重新签名、重新公证、重做 DMG | 不改 MyGo | 更新包（`mygo build` 生成的签名归档）与处理后的应用不再一致，ADR 004 的应用内更新会把「没有 plist 的应用」装回去；公证与 DMG 也要自己重做 | **不选**（会破坏 ADR 004 的信任链） |
| **T3 legacy 安装层** | plist 走 `/Library/LaunchDaemons/`，助手复制到 `/Library/PrivilegedHelperTools/`，用**一次**管理员授权完成；`Program` 用绝对路径；plist 带 `AssociatedBundleIdentifiers` | **现在就能落地**，不动 MyGo、不动更新链；除「安装/注册」外，会话、IPC、恢复、状态机与 T1 完全相同 | 需要自己写安装器；`/Library/PrivilegedHelperTools` 副本在助手版本变化时要一次重新授权；Apple 视其为 legacy 布局；系统设置里照样有开关（`launchd.plist(5)` 的 `AssociatedBundleIdentifiers`），用户关掉后的状态用 `SMAppService.statusForLegacyPlist(at:)`（macOS 13+）读 | **在 T1 落地前采用** |
| **T4 只做 `caffeinate`** | 不碰 `disablesleep` | 零风险 | 不满足需求（调研与 Apple QA1340 都说明 assertion 挡不住合盖） | 不选 |

实现上把「安装／注册」抽成接口，两种形态共用其余全部代码：

```go
// lidService is the install layer: SMAppService when the bundle holds the
// LaunchDaemon plist, the legacy /Library install otherwise.
type lidService interface {
	Status() lidServiceStatus   // unavailable / notRegistered / requiresApproval / enabled / broken
	Register() error            // 需要用户确认时才弹鉴权
	Unregister() error
	OpenSettings()              // 打开系统设置的登录项页
	HelperPath() (string, bool) // 助手二进制路径；SMAppService 下读 Resources，legacy 下读已安装副本的版本
}
```

T3 的安装脚本必须是**全常量**，用一次 `osascript -e 'do shell script "<常量>" with administrator privileges'` 完成全部步骤，脚本里不拼接任何来自文件系统或 IPC 的字符串（避免引号注入）：

```
1. install -d -m 0755 -o root -g wheel /Library/PrivilegedHelperTools
2. install -m 0755 -o root -g wheel "/Applications/Cubbix.app/Contents/Resources/bin/cubbix-helper" \
        /Library/PrivilegedHelperTools/com.conteman.cubbix.helper
3. 写入 /Library/LaunchDaemons/com.conteman.cubbix.helper.plist（内容为常量），chown root:wheel，chmod 644
4. launchctl bootout system/com.conteman.cubbix.helper（失败忽略）
5. launchctl bootstrap system /Library/LaunchDaemons/com.conteman.cubbix.helper.plist
```

因为路径是常量，T3 要求应用位于 `/Applications/Cubbix.app`；不在该位置时合盖保持显示 `LidUnsupported`（tooltip 说明把应用放进「应用程序」文件夹）。这条限制只影响 T3，T1 落地后删掉。

## 5. 与现有常亮的关系

### 5.1 附加开关，不是第三种模式

**推荐：附加开关。** 理由：

1. 「保持屏幕常亮／仅保持任务」是 `caffeinate` 的两个参数组合（`keepawake.go` 的 `awakeArgs`：`-d -i` / `-i`），互斥；而 `disablesleep` 是**另一套机制**，与这两者正交，「合盖也保持 + 仅保持任务」是最有用的组合，用互斥的分段器表达不了。
2. 卡片面板的分段器（`panelModeSwitch`）已经承载模式语义；把合盖塞进去会变成三选一，语义错误且让会话状态更难读。
3. 合盖保持是**安全敏感**决策：它应该是一个可以被单独看见、单独关掉的开关，而不是藏在模式里的隐含后果。
4. 停止语义简单：关总开关 = 两者一起停；关合盖开关 = 只恢复 `disablesleep`，`caffeinate` 会话继续。

数据结构：

| 位置 | 字段 | 含义 |
| --- | --- | --- |
| `awakeSession`（`keepawake.go`） | `Lid bool` `toml:"lid,omitempty"` | 本次会话是否带合盖保持 |
| `Config`（`config.go`） | `AwakeLid bool` `toml:"awake_lid"` | 记忆开关；`⌃⌥⌘K` 与「记忆会话」路径据此决定是否连带开启 |
| `lidController`（新） | `state`、`sessionID`、`reason` | 运行时状态（§3.7） |

`config.AwakeLid` **只在助手读回确认 1 之后**才写入；失败一律不写（否则下次快捷键会拿一个假的记忆去开）。

### 5.2 组合规则

| # | 情况 | 规则 |
| --- | --- | --- |
| 1 | 合盖 + 定时（30m/1h/2h/自定义/直到） | helper 的 `deadline` = `session.End`；两边同时到点 |
| 2 | 合盖 + 不限时 | 无 `deadline`，靠租约 + §8.4 待决定 3 的硬上限 |
| 3 | 合盖 + 跟随进程 | 无 `deadline`（跟随会话的 `End` 为空）；应用 `poll` 发现目标进程消失 → 停会话 → 恢复。助手不看进程 |
| 4 | 合盖开关在常亮未开启时被点击 | 用 `selectedSession()` 开启常亮，成功后开合盖；任一步失败都回到 `lidBlocked`／不写入记忆 |
| 5 | 运行中切换模式（`setMode`） | 只重建 `caffeinate`（既有行为），合盖保持不动。重建成功 → 会话仍活跃，合盖保持照旧；重建失败 → `awakeController.start` 已经把会话置为未激活，`syncLid` 随即将合盖恢复并显示错误（一致性优先于「尽量保住合盖」） |
| 6 | 运行中点时长药丸（`setDuration`） | `caffeinate` 重建（既有行为）。**新截止时间晚于助手的 `deadline` 时必须重发一次 `enable` 续期**（带新 `deadline`，助手只更新 journal 里的时间并读回，不动 `disablesleep`），否则助手会按旧时间提前恢复；新截止时间更早时不改助手，由应用在 `session.End` 到点时统一停止 |
| 7 | `⌃⌥⌘K` 快捷键开启／停止 | 开启时按 `config.AwakeLid` 连带合盖；停止时两者一起停 |
| 8 | 会话自然到期 | `awakeController.poll` 判到期 → `awakeChanged` → 合盖恢复（§5.3） |
| 9 | 跟随的进程结束 | 同上（`ProcessEnded` 错误的显示优先级不变） |
| 10 | 改用电池（会话中） | 助手 5 秒内恢复并给出 `reason=battery`；应用**不保留** `caffeinate` 会话：整个会话按「已因切换电池结束」处理，`caffeinate` 一起停，统一由 `awakeChanged` 收敛，避免出现「屏幕不睡但合盖会睡」的混合状态 |

### 5.3 生命周期对齐（顺序是硬要求）

**开启**（`startAwake` 内，`caffeinate` 成功之后）：

```
1. 前置检查：AwakeEnabled、内置屏、lidService 状态、电源是 AC、无外部设置
2. caffeinate 启动（既有代码）
3. 连助手（必要时先注册 + 起 daemon，最多等 5 秒）
4. enable(deadline) → 读回 1
5. 写 config.AwakeLid = true、config.AwakeSession = 本次会话
6. 刷新界面：猫标 tooltip、卡片状态行、合盖开关
```

第 4 步失败：会话保留为普通常亮（`Lid=false`），`config.AwakeLid` 不写，界面 alert 对应原因。**绝不**出现「合盖保持开了但常亮没开」。

**停止**（任何结束路径）：

```
1. disable → 读回 0（失败则进入 lidRestoreFailed 并重试，界面常驻 alert）
2. 停 caffeinate（既有 stopLocked）
3. 清 config.AwakeSession；config.AwakeLid 保留（记忆）
4. 刷新界面
```

先停合盖再停 `caffeinate`：中途崩溃时最坏结果是「普通常亮还在」这种无害状态，而不是「没有会话却 `disablesleep=1`」。

**统一收敛点**：所有结束路径（到点、目标进程结束、用户停止、退出、电池、助手异常）都必须经过 `awakeChanged`（`awake_app.go`）与新增的 `syncLid`。实现上把「会话是否活跃」与「合盖保持是否在读回确认的状态」做成一对幂等的同步：`syncLid` 只比较这两者，不一致就补齐，避免在十来条路径里各写一遍恢复调用。

**应用重启后的恢复**：`restoreAwakeAfterLaunch` 现在会按剩余时间恢复 `caffeinate`。合盖保持**不自动重开**：助手启动时已经无条件恢复过一次（§3.5），自动重开会在「助手反复崩溃」时形成循环且掩盖故障。改为：若上次会话带 Lid，界面在状态行给一次说明（`R05LidRestored`：上次的合盖保持已结束），用户点开关再开。

**更新（ADR 004）**：`update_view.go` 里 `RestoreAwake` 的记录方式不变，`awakeSession.Lid` 随之持久化；「重启更新」前先按上面「停止」的顺序恢复，恢复失败时不允许重启更新（与「有未保存 JSON 时先提示」同一类保护）。

## 6. 安全分析

### 6.1 资产与威胁模型

| 资产 | 被谁威胁 | 后果 |
| --- | --- | --- |
| root 权限（助手进程） | 本地其他进程（同用户或其他用户） | 提权到 root 就是全系统沦陷 |
| `disablesleep` 设置 | 任意本地进程、包装成 URL 的网页 | 机器不睡、耗电、过热；合盖散热受限 |
| 「谁在替用户做决定」 | 任意本地进程 | 用户以为系统会睡，实际不睡 |

模型假设：单用户 Mac、用户是管理员、应用放在 `/Applications`；攻击者能做的仅限于「以普通用户身份运行的本地进程」。**不**把「root 已被攻陷」或「内核被攻陷」纳入防护范围（防护不了）。

### 6.2 攻击面

| # | 攻击面 | 防护 |
| --- | --- | --- |
| 1 | 其他本地进程连接 socket 并冒充 Cubbix | `LOCAL_PEERTOKEN` + SecCode 校验 Team ID `P93GN4N3DC` 与 identifier `com.conteman.cubbix`；不通过即断开，不读请求体（§3.3） |
| 2 | 其他进程抢先绑定 socket 冒充助手，骗取 Cubbix 的连接 | `/var/run` 只有 root 能写；应用连上后再校验对端签名（只校验 Team ID，§3.3），不一致即断开并只记一条不带对端信息的日志——不给用户看，避免被刷成噪音 |
| 3 | 通过 IPC 注入命令／参数 | 协议只有 5 个固定 `op`、字段值全部枚举或 RFC3339；`pmset` 参数是常量；不调用 shell；单行上限 8 KiB；拒绝后立刻断开 |
| 4 | 伪造 journal 让助手恢复（或阻止恢复） | journal 在 root 0700 目录、0600 文件；普通用户无法写；写盘顺序保证不会出现「值 1 且无 journal」 |
| 5 | 网页／其他应用用 `cubbix://awake?lid=1` 静默开启 | 必须已授权；必须带 1..480 的 `minutes`；不弹鉴权；开启后状态行与 tooltip 可见；`FeedbackMode` 关闭时也强制一条系统通知（例外，见 §8.1） |
| 6 | 用 URL 反复触发鉴权弹窗骚扰 | URL 路径**永不**调用 `Register()`；注册只能由用户点击卡片／命令面板产生 |
| 7 | 助手二进制被替换（T3 特有） | 副本放在 root 拥有的 `/Library/PrivilegedHelperTools`（root:wheel 0755），源路径是常量；应用更新后由「助手需要更新」提示再走一次授权覆盖 |
| 8 | 应用成为「通用提权代理」 | 助手不接受路径、命令、任意 `pmset` 参数（§3.1 白名单）；应用侧不接受 URL 传入的任何标识或参数名 |
| 9 | 拒绝服务（一直占着 `enable`） | 每个连接只能有一个会话；`busy` 时不重复改动系统设置；连接与请求都有超时 |
| 10 | 日志泄露 | 助手日志只写状态迁移、`reason` 码与读回值，不写进程名、路径、用户名、IPC 原文 |

### 6.3 最坏情况

| 情况 | 结果 | 界面必须做的 |
| --- | --- | --- |
| 应用被强杀 | 助手在 15 秒内（EOF 通常 < 1 秒）恢复 | 无（应用已死） |
| 应用与助手同时被强杀 | `disablesleep` 保持 1；launchd 会在 `ThrottleInterval`（10 秒）后重启助手，重启时无条件恢复 | 无（两者都不在），但下次启动应用要读回并说明 |
| 用户在系统设置里关闭／停用助手，会话进行中 | daemon 被卸载 → 立刻没人负责恢复；`disablesleep` 可能保持 1，直到助手下次启动 | 应用检测到断连 → 常驻 alert「合盖保持已中断」，tooltip 给 `sudo pmset -a disablesleep 0`；应用同时尝试一次重新注册 |
| helper 被 `unregister` 且不再启动（卸载） | 同上，且无人恢复 | §3.6 规定「恢复成功才允许停用」；做不到时拒绝停用并解释 |
| 系统冻结／内核崩溃 | 断电重启后值是否仍为 1 取决于设置是否持久（未证实，§4.6 第 5 项） | 应用启动时读回，若为 1 且无 journal → 按外部设置只提醒 |
| 电量耗尽（若未来允许电池） | 关机 | §5.5 的额度与恢复 |

### 6.4 残余风险如何告知

1. 首次授权前，卡片状态行的 alert tooltip 写明「合盖保持需要一次系统授权，之后就绪」——不写长段说明。
2. 异常状态下 tooltip 给出**可复制**的修复命令（`sudo pmset -a disablesleep 0`）。不加常驻说明行：只在异常时出现，符合 AGENTS 的低信息密度。
3. `README.md` 与 CHANGELOG 里各一句：合盖保持会修改系统设置，异常时用上面的命令手动恢复。
4. 不承诺「一定能恢复」：文档与文案都不用「保证」。

### 6.5 明确禁止的做法

- 不用 `sudoers` 白名单或任何长期免密规则（调研已评估：授权长期存在，且仍需 watchdog）。
- 不用 `osascript with administrator privileges` 去直接执行 `pmset`（每次都要密码、且没人保证恢复）。
- 不把 `disablesleep` 的恢复挂到「应用退出回调」上当成唯一手段。
- 不让助手接受任何形式的「执行命令」「设置其他电源参数」。
- 不在测试里真的调用 `pmset`、不在测试里注册任何 daemon（§7.4）。
